# 真机验收闭环

「能点开」只算亮了；存档变了、杀掉重开还在，才算活了。

## 每轮改动的固定流程

1. 记录改动前的 `git diff --stat`
2. 改补丁 / 模块，加断言
3. 跑补丁脚本 —— 必须看到**全部自检通过**
4. 跑构建脚本 —— 确认产物大小 / 时间变化
5. 用与已验证包**相同**的签名方式签名
6. 安装 → force-stop → 启动
7. 抓 logcat + 截图 + 记录操作路径
8. 通过后才更新文档

```powershell
adb install -r --no-incremental <candidate.apk>
adb shell am force-stop <package>
adb shell monkey -p <package> 1
```

## 几个项目共用一台测试设备

用户的 BlueStacks（实例 `Pie64`，Android 9，1600x900，自带 root）和手机由案例 A、B、C 等多个项目共用。规矩：

1. **用前登记、用完销账**：唯一一份登记表是 `<项目根>\docs\<分档目录>\设备占用.md`。开始前把自己写进"谁在用"，
   结束时改回"空"并写清装了/卸了什么包、存档是否还原、应用是否 force-stop。
2. **各走各的 adb 服务端口**：BlueStacks 用 `<项目根>\work\platform-tools\adb.exe -P 5038 -s 127.0.0.1:5555`
   （起服务时带 `ADB_USB=0`，不碰手机）；手机走 5037；另一个项目的环境走 5039。启动模拟器：
   `"C:\Program Files\BlueStacks_nxt\HD-Player.exe" --instance Pie64`，再轮询 `getprop sys.boot_completed`。
3. **只动自己的包**。别的项目的包要卸载/覆盖，先把存档（`/data/data/<pkg>/shared_prefs/*.xml`，BlueStacks 上用 `su -c` 读）
   备份到那个项目的 `logs\`，确认安装包本身在硬盘上还有一份，再动手。
4. **演示包用完就收**：给用户演示的定制包装上后往往一直留在设备上（曾清掉过一个几天前装上的定制样例包）。
   交付时在登记表写清"装着哪些包、各是干什么的"，确认不再需要就卸掉。
5. BlueStacks 上 `run-as` 不可用，读写存档用 `su -c`；`adb install` 拒绝非 `.apk` 后缀（`xxx.apk.1` 这种原包先建一个 `.apk` 硬链接）。

6. **手机挂在哪个 adb 服务端口上不固定**（2026-10-20~22 实测在 5038、5039 上都出现过）：别的项目的服务会抢走手机的 USB，其他端口就看不到它。用 `adb -P <端口> devices` 逐个查，用占着手机的那个服务装包，别去杀它。开发脚本默认连模拟器；用户在用手机时，守卫还会连带拒绝对模拟器的操作，要显式指定目标。备份存档后，核对它到底是哪台设备的（曾经把模拟器的存档当成了手机备份）。

7. **测试包用第三个包名装**（案例 B 2026-11-03）：设备上已经装着正式包和它的存档时，测试包换一个包名并排安装，验完只卸它。开工和收尾各记一次存档、安装包的 md5，逐项比对。需要正式存档时，往测试包里放一份副本，验完放回。
8. **签名不同就不能覆盖安装，重装后的数据目录让系统自己建**：测试签名的包不能 `install -r` 覆盖正式签名的包，要先卸载；卸载前先确认新包已经打好、存档已经备份。卸载后别用 root 手工 mkdir 再推存档，那样目录是 root 属主，游戏读不到。正确做法：先装好包、启动一次，让系统建好目录，再推存档，改成应用的 uid，并跑 `restorecon`。

## 日志里必须确认"没有"的东西

- `LuaException`
- `attempt to index`（空对象访问）
- `CRC Mismatch`
- `SIGSEGV` / 主线程冻结
- 资源加载失败

## 验收判据

- **状态真的变了**：数量、进度、可领取 → 已领取
- **重启后仍然正确**：杀进程重启 / 冷启动 / 飞行模式冷启动
- **退出再进不重复、不丢失**
- **返回路径干净**：来回切页面没有残留面板、黑屏、按钮失效
- **联网时也不外发**：平时都在断网下测，从来看不到联网行为。至少验一次"网络全开冷启动"：root 下 iptables 对游戏 uid 丢包（`-m owner --uid-owner <uid> -j DROP`，数据不出去），
  轮询 `/proc/net/tcp*` 按 uid 读 SYN_SENT 的目标、tcpdump 记 53 端口；修完撤掉规则再测一遍，要求零套接字、零 DNS。没 root 的真机上 `adb shell` 也能读 `/proc/net/tcp*`；uid 取自 `ps -o UID -p $(pidof 包名)`，并对一个在联网的应用跑一次对照。正式包检查脚本里加一项"清单不许有 INTERNET"。案例见 `case-b-laya-native.md` 末节。

- **发出去的是全新档**：存档在每台手机自己的应用数据里，不在安装包里，新装就从 0 开始。出包前仍要用正式包做的分身清空数据冷启动一次，检查等级、货币、首个任务、日期，日志无报错、没有调试功能，然后算 SHA256、写发版说明。往用户自己的正式安装上覆盖时，如果被会话的权限层拦下（判成生产部署），不要绕过，把命令交给用户自己执行。
- **发包前做一次「旧包存档升级」测试**（案例 A 2026-10-31）：玩家的真实路径是拿上一版公开包玩出来的存档，覆盖装新包。只测新包自己能不能玩，会反复漏 bug。做法：装上一版公开包玩出存档 → 覆盖装新包 → 逐键对比存档有没有被删改 → 截图看界面；每个发布变体（全资源 / 免费）都过了，才放进发布目录（案例 A 写成了 `upgrade_check` 工具）。新加了授权功能位时还要验旧码用户：覆盖后旧授权还在、新功能保持关闭；换新码后新功能打开；冷启动后仍在。测试码用正式包证书的本机码签（案例 B 2026-10-20）。
- **声音只能验到「读了对的文件」**：截图和日志听不到声音。点语音后抓 logcat，看游戏读了哪些缓存文件，从包里取出来和目标音频比对（案例 B）；正式包没有日志时，看媒体进程打开了哪些文件（见 `case-b-laya-native.md`）。报告里写「加载了 xxx」，不要写成「已确认出声」。

- **语音驱动的流程（通话、语音剧情）**：量每段从点击到下一个回复气泡出现的时间，要和音频文件的实际时长对得上；最后一段放完自动挂断，并记成已接；中途挂断只记一次尝试，不算已接；冷启动后记录还在（案例 B 2026-10-20）。

## 常见"假通过"

| 看起来通过 | 实际 |
|---|---|
| 界面能打开 | 只是面板渲染了，功能没跑 |
| 一次操作成功 | 没覆盖重复进入 / 连续点击 |
| 有网环境下测过 | 没测离线 |
| 没触发崩溃 | 只是没触发，不等于不会崩 |
| 探针录了数据，结论很明确 | 计时列、血量列长时间不变，录到的是冻结的现场（玩家被秒杀或逻辑停了），整段作废，要补跑 |
| 新版本日志里有报错，就怪到新补丁头上 | 没用“新功能根本没启动”的对照跑复现过，两边的日志设置也不一样；先在对照里复现同一条报错再归因 |
| 注入自测全过 | 测试恰好跑在一份满足前提的存档上（案例 A：领宝箱需要的活跃度只认单独一个键，手机那份档当天正好是满的；换一份档就 `blocked activity=0`，宝箱根本没领成）。在自测里先把前提显式写好、结束时还原，再加一条「前提成立」的断言，并在不同的初始存档上跑 |
| 注入 `ShowPanel` 直接打开面板，满屏占位文字「111111111」和空图标，像是改坏了 | 直接打开跳过了正常初始化，数据没填。直接打开只用来快速看一眼；判断界面对不对，要从游戏里的真入口点进去 |
| 模拟器上复现玩家报的限时活动问题，日志说活动早已结束 | 测试存档里残留着开发时钟偏移键（例：+4 天），游戏时间被推过了活动期。复现前先读存档里的偏移，去掉后再复现（改副本）；测完按备份还原并核对键数；要测跨时刻的功能时再显式设偏移（案例 A 2026-10-24） |
| 满级测试档上，某个提示（如「获取途径」）从来不出现，以为功能没做 | 客户端只在材料数为 0 时才弹它。先读客户端的触发条件，再用调试通道把条件造出来（例如把某材料清零）去验（案例 B） |

**查不出根因的玩家报告，先加诊断输出再做低风险缓解，不要写成「已修复」。** 案例 C 的「音乐电流声 / 开 Wi-Fi 就卡」在模拟器上复现不出（开 / 断网总 CPU 都约 40%，而且模拟器关 Wi-Fi 后仍显示已联网）。做法：做低风险改动（吹气互动改成按住判定、不开麦克风避免手机切通话音频模式；Wi-Fi 下不再自动后台下载），同时在导出日志头加一行诊断（CPU、联网状态、最近 60 秒帧率、音频采样率 / 缓冲，联网状态变化也记一行），要动引擎初始化（如 FMOD 的采样率 / DSP 缓冲，需改 C# 程序集）等有真机复现再做。汇报时写清「做了哪些缓解 + 加了诊断」，不要写成已修复。

## 高风险功能要单独加长回归

凡是涉及随机、动画、异步加载的功能，回归步骤要显式写全。例如本地抽卡：

1. 单抽 → 返回主面板
2. 十连 → 动画完整播放
3. 返回后仓库数量正确
4. 重复进入池子不冻结
5. 杀进程重启不崩溃

## 拿"落盘证据"，别只信界面和内存日志

"重启后仍然正确"要有**落盘层**的硬证据，不能只看界面数字或 logcat 里的内存值——两者都可能来自
"启动时重新灌一遍默认数据"，看起来一样，实际没存。

Unity/Android 常见做法是直接读登录态 SharedPreferences（`run-as` 只对 debuggable 包有效）：

```powershell
adb shell run-as <package> ls /data/data/<package>/shared_prefs
adb shell run-as <package> cat /data/data/<package>/shared_prefs/<package>.v2.playerprefs.xml
```

对着键值判断，例如 `OFFLINE_PLAYER_LEVEL_V1=120`、`OFFLINE_MAIN_TASK_ID_V2=10203`、
`OFFLINE_CARD_STARS_V1=220500:2`。这些键既证明"写进去了"，也证明"任务/进度真的推进了"。

同一套证据还能反证"不卡主线"：任务 ID 在 prefs 里前进了，就是结算链路真的走完了。

## 装机状态以现场读数为准，不信口头描述

"我已经把包删了 / 手机上装的是最新版"这类说法（包括自己上一轮写的）不能直接写进交接文档：
本轮实测就是用户说"包已删"，`pm list packages` 读出来**仍装着**，而且装的是实验配置那一版。

```powershell
adb shell pm path <package>
adb shell dumpsys package <package> | Select-String "versionName|lastUpdateTime"
adb shell run-as <package> ls /data/data/<package>/shared_prefs
```

三件事都要现场读：**包装没装 / 装的是哪个时间点的包 / 存档是什么状态**。读不出来就当"未知"，
不要用推测填空；交接文档里的每一个"当前状态"都应该是某条命令的输出。
**包大小相同不代表没改进去。** apksigner 的对齐 / 填充常让改过内容的 APK 和上一版大小一字节不差。要确认改动真打进去了，就对比两次构建的脚本包内容，并在产物里 grep 新代码的标志字符串（如模块名 `offline_tier`），搜得到才算打入。

**装到用户自用手机前后，存档要逐字节比对。** 真机是用户的，存档丢了无法重来。覆盖安装前用 `adb exec-out run-as <pkg>` 导出 `shared_prefs` 里的 playerprefs xml 做备份，覆盖安装后再导出一次，两份完全一致才算存档没动。Git Bash 会把 `/data` 开头的绝对路径改写坏，用相对路径（`shared_prefs/...`）或命令前加 `MSYS_NO_PATHCONV=1`。
覆盖安装后再看两项：`dumpsys package` 里的 firstInstallTime 没变、应用数据目录的 inode 没变（`stat`），并确认没被装进系统的分身空间。没 root、也不能 run-as 的正式包，就靠这两项证明存档没被清。要用户粘贴授权码的步骤，签好码、写好步骤交给用户自己做（案例 B 2026-10-20）。

## 把结论边界写清楚

同一个"通过"里，往往混着两种完全不同的结论，报告里必须拆开：

- **不卡主线**：即使评分/条件不达标，流程仍判定通过并推进。（本次案例 A 的 2-2 剧情战斗要求 5250，
  实测评分仅个位/十位，仍结算并推进到 2-3。）
- **达到阈值**：评分/条件真正满足需求线。

只验证了前者就不要写成"战斗已通过"——写成"结算链路通畅 + 低分不卡主线，达标路径未验证"。
