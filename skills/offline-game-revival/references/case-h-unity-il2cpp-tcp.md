# 案例 H：Unity IL2CPP + 自研 TCP 长连接，用自写服务端顶替原服

2026-11-16 起。和 A/B/C/G 的区别：**不做离线包**。客户端不动，照常联网，
只是把域名指到局域网里一台跑着自写服务端的机器。所以没有重打包、没有签名、
没有资源校验，难点全在协议和数值上。

项目形态：Rust（axum + tokio）写服务端，TCP 一个端口 + HTTP 一个端口，
iptables DNAT 把客户端要连的几个端口指过去。存档是一个 JSON 文件。

## 为什么值得单独记

前面几个案例都是「服务器已经死了，只能从客户端倒推」。
这个案例**原服还活着**，所有不确定的地方都能抓真包对照——
这是最省时间的前提，动手前先确认它还在不在。

## 一、先抓包，再写一行代码

一个几十行的 TCP 透传代理就够了：监听本地端口，转发到真服，
把每个帧按 `{时间, 方向, cmd, 序号, 长度, hex}` 记成 JSON。
DNAT 指向代理，玩十分钟，协议的轮廓就有了。

本地帧格式：

```
32 45 | PkgLen(BE u32) | payload
payload = Crc(4) Seq(2) Magic(2)=0x3243 Cmd(2) CSPkgLen(4)
          Ver(2)=1 Echo(4) SvrTime(4) body
```

body 用 XXTEA 加密，key 是 16 字节字符串（这里不抄）。

**几个容易漏的点**：

- `32 45` 是两字节魔数，看着像 ASCII `"2E"`，其实是数组长度前缀的残留。
- `Magic` 字段（0x3243）和帧头的 `32 45` 是同一个值的两种字节序，别当两回事。
- `Crc` 只覆盖部分字段，客户端校验不严，写错也能连上，但长连接会随机断。
  排查「偶发断线」先看这里。

### 业务头容易少两字节

真服的 body 前面还有一个 8 字节业务头：

```
[0:2] BE u16 cmd
[2:4] 0
[4:6] BE u16 (len(body) + 2)   ← 注意这个 +2
[6:8] BE u16 1
```

按 `len(body)` 写，客户端会**静默丢弃**这个包，不报错。
如果服务端发送函数已经自动补这个头，抓包存的 `body` 就要存纯负载，
否则头会被补两遍。

## 二、cmd 号从 metadata 的字符串顺序推

`global-metadata.dat` 里 `CS_CMD_*` 字符串**在同一协议家族内按 cmd 号递增排列**。
找到家族里任意一个已知 cmd，按字符串出现顺序做差值就能推出一片：

| 索引（以家族第一个为例 0） | 相对偏移 | 名称 |
|---|---|---|
| 0 | +0 | `CS_CMD_<家族>.DATA` |
| 15 | +15 | `CS_CMD_<家族>.BUY_XXX_REQ` |
| 16 | +16 | `CS_CMD_<家族>.BUY_XXX_RES` |

（实际 cmd 号是四位数，这里只给相对位置。）

比逐个扫包快一个数量级。三个坑：

1. **`CS_MAX_*` 也占一个 cmd 号**，算差值时要数进去，否则后面全部偏移一。
2. **名字表顺序 ≠ cmd 顺序**，需要先用**两个以上已知 cmd** 验证线性关系
   （差值一致）再用；只用一个锚点推出整片，错一格全错。
3. 家族之间的边界不好定。找 `CS_MAX_<家族>` 或 `CS_CMD_<下一个家族>` 当右边界。

**验证办法**：推出来的 cmd，在抓包里找有没有对应的 s2c 包。
没有发过也没出现过的 cmd，先当候选，别写进代码。

命令行可以这样看（Python，只读）：

```python
md = open("global-metadata.dat","rb").read()
i = md.find(b"CS_CMD_HERO")
names = re.findall(rb"CS_CMD_[A-Z0-9_]{3,50}", md[i-400:i+6000])
# names 的**顺序**就是 cmd 顺序，第 n 个 = 锚点 +n
```

## 三、踩过的坑

### 手搓的包长度不对，表现是「卡死」

用 13 字节手搓了一个推送，真服的是 78 字节。客户端报一个笼统的
「网络数据错误」，然后断线重连，无限循环——看起来像卡顿，其实是包坏了。

**修法**：和真服的包逐字节 diff，别凭字段表猜。

### 登录慢：每个包之间 sleep

277 个登录推送，每个之间 sleep 8ms，累计两秒多。
改成让出调度（`yield_now()`）而不是真睡，快很多。
登录期间的推送本来就不需要节流。

### 回高版本号会把「开始游戏」按钮变灰

服务端回的版本号比客户端高，客户端以为要热更，按钮点不动。
**回不高于客户端自己的版本号。**

### 服务端的问题也会出现在真服上

某个数字在界面上一直不刷新。换了 6 个数据源（推送头里的字段、配置表里
对应记录的两个值、存档字段、另一个配置文件）都没用。

最后连真服做同样的操作，**界面也还是那个数**——
说明它是客户端本地算出来的，服务端发什么都不改。

反编译 metadata 得到公式（三个键名在字符串表里连续排列，证据很强）：

```
容量 = 初始值 + 每次增量 × 已购次数
```

但这三个键的**值不在 metadata 里**（metadata 只有名字），
也不在客户端资源里——用 UnityPy 解码了全部 749 个配置表
（`assets/ab/assets_resources_config_resbin_*.bytes.ab`）都搜不到键名。
所以大概率来自服务端下发的配置，而原服那个配置不是我们发的。

**教训**：先在真服上复现一次，再决定要不要改服务端。
这一条省掉的时间比后面所有尝试加起来都多。

### 配置表长什么样：先认结构再读

解开的表里有两种形态，**先判断再解**，否则会把明文当加密读出乱码：

1. **TextAsset 里的明文**（JSON/CSV）——直接 `asset.m_Script` 解码
2. **二进制表**——通常是 `表长(BE u32) | 标志(BE u32)` 起头，后面是变长记录

实例：一张全局参数表是这样：

```
00 00 2d ef | 00 00 0a 2c | 00 00 00 01 00 00 01 43 ...
   表长 11759   长度 2604     id=1      float 2.0
```

`00 00 00 01` 是记录 id（BE u32），紧跟 4 字节 IEEE754 大端 float。
记录定长还是变长，看 id 是不是严格 +1 递增——不是就说明中间还有字符串字段。

**先按 4 字节对齐扫一遍 id 序列**，能连成 1,2,3,4… 的才是定长记录表；
连不上的是变长表，需要找长度前缀（通常是 7-bit 变长整数）。

踩过的弯路：这张表按 8 字节步长从头部对齐去解，只解出 1 条——
第一条记录比后面长 4 字节（可能是版本或容量字段），**从第二个 id 开始才对齐**。
解出一张表后先看 id 连不连续（1,2,3,4…），不连续就试几个偏移重新对齐。
本表最终从 `+20` 起步、8 字节步长，解出 323 条参数（体力上限、刷新间隔、
各种倍率都在里面）。

**判断表是参数表还是数据表**：参数表的值多是整数或短小数
（1.0 / 10.0 / 0.1 / 1800.0），id 连续且值域集中；
数据表的值会有大整数 ID（如 1000220）或长小数。

### 键名和值可能分在两处

`global-metadata.dat` 里有 `XXX_InitMaxValue` 这类**键名**（C# 字符串常量），
但**值是运行时从服务器下发的**。判断办法：

- 全 APK 搜键名字节串，只在 metadata 里命中 → 值不在客户端
- 搜键名在 ab 包里命中 → 值是本地配置，直接改就行

本案例属于前者。**这意味着改服务端也没用**——客户端会用它自己的值，
或者等服务器下发（而我们的服务端不知道这个配置）。

### 延迟回包：好建议，但要看情况

失败账本里「界面状态没就绪，回包被忽略」建议延迟 0.15~0.6 秒。
本案例实测反而更糟：

| 延迟 | 结果 |
|---|---|
| 350ms | 弹窗不关，报另一个模块的「网络数据错误」 |
| 120ms | 偶发「网络断开，请重新连接」 |
| 0 | 正常 |

真服回包天然晚几帧，所以没这个毛病；本地服务端同步回包本来是对的。
**加延迟是在我们这一侧人为制造竞态**——收益要先在真服上验证真服有没有延迟，
而不是照着账本硬套。

### 成本没扣

一个要花 100 货币的操作，余额不足 100 时也能成功。
条件判断写漏了，属于自写服务端的典型缺陷：原服会校验的，自己写的时候忘了。

## 四、锚点断言用在服务端项目上

离线案例的锚点是「包里某段字节必须是某个值」。
服务端项目没有包，锚点落在**数据文件**上：

- 某个二进制头的第 N 字节必须是几（被改成别的值客户端会误读）
- 配置表里某条记录的两个字段必须是某个值（改乱了界面会显示 `0/5`）
- 存档自洽（容量 ≥ 条目数）
- 源码里有某个函数（曾经写死过一个常量导致对不上）

写成一个 `verify_data.py`，跑一遍打印 `5/5 通过`。
以前是几十个一次性脚本，改完就删，没人知道为什么改到那个偏移。

## 五、值得照抄的几条

- **真服还活着就先抓包**，别推断。
- **先在真服上复现**，再改服务端。这一步能省掉整条错误路线。
- **一次只改一个变量**，改完立刻上设备看，不行就退回去。
  上文的「6 个数据源逐个排除」全靠这个。
- **一次性的排查脚本会堆积**：跑完就固化成断言，否则三个月后没人知道它在干什么。

## 六、和离线案例的区别

| | A / B / C / G | H（本案例） |
|---|---|---|
| 客户端 | 改包，离线跑 | 不动，照常联网 |
| 逻辑在哪 | 补丁写进包里 | 独立服务端进程 |
| 重打包 / 签名 | 要 | 不要 |
| 资源校验 | 要处理 | 无 |
| 判断依据 | 只有客户端 | **可以抓真服对照** |
| 卡点 | 资源不全、启动竞态 | 协议字段、客户端本地算的数值 |
