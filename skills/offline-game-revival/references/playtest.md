# 正常游玩复测与数值校准

离线化之后，"服务器给的东西"全变成了本地回包：发多少资源、扣不扣道具、门槛多高，都是我们自己写的。
这些只有**从全新档按玩家的顺序玩一遍**才看得出对不对。本页是这一轮怎么做、会撞到什么。

## 为什么不能用跳进度的测试档

把主线任务号直接改到后面（`settask` 一类）得到的档没有真实积累：没抽过卡、没养成、没解锁功能。
在这种档上量出来的"打不过"或"打得过"都不说明问题。数值结论只认全新档正常玩出来的。

## 开跑前

1. **备份当前存档**，再清档。清档前确认这台设备上的档不是用户自己的。
2. **查开发开关会不会往新档里塞东西**（开发版发的测试资源、预置的引导完成标记）。有就先清掉或记下来，否则量出来的资源偏多。
3. 记下起点资源（货币、抽卡券、体力），后面每个结论都要能回溯到"玩家手里当时有什么"。

## 怎么驱动设备（省上下文）

- **看日志推进，少截图。** 让补丁在关键节点打一行日志（任务完成、升级、引导步骤、战斗结算的分项），脚本按日志判断"这一段结束了没有"。截图缩到宽 540 左右的 jpg 再读。
- **点击宏要有停止条件。** 盲点一串坐标会在引导开始时把引导点乱（看门狗把它判成卡死而强制结束）。宏在日志出现"引导开始 / 剧情存档 / 任务完成"时立即停。
- **引导交给跟随器。** 引导每一步把手指坐标打进日志，脚本照着点；人工只处理它报告卡住的那一步。
- **日志过滤用单个关键字**，输出控制在 8 KB 内；构建脚本的产物路径只取那一行，不要把多行塞进变量（会导致"没装上新包却以为装了"）。
- **引导播放中不要往游戏里注入脚本**，会把主线程打崩。
- **自动点对白的宏只在纯对白时用。** 它会把战斗、选卡、抉择这些界面也一路点过去，结果是"过了但不知道怎么过的"，量出来的数不可信。每用两三轮就截图确认还在对白里。
- **长流程交给子代理玩。** 截图很占上下文。把"照着任务条推进主线、每个门槛记分项、遇到异常截图记录"写成规格，连同工具用法、常用坐标、禁止事项、停止条件一起交给执行型子代理；主模型同时改代码、写文档，等它回来再装新包。设备只有一台，子代理在玩的时候不要装包。
- **子代理回来的问题清单要自己复现一遍再修。** 它看到的是现象，原因常常和它猜的不一样（"节点没了"其实是节点被摆到屏幕外；"教程没触发"其实是它没回主页）。复现时从它存的存档点起步，先抓日志和对象状态，再动代码。
- **给子代理一个只读的诊断探针。** 偶发的显示问题（弹窗看不见之类）重启就没了。事先写好一段只打印状态的脚本，告诉子代理"遇到这种情况先跑它、把输出贴回来再重启"。

## 存档点

每过一个里程碑（一节剧情、一个引导、一次抽卡前后、每个门槛前）存一份带名字的档。
发现 bug 要改包重装时，从最近的存档点接着玩，不用从头再来；也能在同一个档上对比改前改后。
注意：存档点只在"当时的包是对的"前提下可信。包里有会污染存档的 bug（例如不扣道具的升级）时，回到 bug 触发之前的档。

## 在每个门槛记什么

门槛失败时只记"差多少"没用。让结算日志打出分项，记成一行：

`门槛名 需要=N 实得=M | 基础=a 卡牌=b×系数 队伍=c×系数 | 当时资源：等级、卡数、卡等级、货币`

有了分项才能判断该动哪一项：是玩家该有的东西没拿到（发放问题），还是系数标错了（公式问题）。

## 校准的顺序

1. **先查原版给了什么。** 新手礼包、签到、主线任务奖励、升级奖励、副本首通和掉落——配置表里都有。离线版漏发的先补上，这比调系数更接近原版体验。查表是体力活，交给只读子代理，要求带出处（文件:行号）。
2. **再模拟多天。** 第一天的资源过不去不等于设计有问题，原版玩家也是攒几天。给开发版留一个"时间偏移"开关，所有按天刷新的系统都读同一个取时函数，偏移一天就等于过了一天。按天记录资源和实力的增长，看第几天能过。
3. **最后才动系数。** 一次只动一个，改完在同一个存档点重测，并把"改前/改后/依据"写进数值文档。系数是我们自己的标定，要标明不是原版数据。

## 只有正常玩才会撞到的问题（现象 → 原因 → 修法）

| 现象 | 原因 | 修法 |
|---|---|---|
| 教程第一抽之后，下一步教程没东西可点 | 本地抽卡按权重随机，抽到了教程用不上的副件 | 教程依赖的那一抽做保底（没有主件时必出主件） |
| 教程送的资源随领邮件的先后而变 | 教程补给写成"补到 N 个"，先领邮件就不补了 | 补给改成固定发放，或教程那一步直接免费 |
| 后面解锁的功能按钮一直不出现 | "新功能弹窗已看过"只存了一个总标记，后续解锁被当成看过 | 按按钮各存各的标记 |
| 资源不够时点按钮，游戏卡死但没有弹窗 | 弹窗里的图文混排需要登录时由服务器流程装的回调，离线没装，抛空引用 | 登录后补装回调；同类"登录时才初始化"的对象一并补 |
| 从任务面板"前往"进剧情，打完黑屏或界面错位 | 同一个目的地有两条进入路线，层级状态不一样，补丁只照顾了一条 | 让两条路线走同一个入口函数 |
| 升级不扣材料 | 本地回包直接把等级加一，没实现消耗和经验 | 本地回包必须和服务器一样：校验、扣除、落盘，再回包 |
| 确认前显示的评分和结算时不一致 | 界面读的是旧缓存，结算用的是新算法 | 两处读同一个数；至少在文档里记为已知差异 |
| 引导刚开始就被看门狗结束 | 转场黑屏期间的点击被算进"卡住"计数 | 手指出现时才开始计数 |
| 门槛差一点过不去，怎么调系数都别扭 | 原版在这之前发过东西（任务奖励、章节奖励），由"领奖请求 → 服务器发放"完成；离线版任务自动推进，领奖这一步没了，奖励也就没了 | 在客户端配置表里找 `*Award*` / `*Reward*` 表，再找对应的领奖请求名；凡是离线版没处理的领奖请求，都是漏发的来源。先补发放，再谈系数 |
| 升级比原版快很多，后面的等级门槛形同虚设 | 离线化早期为了"别卡住"自编了经验来源（看剧情、打关卡都给） | 查原版经验到底从哪来（奖励表里的经验货币），按表发；自编来源留一个总开关，默认关 |
| 面板上的预览数字和结算数字不一致 | 派生数值（战力等）只在登录/升级时重算，养成操作之后没重算 | 在"进入会用到这个数的界面"时重算一次，比在每个养成入口各挂一次可靠 |
| 老存档拿不到新补的奖励 | 发放挂在"任务完成那一刻"，已经过了的任务不会再触发 | 登录时按进度补发一次，用存档键记已发过的；补发时注意别把当时已经用别的方式给过的部分（如经验）再给一遍 |
| 去过别的页面再回来，某个节点或按钮不见了，可对象明明是激活的 | 这个对象自带一块画布（Canvas）。它被隐藏后重新激活的那一刻，如果上层画布没开，Unity 把它当成根画布重摆：锚点变 (0,0)、大小变成屏幕像素、缩放变成画布缩放系数，位置跑到屏幕外，之后不会自己变回来 | 探针打印锚点、缩放、屏幕坐标就能确认。好的时候把布局记下来，每次回到这个页面检查一遍，被重摆了就摆回去；别去追是哪一次激活弄坏的 |
| 教程在正常流程里根本不出现 | 原版触发条件是"主线正好停在某一条任务，并且人在主界面"。原版的剧情地图是另一个场景，出来必经主界面；离线版把它并成了主界面的一个页签，玩家可以一直往下打不回主页，过了那条任务教程就永远错过 | 条件放宽成"主线到过这条任务"。凡是依赖"玩家一定会经过某个界面"的触发条件，离线版改了界面结构之后都要重查 |
| 一连串弹窗点完，排在后面的教程被跳过 | 防卡死的看门狗把"点了屏幕但教程没推进"算成卡住，而玩家其实是在点前面的弹窗 | 屏幕上正播着别的弹窗时不计数。弹窗本身也只播新的，别把整份名单重播 |
| 某个领奖按钮点了没反应，日志里什么都没有 | 离线发包入口把没人处理的请求悄悄丢掉了 | 在发包入口给"没人处理的请求"每种记一行日志。每次试玩后搜这一行，得到的就是还没接的功能清单，比等人撞到再查快得多 |
| 教学任务要玩家等很久 | 原版教学期的订单、需求是服务器按新手配好的；离线版用了通用的随机生成 | 教学任务期间按任务原文生成（任务说用什么就只要什么、数量取最小档） |
| 剧情里的粒子特效看不见（要玩家点的蝴蝶、光圈），或某块区域是纯白方块 | 离线版为了让界面盖住地图，把根画布改成了叠加模式（ScreenSpaceOverlay），进剧情后没改回来。叠加模式下，按排序层夹在界面之间的粒子特效全被界面盖住；"先抓屏再模糊"的着色器抓不到屏，画成白色 | 进剧情时把画布恢复成原版的相机模式，离开时再铺回去。定位办法：探针列出"又大又没有贴图的 RawImage / Image"，再把画布临时改回相机模式截图对比 |
| 某个按钮"点了没反应"，子代理报成 bug | 其实弹了一条两秒就消失的浮字（如"店铺 4 级解锁"），截图太晚没拍到 | 点完 0.3 秒内截图；子代理报的"没反应"都先这样复核一遍再动代码 |
| 重启后某个界面显示成空（阵容、列表），存档里数据却在 | 登录时客户端的查询比离线版"从存档读出来"早，答了个空的 | 每个查询的应答函数自己先确保存档已读，不要依赖登录步骤的先后 |
| 结算界面第一下点击没反应 | 一块看不见的全屏按钮（跳过）在结算后又被流程打开，盖在结算界面上 | 别只在某个时刻把它藏一次；改在它的点击函数里判断"结算界面在不在"，在就收起自己并转给结算按钮 |
| 某个按钮点了毫无反应，日志里请求和回包都有 | 原版用计数等几条回包：发一条 +1、收一条 -1、减到 0 才开面板，而且是"发完再加"。离线回包在发送函数内部就同步回来了，于是先减成 -1 再加回 0，永远等不到"减到 0" | 在发完全部请求之后补一次判断：计数是 0 且面板还没开，就在这里开。凡是"等多条回包"的入口都按这个查 |
| 从子面板返回后，页面上的按钮全没了，只剩背景，点哪里都没反应 | 为了盖住别的层，离线版把这块面板的底板抬到了很高的层级；面板自己的按钮在嵌套的小画布上，面板管理器每次重新显示时把它们排回低位，于是底板盖住了自己的按钮。在这块面板上再开别的面板（语音等）也一样被盖住 | 抬底板时把它里面带独立层级的画布一起抬同样的量；这块面板开着时，后开的面板在显示流程最后也抬到它上面。定位办法：探针列出面板下所有画布的层级，一眼能看出谁压着谁 |
| 领奖按钮点了变成"已领取"，东西没到账、没有弹窗 | 这条领取请求离线版没接，界面是自己先画成已领的；奖励以前在别处悄悄发过 | 按原版流程补上领取：到条件只标"可领"，点了才发、才弹窗，已领状态存档并在登录时写回界面 |
| 等级 / 好感一直卡在 1 级，界面显示"x/0" | 配置表第 1 级那一行的经验是 0，升级循环写成"需要 0 就停" | 先看界面怎么用这一列（分母取的是哪一行），再定"这一行的数是升到本级要的还是从本级升走要的" |
| 派出去干活的角色和场景里站着的不是同一批 | 早期为了"看起来有东西"留下的占位逻辑：登录时塞一份假名单、没派的也硬算一个位置。后来做了真的存档，占位的没拆 | 真功能做好后回头搜一遍同一功能的占位代码，改成"没有真存档时才生效"或直接删 |
| 注入探针后游戏画面定住、进程还在 | 注入的脚本是在另一条线程上进游戏的 Lua 环境的；主线程正好也在跑脚本（动画、弹窗收起、教程）时两边撞上，主线程崩掉 | 只在画面静止时注入；刚点完会播动画的按钮后不要马上注入，要看状态先等两三秒或用截图；崩了就重启，存档不受影响 |

## 模拟过天（把几天的日常压到几分钟）

卡进度的常常不是实力而是天数（店铺等级、主角等级、每日次数）。逐单点屏幕太慢，做法是：

1. 过天用工程自己的时间偏移（本项目 `v3_dev.py timeskip 86400`），不要改系统时间。
2. 重复性的日常用脚本直接调"服务器应答"那一层的函数，和真点走同一条结算逻辑；玩家本该花时间生产的货按需补足。每种日常先真点一两次确认界面流程是通的，再用脚本批量。
3. 每个天数门槛（升级、解锁）仍然真点，顺便验界面。
4. 脚本里的全局变量会留在游戏的 Lua 环境里，下次运行前显式清掉。

本项目交满当天订单的脚本（`v3_dev.py luamainfile`，在主界面、没有教程在播时运行）：

```lua
SIM_ORDER_LIMIT = nil
local n, max = 0, V3_OrderDailyMax()
for k = 1, 40 do
  V3_OrderRollDay()
  if V3_GetNum('OFFLINE_V3_ORDER_DONE_V1', 0) >= max then break end
  local list = V3_OrdersFill(V3_OrdersLoad())
  local o = list[1]
  if not o then break end
  for _, x in ipairs(o.want) do
    local have = V3_ItemCountOf(x[1])
    if have < x[2] then _G.OfflineEF_ApplyItem(x[1], x[2] - have, V3_ItemType(x[1])) end
  end
  local ok, err = pcall(V3_OrderReceive, { iSeq = o.seq })
  if not ok then LuaDebug.info('[OFFLINE-MEMORIAL] SIM order err ' .. tostring(err)) break end
  n = n + 1
  if SIM_ORDER_LIMIT and n >= SIM_ORDER_LIMIT then break end
end
LuaDebug.info('[OFFLINE-MEMORIAL] SIM orders delivered=' .. n .. ' today=' .. V3_GetNum('OFFLINE_V3_ORDER_DONE_V1', 0) .. '/' .. max .. ' shopexp=' .. V3_ShopExp())
```

共用真机时：每次点击前看一眼前台是不是自己的游戏（`dumpsys activity activities | grep topResumedActivity`）。用户可能中途拿起手机用别的应用，盲点会点到他的应用里。

共用真机上做会改存档的测试（塞道具、调好感）：先 `save` 一份带日期的备份，测完 `restore` 回去再 `restart`，最后再 `save` 一份和备份逐键比对（只应有会话计数、时间戳不同）。

往游戏里注入脚本：刚重启完、或者刚注入过一次，不要马上再注入（2026-10-13：重启后 12 秒内连注两个文件，注入线程 SIGSEGV，游戏直接退到桌面）。等主界面静止十几秒，一次只注一个文件，把要做的事合进同一个文件。

用户自己也在这台设备上玩的时候，不要再用「备份他的存档 → 换上测试档 → 写回」：换档期间他拿起手机看到的是别人的进度，会话的权限层也可能直接拦掉这种操作。改成并排安装一个改了包名的测试分身（等长替换二进制清单里的包名和组件名，重新签名），测试全在分身里做；工具默认指向分身，对正式包只允许覆盖安装和只看不改的检查。

改包名要把资源表 `resources.arsc` 里的包名一起改。只改清单的包能装上，但一启动就崩：`Resources$NotFoundException: String resource ID #0x0`，栈顶在 `UnityPlayer.<init>`——Unity 用 `getIdentifier(名字, "string", getPackageName())` 查资源，资源表里登记的还是旧包名就查不到（2026-10-13 真机）。打完分身先在包里数一遍旧包名（UTF-8 和 UTF-16 两种写法，清单、资源表、dex、so 都查），装上后先确认能进主界面，再安排长时间的测试。

新包名第一次通过数据线安装时，系统可能弹一个限时的确认窗（小米：发起后近一分钟才弹，10 秒不点自动拒绝）。先请设备主人点；他明确说让你代点时，只在前台确实是那个窗口时点一次，不要盲目反复发起安装。之后覆盖安装不再弹。往设备公共目录里放过的旧安装包，换了新包后要删掉，免得主人顺手点了旧的把分身装坏。

## 先用脚本验，手点只留给脚本看不见的东西

手点一章要几十分钟和大量截图。后面的章节先按这个顺序用脚本过一遍，再决定哪里值得手点：

1. **不连设备的静态检查。** 读剧情表和资源清单：对白链每一句的"下一句"存不存在、引用的背景 / 立绘 / 特效包在不在包里、有没有前面章节没出现过的小游戏类型。结果是一张"哪一节要重点看"的清单。
2. **注入式推进。** 往游戏里注入一段脚本，用**真实的结算函数**把主线任务链一口气推过去，遇到等级 / 店铺门槛自己抬，顺带把每个门槛的要求打出来。几百条任务几分钟。
3. **游戏内自测。** 每个本地模块配一个注入自测：造请求 → 调本地应答 → 断言存档和回包。改完代码先跑它。
4. **手点。** 只点脚本看不见的：层级、遮挡、弹窗位置、小游戏画面、连点两次的行为；以及静态检查标出来的节。

每一层证明的东西不一样，写结论时别混：
- 注入推进只证明任务链和结算逻辑通，画面一眼没看。
- 自测不走客户端的发送函数，"先发后置标记"、面板生命周期这类毛病抓不到。
- 用开发手段把门槛抬过去的走查，只证明流程通，**不证明正常养成够得着**——数值要另外从表里算（材料产量 × 体力 × 天数），或者正常玩一遍。
- 模拟器上过了，不等于发布设备上过了。

子代理按规格执行时会把规格里的字面意思做到底（例："这个卡池的过期字样要处理"被做成了把整个卡池藏掉）。审它的改动时对着用户的意图看，不是对着规格看。

## 收尾

- 结论写进数值文档和用户反馈表：每个门槛的分项、改了什么、依据是原版数据还是自己的标定。
- 没修的现象单独列出来，写清楚复现路径，不要混在"已修"里。
- 需要用户拍板的事（例如教程补给的语义、发放量）列成选项并给出建议，不要自己悄悄定。

## 每修一个玩家报的 bug，就留一个注入回归自测（2026-10-17）

- 写法：一个 Lua 文件，直接调界面按钮的处理函数（不点屏幕），用游戏自己的计时器按步排好，每步后断言界面状态（当前页签、高亮挂在哪个按钮下、某面板是否还活着），每项打 `PASS` / `FAIL`，最后打 `DONE pass= fail=`。案例 A 的例子：`tools\dev_selftest_nav.lua`（底部导航 + 角色页进出，17 项，约 20 秒）。
- 处理函数要用玩家实际会走的那个（比如关角色页用返回按钮的 `OnBackBtnClick`，而不是直接关面板），否则绕过了补丁挂的钩子，测不出问题。
- 每出一个新包，上机先把这些自测跑一遍再交给人玩。

## 后期章节先做「等级 × 金币」两条曲线的静态推算，再决定要不要上机（2026-10-17）

- 原版很多奖励在服务器（订单池、订单奖励表在客户端里是空的），离线版自定的规则往往只照前几章校准过。打开后面章节之前，先用配置表算：主线要求的等级 / 店铺等级各要多少经验、多少金币；离线版每天各来源最多给多少；按日模拟到每章末是第几天。
- 案例 A 的结果：第 6-15 章照原版要约 293 天，卡点全是等级；店铺升到 114 级要约 2.48 亿金币，现有规则要 297-364 天，金币和等级几乎同时卡。只加速其中一条，另一条马上变成瓶颈，所以节奏要两条一起调。
- 做法：一个只读子代理导配置表、读发奖代码、写按日模拟脚本；主会话核对公式（子代理把 `floor(x*2/10)*10` 读成了 0.2 倍，实际是 2 倍），再把结论交用户拍板。

## Acceptance run order (2026-10-18)

- Back up the save first, and pass the backup to restore as a full path.
- Run selftests that max out resources (start mode / max-out) last, or restore the save after them. Tests that assume "not enough tickets / items" fail falsely after a max-out.
- If the in-game file channel doesn't respond, the injector may fall back to a debugger attach. That can freeze the game's main thread (process alive, log silent). Prefer the main-thread file runner. Very long selftest files may exceed its size limit and print nothing; record those as "not run", not "passed".
- A final (release) build has no injection hook. To test real licensing there, sign a real code, write it into the save XML (URL-encoded, as PlayerPrefs stores strings), restore the save, cold start, and read the gate/cap log lines.
- If the emulator's adb shows "offline" and reconnecting fails, kill only that instance's player process and relaunch it; leave other instances alone.
