# 本地回包与离线玩法的坑

进离线流程的时机、伪造回包、配置表读取、玩法规则、"等不到的服务器推送"、AI 聊天替代服务器。

现象 → 原因 → 修法。原来都在一份 `pitfalls.md` 里，2026-11-19 按阶段拆开，条目原文没改，按原来的先后排。原来的分节标题留在条目最多的那份文件里，别的文件用三级标题注明出处。索引见 `../pitfalls.md`。

## 启动阶段

**进离线入口后中途报错，落回登录界面**
- 原因：进得太早，配置表还在解析
- 修法：等数据表就绪再进，把入口挂到解析完成之后
- 实例：案例 A `ParseDataTable` 未结束时进 `OfflineEnter`，拿到空表

**黑屏且画面完全不动，但调试通道照常响应（JS 引擎）**
- 判据：`Laya.timer.currFrame`（或引擎的帧计数）不再增长；日志里只有一两条 `JS onFrame error`。
- 原因：引擎主循环是 `rAF(loop)` 里先渲染再续帧，渲染抛一次异常就不再续帧。离线后资源偶发加载失败、回调拿到空数据仍去建对象，是常见触发源。
- 修法：给每帧入口（如 `stage._loop`）包 try/catch，再给触发源对象加空数据保护。只修触发源不够，下一个空资源还会冻住。
- 实例：案例 B 的剧情 1-1 的粒子 `.part` 加载失败，`new Particle2D(undefined)`，见 `case-b-laya-native.md`。

**改了一处伪造回包后，资源开始随机加载失败（重试在同一毫秒内全部失败）**
- 原因：引擎复用网络请求对象（连接池/加载器池）。伪造回包时把 `status`、`readyState` 钉死在实例上（例如 `defineProperty` 写成只读），后面复用这个实例的请求一发出就"已完成、失败"。
- 修法：伪造字段只在当次有效，下次 `open()` 前删掉。上线前用"同一对象连发两次请求"自测。
- 实例：案例 B 的 v0.3d，为 `""` 皮肤伪造的 404 毒化了 Laya Loader 的 XHR，剧情 1-1 打不开。

**功能点下去没反应，日志有 `NullReferenceException`**
- 原因：离线时网络层抛异常，打断了调用方
- 修法：所有离线调用点用 `pcall` 包住

## 本地回包 / 伪造服务器数据

**界面显示 `1970年01月01日`（或类似的纪元默认值）**
- 原因：为了让卡片/条目走「已解锁 / 已读」分支，把服务器下发的**时间戳字段**用非零哨兵常量顶上去
  （典型写法 `iFirstReadTime = 1`）。下游拿到这个字段直接当 Unix 秒去 `os.date('%Y', t)`，
  1 秒就是 1970-01-01。分支判断（`~= 0`）过了，显示就露馅。
- 修法：**伪造服务器字段时按它的真实语义取值，不要只满足分支条件。** 时间戳就给真实时间（
  `os.time()`），并按条目/章节持久化（例如 PlayerPrefs key 带条目 ID），首次写入后续复用，
  这样日期稳定、重启不变、也不会回落到「未读」分支。
- 实例：案例 A `<角色约会卡片项>:SetCardItem` 的 `chapterInfo.iFirstReadTime`，
  三处本地回包都写过常量 `1`，全部要换成 `OfflineEF_RoleReadTime(chapterID)`。

**某个入口按钮/菜单永久不出现，点上去像「空按钮」**
- 原因：原版代码用**某个状态值**来 gate 入口，而离线回包把这个状态硬编码成了「临时态」。
  典型：热卖/活动/限时状态本来只在活动期 > 0，离线种子为了「让数据看起来有」写死一个非零值，
  于是 `ShowXxx(not IsHotSaleTime())` 这类判断永远走隐藏分支，入口再也没有打开过。
- 排查：在反编译代码里搜这个状态的 getter（如 `IsHotSaleTime` → `sellInfo.iLeftFastSellTime > 0`），
  再搜谁读它、读到之后是显示还是隐藏。
- 修法：**离线种子要把状态落在「正常态」**（能让玩家自己触发的初始状态），不要落在「临时态」。
  「有数据」和「处在限时状态」是两件事。
- 实例：案例 A 的店铺 `iLeftFastSellTime = 1000` 让「热卖中」永不过期，
  `StoreBuildPanel` 的 热卖/上架/升级 三按钮被永久隐藏 → 商业街上架面板没有入口。

**别跨模块调用「注入进去的全局函数」——它们可能是惰性定义的**
- 症状：自己在补丁模块 A 里调用模块 B 提供的全局函数（如 `OfflineWareHouseApplyItem`），
  调用处明明在 `pcall` 里"没报错"，但**功能静默失效**（东西没发出去、状态没变）。
- 原因：补丁常把模块文件的内容**整段替换进某个函数体**（例如把抽卡模块塞进
  `XxxManager:SendLuckDrawReq`）。于是模块里那些看似全局的 `function Foo()` 定义，
  **只有在该函数第一次被调用时才会执行**——在那之前 `_G.Foo` 就是 `nil`。
- 排查：在调用点先打印 `tostring(_G.那个函数)`。是 `nil` 就中招了。
- 修法：**只用同一模块内已有的工具函数**，或把需要的工具定义在一定会先加载的地方。
  本项目里 `offline_all_features.lua` 自带 `OfflineEF_ApplyItem`（且内置 fallback），
  种植模块改用它之后就正常了。
- 附带教训：**发放/扣减这类关键动作不要只包在 `pcall` 里静默失败**，
  至少在失败时打一条日志，否则"没报错但没效果"会查很久。

**同一个种子函数喂多个消费方，筛选口径被"一刀切"**

**复活活动时，每个活动的购买 / 领取请求都要逐个确认有 handler（案例 B）**
- 症状：往事重现活动里买不了情笺。
- 原因：那几个活动的通用购买请求（`reqActivityCommonBuy`）没有专门的 handler，落到通用逻辑返回「活动没配置」。
- 修法：在通用购买 / 领取入口加兜底，按配置处理这类活动。复活一个活动 hub 时，把它每个子入口的购买、领取、兑换请求名列出来逐个确认离线有接（可配合 `case-c` 的「扫所有 RPCWaitSend 和已注册路由求差」）。
- 症状：某个列表/商店/背包里出现**明显不该出现的内容**（礼包、月卡、货币被摆上货架）。
  链路能跑通，所以容易被归为"小问题"而长期挂着。
- 原因：离线补丁常写一个"造数据"函数同时喂两个入口，筛选条件取了两边的**并集**（或干脆按宽口径）。
  但两边合理内容其实不同：NPC 商店卖消耗品，玩家货架只该摆"商品"。
- 排查：**去配置表找权威对应关系**，别凭字段类型猜。
  例：本项目 `reptGoodsNpc` 列的是"顾客会买的 70 件商品"，一查全是 `iItemType == 5` —— 这就定义了"商品"。
- 修法：给种子函数加**口径开关**（如 `onlyGoods`），**只改有问题的那一侧**，
  已验证过的另一侧保持原样，避免把修 bug 变成回归。
- 附带教训：**改了函数签名或调用行，要顺手搜一遍断言/测试里有没有写死旧签名的**，
  否则补丁会以"断言失败"的形式报出来（这次连中两条）。

**同一行数据被多个消费方用不同字段名读取，某处算术/取值崩在 nil**
- 原因：反编译产物里同一个数据结构在不同 UI 里读法不一致（旧命名 `iItemID`/`iCount`
  vs 新命名 `iItemId`/`iItemCount`）。伪造数据行只满足了一边，另一边拿到 nil，
  报错形如 `attempt to perform arithmetic on field 'iItemCount' (a nil value)`。
- 排查：拿到报错的文件行号，去那一行看它读的字段名；再全量搜**同一份数据**的其它消费方，
  列出所有用到的字段别名。
- 修法：**伪造行把所有别名都写上**（`row.iItemID` + `row.iItemId`、`row.iCount` + `row.iItemCount`）。
  多余字段对 Lua table 无副作用，漏一个就有一处 UI 挂掉。
- 实例：案例 A `OfflineEF_ShopGoods` 只给 `iItemID`/`iCount`（NPC 商店读法），
  `RetailPanel`/`StoreGoodsItem` 读 `iItemId`/`iItemCount`，一开店面板就报错。

**点击完全没反应，但日志里连请求都没有（静默 gate）**
- 原因：交互函数里有一个**不报错的边界判断**直接 return，常见是容量/上限/数量判断，
  如 `if (not (itemTotalCount >= self.totalCapacity)) then ... end`。
  离线种子把数量堆到超过上限（`50 x 999 = 49950` vs `iMaxStorage = 1580`），
  于是后续所有点击都被这个分支吞掉。
- 排查：搜该交互函数名，逐条看它开头的提前 return；同时**去看 UI 上自己的数字**
  （容量条、计数、进度）——超限往往就写在界面上，只是不显眼。
- 修法：种子数量必须**尊重界面自己展示的上限**（读配置表的上限字段，别用拍脑袋的大数）；
  需要「给足」时就贴着上限给，不要突破。
- 实例：案例 A 的货架容量条显示 `49950/1580`，`OnClickWarehouseItem` 因此静默挡死上架。

**自造的数值字段（战力/属性/评分）只满足分支条件，丢掉了成长维度**
- 原因：原版这类字段由**服务器算好下发**（如卡牌 `stPropInfo`）。离线补丁只能自己造，
  常见做法是拿配置表里的基础值乘一个显眼因子（典型 `基础值 × 星级`），
  而客户端里其实**已经有一份权威算法**（如 `CommonFuncion:GetCardAttribute`）。
  自己手搓的版本漏掉等级、突破、加成等任一维，数值表面上「看起来正常」，成长链却是断的。
- 症状：玩家升级/突破/强化**照扣材料、数字照涨，战力一点不动**；或反过来，数值虚高到门槛毫无意义。
- 排查：先在反编译代码里搜这个字段的读取方，再搜客户端**自己**算它的函数（往往用在对比/预览 UI 上），
  两者对照就能看出漏了哪几项。
- 修法：**照搬客户端权威公式**，把输入的每个维度都接上；然后拿配置表离线算出理论上限，
  和关卡门槛比一次（上限 ≪ 门槛 → 公式漏项；上限 ≫ 门槛 → 门槛形同虚设）。
- 实例：案例 A 的剧情战斗要求 1650 / 5250，离线公式只有「卡面×星级」，
  满星上限 1550 / 1500 → 怎么练都过不去；补回等级项与突破加成后上限 52005。
  客户端公式：`floor(0.01 × 卡面 × param) + 突破加成`，`param = (iAbilParam + lvl×250/(lvl+250)) × (1 + star/4)`。
- 附带教训：**别急着下「门槛太高、玩家会被卡死」的结论**。先确认成长链是通的，
  否则会把「公式漏项」误判成「设计不合理」，进而去做错误的下调门槛。

**"服务器推过来"的玩法（随机事件、报恩、通知类）：先找谁打开那个面板**
- 做法：从请求名 / 通知名搜到 manager 的回调，再到 model 存到哪张表，再搜谁读这张表、谁 `ShowPanel`。只看面板代码会走偏：客户端里留着从来没人打开的旧面板（案例 A 的 `<宠物互动面板>` 有一整套"摸宠物找惊喜"逻辑，全工程没有一处打开它；真正在用的是后院气泡 → `<宠物事件面板>`）。
- 触发规则在服务器上查不到时：定一条离线规则，写进代码注释和用户文档，标明"离线版定的"；规则里的数（概率、次数）单独列成常量。
- 定规则时先拿配置做统计找线索（案例 A 2026-10-18 的店头纸条）：客户端只有请求号和回包字段，看不出触发条件。统计商品表里各商品指向的纸条池，70 个里有 59 个指向普通池，于是定成「每个游戏日第一次卖货结算时，出一张还没得过的普通纸条」；纸条挂在店上直到被读，关闭详情时才记入存档。
- 面板关掉时只发界面内通知、靠另一个界面元素接着发请求的（这里是后院里那只宠物），元素不在场就没人接：在 model 的通知函数后面加一个兜底调用，处理函数自己保证只发一次奖励。

**"获得 XX"的通知弹窗数错（套装已收集 0/3）**
- 原因：弹窗读的是 model 里某一类的已有列表，这张表要先收到"整页数据"的回包才有；这次登录没进过那个页面时是空的。
- 修法：发通知前先按"得到之前"的样子把整页数据灌一次（注意别顺手把页面打开：先把 manager 上"收到数据就开面板"的开关关掉再灌），再记账、再发通知。顺便核对整页数据里有没有漏掉的类别（这里漏了宠物收藏 104，收藏界面里永远看不到）。

**把"结算用的数"显示到界面上，会照出结算函数的老毛病**
- 症状：让情报页的"总实力"改用结算同一个函数后，17 级的档显示 20144（应为 10342）。
- 原因：结算函数靠遍历顺序去重（"先遇到链头就把后面的步骤标成已算"），步骤表的顺序不固定，后面的步骤排在前面时整条链被算了两遍。以前结算数字只进日志，没人看见。
- 修法：先扫一遍找出"排在别的步骤后面"的步骤，只从链头算。教训：界面和结算各算各的时候，先让界面显示结算的数，再看数字合不合理。

**规则有好几种条件，本地只判了一种，其余等于全放行**
- 症状：某类关卡 / 功能新档一进去就全开；高阶材料随便刷，后面章节的门槛形同虚设。玩到高等级的测试档看不出来，因为它本来就满足条件。
- 原因：原版解锁表里有「先通过某一关 / 主角等级 / 好感等级」几种条件，本地实现只写了其中一种，遇到不认识的条件类型就返回"已解锁"。
- 修法：写解锁判断前先把表里实际出现的条件类型数一遍（按类型分组计数），每种都实现；不认识的类型默认**锁住并打日志**，不要默认放行。验证必须用全新档。
- 同类：上限公式要先看存的是什么。突破等级存的是 0 / 10 / 20，按"突破了几次"去乘就算出一个离谱的上限。

**奖励串里的"类型"没分发，全当成道具塞进仓库**
- 症状：奖励写着"店铺知名度 100"，领了不涨；好感、藏品类奖励领了不见。
- 原因：奖励格式是 `类型;编号;数量`，类型不同去处不同（道具 / 货币 / 店铺知名度 / 好感 / 藏品…）。本地入账函数只认道具。
- 修法：入账函数按类型分发；先在全部配置表里统计奖励串出现过哪些类型，逐个确定去处，没处理的类型打日志而不是静默入仓。

**原版"先发请求、紧接着改标记"，离线同步回包后标记卡死**
- 症状：某个按钮第一次点正常，第二次点没反应或状态不对；注入式自测全过。
- 原因（我的推断，和"同一帧销毁再重建"是同一类）：联网时回包晚几帧到，处理函数运行时标记已经置好；离线回包在发送函数内部就同步处理完了，随后才执行"置标记"那一行，标记留在"等待中"。自测直接调处理函数，不走客户端的发送函数，所以抓不到。
- 修法：静态扫一遍"调完 Send 立刻赋值"的写法，逐处判断；新接的功能在界面上把同一种操作至少连点两次。

**离线同步回包撞上客户端的三类时序假设（计数门闩 / 界面未就绪 / 预扣）（案例 A 多次）**
- 原版回包走网络、晚几帧才到，客户端为此埋了三类假设，离线同步回包会一一踩中：
  1. **「等 N 个回包」的计数门闩**：面板 onInit 发两个请求、各回包 `count--`，减到 0 才开面板（案例 A 商店 `transactionPanelReqCount`、`ShoppingManager`）。同步回包时第二个请求还没发，第一个已经把 count 处理完；更坏的是「发完再 count++」的写法会先减成 -1 再加回 0，永远不等于 0。修法：所有请求发完之后补一次判断，count 为 0 且面板没开就在这里开。凡是「等多条回包」的入口都按这个查。
  2. **界面状态没就绪，回包被忽略或被随后覆盖**：上架、速度查询、热卖结算点了界面不刷新。修法：用游戏调度器把回包延迟 0.15~0.6 秒（封成 `V3_Later(sec, fn)`：`LuaScheduler.delay` 挂当前 UI 的 gameObject）；战斗结算等战斗面板关闭后再回。
  3. **客户端已本地预扣，服务器又扣一次**：工坊做 1 个扣了 20（应为 10）。修法：处理请求先查面板的「已发送」标志（如 `mIsSendMakeFormationBtn`），预扣过就先把预扣的加回、再由服务器统一扣一次；失败路径把加回的再扣回。
  4. **界面搭建时就读的数据，恢复晚了就对不上**（2026-10-13~18）：有三种表现。后院按屏列表的顺序算位置和滚动范围，离线模块却在面板搭好后才恢复已解锁的屏，重启后点页签画面不动。某角色页的离线回包早于面板设好角色数据，一打开就报 nil，列表几乎是空的。原版靠服务器主动推送灌进 Model 的数据（如已得纸条），离线后没人发，面板每次打开都是空的。修法：恢复存档里的解锁态，放在面板搭建之前做（进入该界面那条请求的应答里），不要事后补刷；要用到面板数据的回包，延后到面板初始化之后再处理；没人发的推送，在 Model / 面板初始化处挂钩，用原版的解析函数（如 `Parse...Rsp`）把存档内容灌进去。
- 通用：接任何「发请求 → 等回包」的功能前，先读客户端这三处：有没有计数门闩、有没有在回包前切界面状态、有没有本地预扣。

**离线客户端的「服务器时间」恒为 0，限时活动永远不开（案例 A）**
- 症状：限时活动判断开没开拿到的当前时间是 0，活动永远不开；主线进度模型值也可能恒 0，男主个人剧情全判成「主线没走到」。
- 原因：离线版从不向服务器校时，`GetCurrentServerTime()` 一直返回 0；同理 `MainStoryModel` 的当前章 / 当前节也没人写。
- 修法：登录后主动校一次时（本游戏 `GufengxGameSystem.Instance:SyncServerTime(os.time())`），再下发本地构造的活动通知列表（`GET_ACTIVE_NOTICES`）。进度字段用「原值与按任务链推算值取较大者」补（包装 `GetCurSectionID` / `GetCurChapterID`）。校时后要回归所有读服务器时间的界面（对话、交易、换装、茶楼……）。
- 怎么确认的：注入探针读到时间 / 进度为 0，调用校时 / 包装后连读正常。

**自造的完成判定 / 已读 / 已领状态，要对照客户端的计数函数和提示文案，别按字面当单条处理（案例 B/C）**
- 几种一类的坑：
  - 红点 / 图鉴完成条件只查主件：只拥有套装里一件衣服，图鉴奖励就亮红点可领。服务器 `suitCheck` 只查 `mainPart`，但客户端 `getSuitOwnCount` 要求 `partItems` 全拥有（builtin 件跳过）。改成和客户端计数一致；登录时清掉未集齐套装的旧红点，已领不收回。原版规则查不到就按客户端提示文案（如提示 4019「收集完成可领取」）推断并标 `[推断]`。
  - 客户端进某页只发「第一条编号」表示整页已读（案例 C 手札总录 / 大事记、uiboyletters）：离线服务器只标那一条 → 每次进游戏又显示未读。改成按页（类型）整页标记已读。
  - 回包里「已领档位」列表被填成一串 0：界面认不出，日常宝箱领完还显示可领、能反复点。按真实档位写并持久化。
- 通用：伪造「状态类」字段前，去客户端 Model / 面板读它到底怎么用这个值（计数函数、提示语、「记录必须先存在才 +1」的前置行），不要按字面只处理一条。

**按分类过滤发放时漏掉另一类物品（案例 B）**
- 商城整妆脸（`avatarUse==SHOP`、部位 16）不进衣柜分类，被「全部衣服」发放逻辑跳过 → 保存脸被客户端校验拦住。修法：发放时把这类也放行（排除原版就屏蔽的，如名字带「(屏蔽)」的），存档版本号 +1 让老存档登录补发；保存失败加日志写明原因。和 builtin 套装被跳过是同一类：按某个分类字段过滤时，先列全该字段的取值，确认没把另一类该发的漏掉。

**新手指引在另一条指引进行中被触发，两条串在一起卡死**
- 症状：遮罩和手指一直盖着，只能重启。出现在一次连开好几个新功能的节点。
- 原因：原版"开始指引"不检查当前有没有指引在跑，直接换编号；步骤内容还是旧的，对不上。联网时这些触发被服务器节奏隔开，离线时同一刻满足。
- 修法：有指引没走完时，新指引一律推迟，结束后再触发。

**自造一张新主卡，退回列表时后台报 Lua 错（案例 A 2026-10-15）**
- 症状：从新卡详情页退回卡牌列表时，界面看着正常，日志里列表项脚本报空值错误。
- 原因：原版每张主卡都配一对日 / 月副卡，列表项会去读它们。新卡没有副卡，读出来是空。
- 修法：照模板卡把副卡补齐：配置行、缩略图（可以从卡面裁两块）、存档里的卡片条目。补完再进列表，日志没有报错，副卡页签也能看到新缩略图。
- 通用做法：新增任何自制条目之前，先找一条原版同类条目，把所有引用它编号的表和存档键列全，再逐项克隆。

**登录下发的属性按编号顺序应用，前面的属性依赖后面的就拿到 nil（案例 C 2026-10-24）**
- 症状：随机点击时客户端报 `string.format` 拿到 nil，出错位置在设置数据的初始化里。
- 原因：客户端按属性编号逐个应用登录属性。编号小的属性（37）在设置函数里要读编号大的属性（116），而后者那时还没赋值。
- 修法：这类属性登录时先不发，等第一个 tick 再单独推（本例做成一张 `LATE_PROPS` 名单）。
- 怎么确认的：monkey 随机点击抓到这条报错；加上名单后，登录日志里不再出现。

**扫荡只发普通奖励，漏掉“完美”额外奖励（案例 C 2026-11-05）**
- 症状：玩家反馈有完美额外奖励的关，扫荡和一键过关从来不掉，只有结算页“再来一次”能掉。
- 原因：本地服务器的扫荡处理只发普通奖励，只有单次结算会掷额外奖励。
- 修法：扫荡的每一次循环都按单次结算的同一规则掷额外奖励。本例表里是 15% 概率加 4~5 次保底，回复玩家时要说清“不是每次必掉”。凡是批量路径（扫荡、一键、连续），都要和单次结算对一遍发的奖励种类。
- 怎么确认的：场景测试里，完美关扫荡 205 次掉了 65 次，非完美关 0 次。界面没上机看。

**有每日次数上限的关：服务器不限次、进度字段没人写，次数变负、按钮变灰（案例 C 2026-11-05）**
- 症状：困难关刷过之后次数显示异常，扫荡按钮点不了；日志里同一关一天打了 6 次（上限 5）。
- 原因：困难关的进度字段从来没人写，关号还混进了主线进度。客户端重进或跨天后拿不到当天次数，就按本地剩余次数判断；服务器也不拦，超限后剩余变成负数。
- 修法：两条进度分开记；登录时按通关记录重算进度，顺手修好老存档；发给客户端的次数夹在上限以内；开始关卡时次数已满就回“次数不足”错误。
- 附带：日志里同时有时钟跳变，一度被怀疑是时间问题，其实无关。

**发放规则里的“排除”和下游检查对不上：整批衣服被跳过，依赖它的功能全部失效（案例 C 2026-11-05）**
- 症状：领了“全部衣服”之后，双人拍照动作解锁不了，另一位角色也换不上情侣套装。
- 原因：一整类套装（19 套）的部件被标成“内置”，发放逻辑把它们当成不用发的跳过了。可拍照动作的条件和那个衣柜检查的都是“所有部件真的在背包里”。
- 修法：先看下游真正检查什么，再定发放的排除规则（内置 / 付费 / 屏蔽）。这类套装照发，但从“收集数”统计里排除，免得任务计数出错。已经领过的老存档用一个版本号字段在登录时静默补发，不再寄信。
- 怎么确认的：脚本检查 19 套全拥有、41 个套装条件全满足。还没上机。

**功能“只能预览”或点购买没反应：解锁条件里的东西离线版没有来源（案例 C 2026-11-05）**
- 症状一：设置里换主场景只能预览，切不过去。原因：解锁要特定物品，而它只在已关闭的道具商城里卖，离线版没有任何获取途径。修法：登录时给每个玩家补一件，只给一次；VIP 条件直接放行。
- 症状二：通关后自定义套装位不解锁，点购买既不扣钱也没反应，日志里有 `unhandled ...reqBuyCard`。原因：服务器只发存过的槽位，不按通关 / VIP 规则算；购买请求根本没写。修法：按数据表规则算每个位开没开，刚通关就推一次；补上购买处理（扣钻石、回错误码）。
- 通用：功能点了没反应，先搜日志里的 `unhandled`，再把它的解锁条件追到底。商城、付费、VIP 都算“离线版没有来源”。

**自造小游戏规则前，先读原版客户端的判定代码，服务端和客户端用同一个公式（案例 A 2026-10-13）**
- 症状：钓鱼角力玩法的第一版，力量条一出来就是满的，没有「加油」按钮；第二版客户端的条满了，服务端却判鱼跑了。
- 原因：没读原版就自己设想规则。原版的条比的是（主角实力 + 队伍）对鱼的力气，只有条不满时才出现加油按钮和倒计时；服务端另写的判定公式和客户端的条不一致。
- 修法：读原版的判定类（这里是 `FishingForceContestBase`）。鱼的力气按流域要求的实力定，服务端用和客户端条完全相同的公式判输赢。验证时把鱼力临时调大，确认加油按钮、倒计时、连点能钓上、不点鱼会跑这几条分支都出现。
- 相关：案例 B「服务端要复刻客户端的判定时，从 bundle 里把那几个函数原样抠出来对拍」是同一个思路。

**复活收集类玩法：先看发送函数是不是空桩、客户端按什么键匹配、编号会不会和别的系统撞（案例 A 2026-10-18）**
- 症状：两条领奖请求写了本地应答，也永远触发不了；某个收藏的第 1 档一开始就显示已领取；另一张收藏表的行在界面上始终对不上；CG 页里没通关章节的 CG 也显示已拥有。
- 原因：① 终版客户端里那两个 `Send...` 函数是空函数（APK 里的原始副本也是空的），根本没人发消息；② 伪造回包里的「已领档位」列表是写死的，里面含第 1 档；行用了客户端从不匹配的 id，客户端实际按类型（1–5）每级取一行；③ CG 编号和另一种收藏的编号段重叠，旧逻辑按编号查收藏是否拥有，于是别的收藏让 CG 被误判成已得。
- 修法：写应答前先看对应的发送函数有没有内容，是空的就在补丁里补成真发消息。填回包前先读客户端的匹配代码（Model 和面板里怎么取、用什么键比）。已领列表从存档算。配置里的档位阈值在游戏里够不到时（本例 100000+，实际最多 150 点），按能达到的最大点数另定档位，并写进文档。不同系统的拥有状态各用独立的存档键，别借别的收藏表来判断。
- 怎么确认的：读两个发送函数，确认是空函数体；对比两张表的编号范围；补完后自测 41/41 通过。

**本地抽卡：预览列表不是爆率表，已拥有的卡要按碎片演出，常驻池别挡住限时池（案例 A 2026-10-19~20）**
- 症状：玩家反馈抽到的几乎全是高品质宠物，普通的抽不到，卡池详情每项都显示 33.33%。全卡已三星后，十连仍然每张都播新卡动画。为了去掉一个反复弹出的提示让新手池常驻，结果活动期的限时池不见了。
- 原因：离线版把卡池界面展示的 3 个预览奖励当成候选等概率抽，其中一个就是高品质，所以约 1/3 的概率出；普通品质和别的品种根本不在候选里。真实概率在服务器上，配置表里没有。抽卡把卡本体当奖励发，客户端的 `iIsNew=0` 不起作用，结果面板按物品类型走了新卡演出。新手池在原版抽满后应该收起让位，改成常驻后就把限时池挡住了。
- 修法：先看表里有没有权重字段。没有的话，用界面上写的保底次数反推一个合理的概率：品阶和品种分开抽，保底要真的实现，界面上的倒数才准。数值放进一张常量表，标 [自造]，并告诉用户原版概率找不到。限定 / 付费的只给有对应授权的存档，并压低概率。展示列表里已拥有或本次已抽到的卡，换成碎片类物品（按卡表的换碎片数），发放列表照原样入库。改「池子何时出现」之前，先弄清原版的让位规则，再决定屏蔽哪个提示（本例改成抽满就收起，抽满那一次照常弹原版提示）。
- 怎么确认的：在电脑上（lupa）和模拟器上每池各模拟 3 万抽，各品质占比与目标一致，最长连续不出的次数不超过保底；从主界面点进去，卡池详情显示新概率；十连里已拥有的卡显示为碎片。

**本地应答条件不满足时把数据丢了却回成功；旧补丁伪造「已解锁」，玩家找不到解锁入口（案例 A 2026-10-28~11-01）**
- 症状：玩家在某个生产区派猫点保存，界面显示成功，但猫全没派上，也不产东西；上一轮还被误报成「修好了」。
- 原因：两处叠在一起。本地保存函数发现格子没解锁，就把整批猫丢掉，但仍回 ret 0；同时一段旧的布局种子把 6 块地全画成已开放，而存档里一块都没解锁，客户端模型停在「等待解锁第 1 块」，解锁光圈也就不出现。
- 修法：去掉伪造的「已开放」，改用真实数据：第一块显示未解锁牌子，解锁后才能派。本地应答发现前置条件不满足时，必须给出明确提示，不能静默丢弃再回成功。非 0 的 ret 会走错误码文案，查不到就显示「N错误码未配置」，所以先读客户端的 `Parse...Rsp`；稳妥的做法是飘字说明原因，再回一个 ret 0 的空结果。
- 怎么确认的：玩家日志里保存的猫数是 0、回包 ret 0；在和玩家同进度、该区未解锁的测试存档上复现，修后解锁、派猫、等产出都验过。发「已修好」之前，一定先用同进度的存档复现。

**自造的订单从仓库任意材料里抽货，要出产不了的东西，还永不过期（案例 A 2026-10-28）**
- 症状：订单要 150 个根本做不出来的材料，一直占着面板，后面的单越积越多。
- 原因：离线订单逻辑从仓库里某几类物品中随机抽，不看当前能不能产出；过期时间填的是 0；来单节奏也和游戏内的规则说明对不上。
- 修法：自造规则前，先去解密后的配置里找原版规则文本（这里是 `reptPanelRule`）和客户端用到的字段，再对齐。只从当前产得出的货里选（已解锁格子的产物，加上配方和原料都产得出的成品），数量按产出速度封顶。订单记下生成时间，过期字段填真实的过期时间，客户端倒计时到 0 会重新拉列表。读档时清掉过期单和现在产不出、又交不上的旧单，让已经卡住的玩家更新后能恢复。给客户端的时间戳用真实时间，不用开发快进后的游戏时间。
- 怎么确认的：用 lupa 在电脑上跑真的 Lua，26 项检查（节奏、离线补单、过期、旧档兼容、清理旧单、快进换算）全过；游戏内还没验。

**客户端要「打开某个面板」或「收到服务器推送」才加载的数据，离线后在主界面看不到（案例 A 2026-10-31~11-07）**
- 症状：有几种表现。签到后重启，红点又亮，点开签到面板才灭；剧情选项要求持有某藏品，重开游戏后全锁；突破材料里点跳转，提示「通关上一关后解锁」，进过一次那个玩法界面后又能跳；做完日常任务，主界面不亮红点，点进面板才亮。

- 怎么确认的：同一份「今天已签」的存档，旧包重启红点亮、新包不亮；不预载时跳转结果和提示与玩家录屏一致，预载后能跳。

**改「几点换日」时，把按钟点判断的逻辑也一起偏移了（案例 A 2026-11-05）**
- 症状：饭点（12–14 点、18–20 点）领体力的界面不出现「可领取」，要晚 5 小时才能领。

- 怎么确认的：开发包把时钟拨到 12:46，显示可领取，点了体力增加；新自测 21/21。

**升级弹窗显示「Lv.0 → Lv.1」：服务端回的是升了几级，客户端要的是升到第几级（案例 B 2026-11-02）**
- 症状：好感从 9 级升到 10 级，弹窗显示 Lv.0 → Lv.1。
- 原因：本地服务端的好感升级字段回的是增量，客户端把它当成当前等级来显示（源码注释里写着是当前等级）。
- 修法：升了级就回新等级，没升回 0。所有会升级的路径（送礼、抽卡、约会等 7 处）一起改，测试断言跟着改。填等级、数量这类字段前，先看客户端拿它做什么。
- 怎么确认的：改后送礼升级，弹窗显示的前后等级正确。

**默认回空包的副作用：时钟被清零、玩法全被锁、数值刷成 0、奖励被悄悄丢（案例 G 2026-11-10~13）**
- 症状：①倒计时显示几十万小时；②打完新手章后，所有“按章节开放”的玩法仍提示未开放；③每分钟一次的“查询当前修为”把界面数值刷回 0（存档里没丢）；④剧情选项里的好感奖励一直没到账。
- 原因：没实现的请求统一回空对象，客户端读到 undefined / 0 就照用。①校时请求（连心跳也是校时）回了 `timestamp = 0`，服务器时间被清零；②判断玩法是否开放读的是一个“已通关最高进度”字段，原版由单独的协议下发、平时值就是 0，不回就是 undefined，所有比较都失败；③轮询类查询的默认值不是“当前值”；④发奖函数遇到不认识的奖励类型直接跳过，没有任何日志。
- 修法：默认回包处挂一个钩子，把落到默认回包的请求名记成清单，这就是待办表，每玩一段看一次。校时的所有入口（登录、心跳、专门的校时协议）一起补。缺字段给原版常态值，别留 undefined；轮询类请求回存档里的当前值；发奖函数遇到未知类型要记日志并计数。
- 怎么确认的：读客户端判断玩法开放的代码；真机上玩法开放后重启，数值不回 0。

**领奖“报莫名其妙的错、东西领不进去、还能重复领”：三个触发源和一套统一的补法（案例 G 2026-11-15）**
- 症状：玩家说领奖时弹一句没头没尾的拟声词错误，按钮还亮着；有人说领到的东西重启后没了、又能再领。
- 原因：服务端拒绝领奖时统一回失败码 1，客户端拿它去查原版的错误提示表，1 号恰好是一句拟声词，界面又不变。三个触发：①连点两下，第二下被拒；②游戏开着过零点：原版服务端会推“新的一天”通知来刷新每日任务、签到、在线奖励，离线服务端从没推过，界面停在昨天；③导入存档或重置后没重开就继续玩：为防定时落盘盖掉刚导入的数据，存档被冻结，这一局什么都不保存。另外有些累计类奖励（主线目标）本身没记“已领”，能重复领。
- 修法：被拒时按类别给人话提示（已领过或条件不够 / 货币、道具、次数不够），个别协议单独写；同一请求 3 秒内刚成功过就静默；被拒后把服务端真实状态补推一次，让按钮变灰；每 20 秒查一次日期，换日时补推原版会推的刷新通知；存档冻结时“进入游戏”改成“请先完全关掉再打开”；写盘失败（手机存储满）要弹提示，不能只记日志；所有累计奖励都记已领。
- 怎么确认的：模拟器上连发两次同一领取请求只弹一次“恭喜获得”；模拟过零点后日常清零、登录奖励可领；冻结后点进入被拦住；重启后领取状态保持。每次被拒在日志里记一行（协议名 + 参数），玩家导出日志就能直接定位。

**界面显示成功率 100% 还是失败：显示值和服务端掷骰要同源（案例 G 2026-11-15）**
- 症状：玩家说升阶界面写着 100%，还是失败。
- 原因：客户端界面上的成功率是一串加成（药物、各类 buff、技能）现算出来的，离线服务端按自己的公式另掷骰子，两边对不上。
- 修法：服务端直接取客户端界面上算出的那个值当成功率，取不到才退回自己的公式，“显示多少就是多少”。
- 怎么确认的：把随机数压到最坏，界面 100% 时必须成功。

**回包和推送谁先到：推送比回包早，读玩家字段又比“取玩家数据”早（案例 G 2026-11-10~15）**
- 症状：打开某个商店界面报错；登录后会员等级一直是 0。
- 原因：这个引擎里推送延时 0 派发、回包延时 1，所以在处理函数里直接推，推送先到。商店界面一进来就读货架数据，货架没先推就报错。会员等级这类玩家字段，客户端在“取玩家信息”的响应里就读了，早于“取玩家数据”，在后者里才算就晚了。
- 修法：界面依赖的数据在处理函数里直接推（保证先到），只有“要等回包处理完再推”的才用定时器；玩家字段在最早读它的那个请求里算好。顺序拿不准就在客户端代码里搜读取点。

**把多人系统做成“虚拟玩家”：衣服、榜单、举报三处最容易被投诉（案例 G 2026-11-15）**
- 症状：排行榜点开别人，角色只穿内衣，玩家投诉“涉黄”；点自己的资料页，角色光着；榜单上玩家怎么练都上不了第一；举报按钮点了没反应。
- 原因：虚拟玩家的外观随机抽，约一半缺关键部位；点自己的资料页没有处理函数，回了空数据；虚拟玩家的数值随玩家一起涨，永远追不上；举报按钮原来是往已关闭的官方网页发请求。
- 修法：所有带人物资料的回包统一过一遍“补全整套”（自己用自己的装扮，别人按编号稳定地补全），并扫一遍虚拟玩家的名字和台词有没有不雅字；虚拟玩家的数值取玩家昨日快照的一个比例并设上限，玩家够强就能上榜首；举报改成本地处理（拉黑、改名、给明确提示）；好友 / 公会成员的实力按玩家实力等比。
- 怎么确认的：对所有带人物资料的回包做烟测，断言没有空衣服。

**一个活动的数据缺字段，排在它后面的活动全不出现（案例 G 2026-11-14）**
- 症状：新加的活动图标一直不出现，列表里别的活动正常。
- 原因：客户端处理活动列表是一个循环，逐个交给各自的模型；其中一项缺一个子字段，处理时抛异常，循环中断，后面的都没处理。
- 修法：每个活动的登记函数包 try/catch 并记日志；加活动后在日志里找这一行。

**章节有两条分支时，后半段分支重复播了前半段的剧情（案例 G 2026-11-14）**
- 症状：玩家反馈“前面的剧情又播了一遍”。
- 原因：同一章里两条分支在后几个小节共用同一批剧情任务，状态机按小节顺序推进时把已经读过的任务又推了一次。
- 怎么确认的：用实际的章节代码把两条分支各按小节顺序推完一遍，标出重复出现的剧情任务编号。修在章节状态机里，修完用同样的方法再跑一遍。

### 方向误判（最贵的错误）（续，原节在 `agent-workflow.md`）

**新手指引在离线版被悄悄跳过 / 卡死的几种原因（案例 A，逐条真机复现）**
- 看门狗误判：转场黑屏期间的点击、以及点别的弹窗（`promptType ≠ 1000`）的点击都被计进「点了没反应」次数，指引刚出现就被强制结束。修法：手指晚出现时重置看门狗计时和点击数；当前有别的弹窗在显示时点击不计入；强制结束要同时关指引视图（`ctx:Finish(true)` → `FinishCurGuide()` → `CloseGuideFinger(true)`），否则留幽灵气泡。
- 「新功能开启」弹窗只弹一次：功能格子默认隐藏、靠弹窗播放后才亮；离线版限制成全局只弹一次，后续解锁的按钮一直藏着、指引找不到目标就自动结束并记成已完成。修法：按每个解锁按钮单独记「已看过」键，只播没看过的（已看过的从字典移除并直接 `SetActive(true)`）；日志打 `unlock popup: N new of M -> show`。
- 高亮目标在非主页签上算到屏幕外（>3000）：原版强制手指在目标离屏 / 不可见时结束并标已完成。修法：指引只在主页签开始、登录后轮询检查；目标曾被放到屏幕外时重新摆放而不是结束；地图 / 英雄页上指引层抬到最上并同步移动嵌套画布，归还目标时恢复原缩放。
- 离线绕过了原版弹窗（如抽卡确认框）：指引等的事件没人发 → 卡住。修法：离线绕过弹窗的地方补发指引在等的事件。
- 同步回包的时序：业务事件（编号 ≥100）比指引早到、点击事件比回包晚到，会丢步或多跳一步。修法：步骤开始前 2 秒内到达的业务事件在步骤开始时补发；同一帧内已被业务事件推进的，吞掉随后的按钮点击。
- 通用：指引走查用「补丁内置每步日志（guide / step / 等待事件 / 目标名@坐标 / 手指位置 / 遮罩状态）+ 脚本按手指实际位置点屏幕」驱动，不要往运行中的游戏注入 Lua（会和主线程抢虚拟机 SIGSEGV），人工盲点也会误触看门狗。

### 工具链 / 环境（实测坑）（续，原节在 `device-emulator.md`）

**本地应答函数「查不到就什么都不做」，剧情晾在原地**
- 症状：剧情走到某个小游戏，对白框消失、画面停住，怎么点都不动；日志里没有报错，也没有"未处理的请求"。只在某个分支选项里出现，别的分支正常。
- 原因：原版把"向服务器要小游戏结果"换成了本地函数，函数里查配置表用错了表名（表其实叫 `rept某某Cfg`，写成了 `rept某某`，取出来是空），于是返回"没启动"；调用处在"没启动"时什么都不做。客户端自己随机的小游戏不走这条路，所以大多数小游戏正常，只有"结果由服务器给"的那几个起不来。
- 修法：表名对着配置管理器里的赋值语句核一遍；本地函数失败时必须留一行日志，并且走一条不卡死的退路（这里是跳过小游戏接着播）。
- 举一反三：靠试玩覆盖不到所有剧情分支。配置里有"是否由服务器决定"这类字段时，直接把这类条目和用到它们的对白全列出来（真机上注入一段只读脚本打日志即可），逐个确认有本地实现。服务器回包里的数值（落点、次数）没有原始记录时，看小游戏结束后接的那几句台词，剧情要什么结果就给什么结果。

**账号字段是"空"和是 0 不一样**
- 症状：主界面头像是一个空圆；点头像没反应。
- 原因：本地造的账号没填头像 / 头像框编号。原版代码对 0 有兜底（显示默认头像），对"空"没有：既不走兜底，也查不到配置，什么都不画。点头像没反应是另一回事：面板等的那条资料请求没人回（改名、换头像这些"写"请求早就接了，偏偏漏了打开面板的那条"读"请求）。
- 修法：本地造账号时，协议里的数值字段都给上默认值，默认值去全局配置里找（这里是"默认头像 / 默认头像框"那一条）。接一个面板时，把它打开、读、写三类请求列全，别只接写。

**本地应答时调了原版的"回包处理"，它顺手又开了一条流程**
- 症状：打完一关回到列表，关列表时冒出一段没见过的对白，后面还跟一场多余的战斗。
- 原因：离线版自己直接开了战斗页，同时为了"记下当前关卡"调了原版的开始回包处理；那个函数还会通知列表面板去走原版流程（对白 → 对白里进战斗）。两条流程并存，原版那条被压在下面没人管。
- 修法：调原版回包处理前把它读到底，看它通知了谁。只需要其中一两行副作用时，自己写那一两行，不要整个调。

### 分档第二批：开局拉满 / 资源券（2026-10-17，会话 C）（续，原节在 `save-data.md`）

**往背包加一个「使用」弹自选面板的道具：配置行 + 现成的礼包使用消息**
- 配置库 `reptItem` 加一行（`iItemType=6`、`iUseType=2`、`iSubItemType=0`、`sSource='999|活动'`）。`sSource` 为空时详情面板不显示「使用」；`iSubItemType` 101~103 走礼包预览面板 122、104 走原版自选礼包，都不要。点「使用」发 `E_SVR_MSG_ID_OPEN_PACKAGE`，离线分发表里按 `iPktID` 拦自己的券，别的礼包交给原来的处理。
- 原版 `<宠物自选礼包面板>` / `<角色自选礼包面板>` 只有宠物 / 角色两种固定样式，没有通用列表，别指望复用。

### 游戏内读相册 / 自定义图片（案例 A 2026-10-17，tier/custom-media）（续，原节在 `device-emulator.md`）

**pbc 解出来的配置行读「不存在的字段」直接抛错**

### 零散条目

**At runtime the config table name has a `Cfg` suffix that the dumped table name lacks; reading the wrong name silently gives 0 rows (2026-10-18, 案例 A)**
- Symptom: the code that unlocks everything says it worked, and the self-test passed, but the count stayed 0. `dt.reptXxx` is nil at runtime; the real table is `dt.reptXxxCfg`. Some tables have no suffix (`reptCGProp`, `reptPet`). Grep the original client code for how it reads that table (`DataTableMgr.<name>`, `GetAll…Cfg`).
- Fix: try both names (`dt.xCfg or dt.x`), and give every count check `> 0`. Otherwise "0 == 0" passes and hides the bug.

**A client getter that the decompiler emits as `return nil` was filled by the server; offline it stays empty forever (2026-10-18)**
- Example: `BackRoomModel:GetCollectorCGIDs()` decompiles to `return nil`, so the CG album is dark even when the save owns every CG. Override the method on the class at login and build the list from the offline save.

**"Unlock everything" exposes dead buttons the original never shipped (2026-10-18)**
- Symptom: after a perk that makes every unlock check pass, the main screen shows entries that do nothing when tapped (案例 A: the "升星" button btn_petStarUp on a 某系统界面, and the blank 好友 button).

**A daily "wish" flag preset to "done" hides the whole riddle UI (2026-10-19)**
- Symptom: gift riddles never appeared and the wished gift was drawn from every character's pool.
- Cause: the login seed set the "liked gift sent" flag to 1 for everyone, and the wish picker ignored the gift table's per-character category column.
- Fix: read the category column (here `iGiftType` equals the character ID), keep the per-day "solved" state in the save, and resync it whenever the base info is rebuilt.

**A server-side relaxation never takes effect because the client checks the same rule locally first (2026-10-19, 案例 B)**
- Symptom: the offline server lowered "auto explore" from 10 cans to 1 and the unit tests passed, but on the device the button did nothing. The client checks `num < 10` itself, shows a toast, and never sends the request.

If it is hard-coded, either keep the original value or patch the client too. Then tap the button on the device; a server test cannot catch this.

**A collection UI exists but nothing in the offline server ever grants its items (2026-10-19, 案例 B)**
- Symptom: the album/collection screen works, its query and "crack/unlock" routes are implemented and tested, but every entry stays 0/3 forever. The items were dropped by a server-side roll (here: cat explore "有几率获得线索") that the offline rewrite never added.
- Fix: for every item type that a collection screen counts, find at least one grant site in the offline server (`grep "type: <N>"` in the modules). Read the UI help text: it usually names the source. Add an end-to-end test that goes from the source to the collection screen.

**Sized a revived feature from code alone; the page art said otherwise** (2026-10-23)
- Symptom: a revived "level a card to unlock its message" page was filled with ~50 rows made by pairing every related message onto a card range; on screen, the background art named one specific festival event and its dates.
- Cause: the server-side list was lost, and the row count was inferred only from the client's per-group rule ("exactly 2 per card").
- Fix: open the page before deciding how much data to serve. Filtering the content by the printed dates gave exactly 2 per character and 4 cards (one screen of columns) — three independent checks agreeing — so only that event ships.

**The decompiled data table disagreed with the game at runtime** (case C, 2026-10-24)
- Symptom: workshop evolution consumed 2 copies on the device, while the same server code run in lupa against the decompiled `data/partevolution.lua` consumed 3. The UI showed "14/3" (it prints `originalNum + 1`), i.e. 2 at runtime.
- Cause: the decompiled table had a wrong value for that row (re-decompiling the final bundle gave the same 3; there was no hot-update file on the device). Large constant-only tables are where decompilers slip. The server was right because it reads the same in-memory `Data` the client uses.
- Fix: never hard-code numbers copied from decompiled tables into the fake server; always read `Data.xxx` at runtime. When a device result disagrees with an offline test, log the runtime value (`N.log`) before "fixing" the server. Treat decompiled tables as good for structure and ids, not as ground truth for every number.

## 「按钮点了没反应」先查有没有没回的等回包请求（案例 C，2026-10-24）

- 现象：每日任务面板里第 1 个活跃宝箱点了不发请求，同面板别的按钮有的能用；模拟器上什么都不提示，真机上过一会儿弹「数据请求超时」。
- 原因：面板 onInit 发了一个 RPCWaitSend("queryElect")（评选赛数据），本地服务器没接 → 客户端的等待遮罩把界面锁到超时，这段时间里的点击全被吞掉。和特效、射线检测都无关（之前在这上面白花了两轮）。
- 做法：一出现"点了没反应"，先看 logcat 里有没有 `unhandled`；更彻底的是把客户端所有 `Event.RPCWaitSend / RPCOverTimeSend` 的请求名扫出来，和服务器已注册的对比，没接的至少回一个空包（脚本思路：正则扫 `Event\.(RPCWaitSend|RPCOverTimeSend)\s*,\s*"(\w+)"`）。

## 中途改属性客户端不理：只有 setX、没有 onX（案例 C，2026-10-24）

- 现象：在线时周期开启（05:00 的周六周期）、角色支线通关后下一关解锁，都要重新登录才生效。
- 原因：客户端属性分发（refreshEntityProperty）登录时调 `set<Name>`，之后变化调 `on<Name>(old, new)`。很多模块只写了 setX，在里面把数据拷进自己的管理器（ActivityCycleMgr、TaskBranchData），中途用 batchSyncProperty 推属性，值虽写进了玩家对象，管理器里的副本不变。原版服务器中途用的是专门的推送 RPC（notifyCycleStatus、syncBranchProgressData）。
- 做法：服务器中途推属性前，先查客户端有没有 `on<Name>`；没有就找同名的 sync/notify RPC。可以写脚本扫 `function set(\w+)\(self` 和 `function on(\w+)\(self, *old`，和服务器会中途推的属性求差。另一个连带坑：重发属性的计算函数里如果有"已通知"之类的副作用（cycle 的 notified），重发会把增量推送吞掉。

## os.date 在游戏进程里会返回错的日期（案例 C，2026-10-25）
- 现象：本地服务器的"游戏日"偶尔在登录时跳到明天又跳回来，按天重置的数据被清两遍。
- 根因：Lua 5.1 的 os.date 调 C 的 localtime / gmtime，结果放在进程共用的静态缓冲区；Unity / Mono 的其他线程同时调用会把它写乱。同一秒里 "%Y%m%d" 偶尔返回明天，"!" 格式的 UTC 错 16 小时。登录时调用最密。
- 修：在最早加载的模块里包一层全局 os.date，连调两次结果一致才返回（客户端模块只把 os 表存成局部变量，也一起受益）。查这类问题时，在可疑函数里同时打印"算出来的值"和"重新格式化一次的值"，两者不一致就是它。

## 客户端"按物品号数数量"的缓存可能在登录时被建成空表（案例 C，2026-10-25）
- 现象：存档和客户端背包里都有某件物品，界面却按 0 件处理（收集进度 0/3、商店"已有 0"），只有本次登录里新得到的物品数得对。
- 根因：Bag.amoutCache_ 第一次查询时按当时的背包一次建好，之后只有 onBagUpdate 会补；离线服务器把背包放在登录属性里一次下发，属性按号赋值，背包装进来之前已有界面查过数量。
- 修：登录后第一个 tick 把这个缓存清成 nil，让下次查询按完整背包重建。查这类问题时直接探针打印背包表的条数和缓存表的条数。

## 装扮部件：设部件接口每次都从加载时的部件表重新合并（案例 D，2026-10-29）
- 现象：先关眼镜再开睡衣，眼镜又回来了。
- 做法：一次传完整的开关表。部件表的键是装扮表里的商品 id（不是部件 id），打开一件会自动关掉同类其他件。

## 大模型回复清洗：先去加粗再去 *动作*（案例 D，2026-10-29）
- 现象：`**今天也想见你哦**` 清洗后成了空串。
- 原因：删动作描写的 `\*[^*]{1,60}\*` 先执行，把加粗里的正文当动作删了。
- 做法：先删 `**` / `__`，再删括号旁白和 `*动作*`。用假接口按触发词回各种脏格式，逐条验清洗结果。

## 给大模型的人设提示词：先找人审（案例 D，2026-10-29）
- 现象：自测全通过的人设提示词，独立审稿挑出 10 个问题：人设卡“你/他”指代写反、待机催话台词被当成样例和兜底、出戏词表误杀“作为一个过来人”、要求模型“不知道自己是 AI”（在线模型会破角声明）、重试提醒复述触发词、Ollama 默认上下文截掉人设。
- 做法：人设卡第二人称对角色说、玩家统一称“对方”；样例按情境分组并剔除待机台词；出戏规则写锚定正则；用“对方知道是虚构、不确认不否认”代替“否认是 AI”；重试提醒附在最后一句用户话后、不引触发词；本地模型 `OLLAMA_CONTEXT_LENGTH=8192` 并少带几轮。假接口只能验流程，验不了提示词本身。

## 没有 API 也要用真实模型试一遍提示词（案例 D，2026-10-29）
- 现象：假接口只验流程；人设提示词实际效果没人测过。用户没有 API 密钥、电脑上也没有本地模型，又不该替用户下载安装。
- 做法：让子代理（便宜档 + 中档两种）当“应用背后的模型”：把应用发出的同一份系统提示词和诱导题写成 JSON，子代理逐条作答写回 JSON，再用应用里同一套清洗和出戏规则判分，主会话通读。这一轮挑出了一条**我们自己规则的误判**（“我是某某呀”被当成第三人称旁白）和“口头禅太勤”，改后复测。报告里写明替身模型不是用户要接的模型，结论要打折扣。

## 轻生 / 自伤的话不能交给出戏检测（案例 D，2026-10-29）
- 风险：模型听到“不想活了”时往往跳出角色给求助建议，出戏规则会把它当成出戏、重答，最后换成一句撒娇的备用句。
- 做法：在出戏检测之前先判轻生 / 自伤信号（不想活、想死、自杀、轻生、割腕、死にたい……，口语“笑死、困死、考试考死了”不算）：命中就只调一次、不重答、不换句，回复后面保证附上求助信息（中国大陆 12356 心理援助热线，有危险拨 120 / 110）；没接接口时也不回原台词。宁可多触发。人设规则里同时写一句“这时不必拘泥于角色口吻”。

## 长期记忆整理失败时游标也要前进（案例 D，2026-10-29）
- 现象（代码自查发现）：整理结果不合格（被出戏过滤拒掉）时只是不写记忆，游标没动，之后每发一句都会再触发一次整理，悄悄多花接口费。
- 做法：结果不合格就保留旧记忆、游标照样前进；只有网络出错才下次重试。

## 任务进度的红点：在事件处补请求，不只靠开机预载（案例 A 2026-11-07）
- 现象：做完日常 / 七日任务，主界面不亮红点，要打开任务面板才更新。开机预载只能管到"进游戏那一刻"的状态。
- 做法：在任务事件触发处补一次静默请求，加 0.5 秒防抖，免得一串事件连发。

## 上限由配置表某一列决定时，改那一列最省事（案例 A 2026-11-16）
- 现象：玩家嫌能收藏的语音太少，想让上限随玩家等级涨。原版上限是好感等级表里的一列，收藏按钮、管理页、离线判满三处都读它。
- 做法：在内存里给那一列加上加成（原值另存一份，避免重复叠加），在登录、升级存档、打开相关页面时刷新。三处自然一致，不用逐个打补丁。

## 给配置表挂的自定义标记被 for-in 当成一条数据（案例 G 2026-11-16）
- 现象：最高 VIP 的玩家一打开 VIP 页就卡死。
- 原因：离线代码往原版 VIP 配置表上挂了一个自定义标记字段，界面用 for-in 遍历，把它当成多一级 VIP，去读不存在的配置。
- 修法：标记用 `Object.defineProperty(..., {enumerable:false})`，或者干脆别挂在原表上，另存一张表。

## 离线加载卡住：在等永远等不到的东西（另一款游戏 2026-11-17）
- 加载卡住，多半是在等离线永远等不到的东西：某个场景要等服务器推数据（改用游戏自带的本地场景开关进去）；赛季视频、开场视频、开箱动画放在 CDN 上，离线播不完（直接标成"已看过"）。
- "已看过"一类客户端设置要进存档，不然一次性弹窗每次启动都出。主界面按钮不显示，是对应系统都没解锁，改成全开。
- 让 AI 替玩家上场会弄坏结算：把玩家标成机器人以后，结算靠"不是机器人"认玩家，就跳过了；某个玩法要从真人列表取值，全员 AI 时列表为空，每帧报错。修法：结算按 uid 认玩家；验证结算另写一个"笨玩家"脚本代打。
- 存档等级超出某张表的范围（伤害飘字的字号表只到 15 级）就每次掉血都报错；建号时间每次登录都变，按天算的功能会漂（首启定下来存进存档）。
- 出错保护返回空值会让面板崩，改成返回空表 / 最小可用回包。
- 首通奖励抽到空也记"已领"，以后永远拿不到：改成真发出东西才记。

## 客户端自带的报错码和界面空位，都是回包的提示（案例 B 2026-11-16）
- 关池、不在活动时间这类拒绝，先找客户端自己的错误码表（案例 B 的错误码表里就有"不在活动时间"）。回 `result:false` + 那个码，客户端自己弹框，不用改客户端也不用自造文案。
- 宣传底图上"祈愿 __ 次内必含"留了空，对应界面上叠在底图上的文本控件，它读的是回包里的某个字段，只有字段存在才显示。所以只给限定池带这个键，别的池不带，老池界面不变。

## 补缺失语音的时长要向上取整（案例 B 2026-11-16）
- 现象：补上的语音尾巴被掐掉。
- 原因：客户端按回包里的时长倒计时，到 0 就停声音。官方数据自己也不统一（有的向下取、有的向上取）。
- 修法：给的时长一律向上取整。
