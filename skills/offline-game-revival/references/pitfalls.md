# 失败账本

现象 → 原因 → 修法。下次遇到同样症状直接查这里。读到的坑花一分钟，踩进去的坑花一晚上。

## 启动阶段

**进离线入口后中途报错，落回登录界面**
- 原因：进得太早，配置表还在解析
- 修法：等数据表就绪再进，把入口挂到解析完成之后
- 实例：案例 A `ParseDataTable` 未结束时进 `OfflineEnter`，拿到空表

**新包一启动就闪退，日志是"分配内存失败"而不是脚本错误**
- 症状：启动约 2 秒原生崩溃；日志有 `Could not allocate memory ... MemoryLabel: String`（要分配的字节数是个天文数字），随后 `Fatal signal 5 (SIGTRAP) ... UnityPreload`。上一个包还好好的，这次只多了几百字节脚本。
- 原因（原先的判断）：往某个脚本文件里注入的代码把它顶过了加载器的体积界限（案例 A：261184 字节能启动，261352 字节崩）。**2026-10-18 更正：很可能不是体积界限，而是某块「压缩后恰好等于原始大小」被 Unity 当原样读——见文末 "compressed size equals its raw size" 一节；日志特征一模一样。**
- 修法：打完全部补丁后给宿主文件统一瘦身（去整行注释、空行、行首缩进；长字符串内部不动；瘦身必须在最后做，否则前面靠缩进原文当锚点的补丁会找不到位置）。更重要的是在打包脚本里加体积断言，留足余量，让它在打包时失败。
- 教训：每次装新包后先确认进程还活着再点屏幕。闪退后屏幕是桌面，盲点会点进别的应用。

**黑屏 / 卡住，日志有 `CRC Mismatch`**
- 原因：改了 bundle，校验字段没更新
- 修法：把生效的 manifest 里 CRC 改成 `0` 或 Unity 日志给出的正确值
- 注意：可能有多个 manifest，要试出游戏真正读的那个

**黑屏且画面完全不动，但调试通道照常响应（JS 引擎）**
- 判据：`Laya.timer.currFrame`（或引擎的帧计数）不再增长；日志里只有一两条 `JS onFrame error`。
- 原因：引擎主循环是 `rAF(loop)` 里先渲染再续帧，渲染抛一次异常就不再续帧。离线后资源偶发加载失败、回调拿到空数据仍去建对象，是常见触发源。
- 修法：给每帧入口（如 `stage._loop`）包 try/catch，再给触发源对象加空数据保护。只修触发源不够，下一个空资源还会冻住。
- 实例：案例 B 的剧情 1-1 的粒子 `.part` 加载失败，`new Particle2D(undefined)`，见 `case-b-laya-native.md`。

**改了一处伪造回包后，资源开始随机加载失败（重试在同一毫秒内全部失败）**
- 原因：引擎复用网络请求对象（连接池/加载器池）。伪造回包时把 `status`、`readyState` 钉死在实例上（例如 `defineProperty` 写成只读），后面复用这个实例的请求一发出就"已完成、失败"。
- 修法：伪造字段只在当次有效，下次 `open()` 前删掉。上线前用"同一对象连发两次请求"自测。
- 实例：案例 B 的 v0.3d，为 `""` 皮肤伪造的 404 毒化了 Laya Loader 的 XHR，剧情 1-1 打不开。

**授权码：所有玩家的本机码一样 / 设备上验签代码报 BigInt 未定义**
- 原因：引擎自带的"设备信息"多是 MAC/IMEI，新版 Android 统一返回假值；嵌入式 JS 引擎（如 LayaNative 的 V8）可能很老，没有 BigInt。
- 修法：本机码从 Java 层取 `ANDROID_ID`（smali 加一个静态方法，走引擎已有的 JS→Java 反射桥）；验签用不依赖 BigInt 的实现，并与标准库对拍。
- 实例：案例 B，见 `case-b-laya-native.md`「授权码 + 水印」。

**功能点下去没反应，日志有 `NullReferenceException`**
- 原因：离线时网络层抛异常，打断了调用方
- 修法：所有离线调用点用 `pcall` 包住

**JS 引擎启动约 2 秒后原生崩溃：过早挂了 `window.onerror`（案例 B 2026-10-29，模拟器）**
- 症状：加了导出日志模块的测试包，在模拟器上启动约 2 秒就 SIGSEGV，正式包正常。先后怀疑读了不存在的文件、怀疑 debuggable 标志，换掉之后照样崩。
- 原因：模块在游戏代码加载前挂了 `window.onerror`。conch 设这个钩子时会调原生的异常弹窗函数，在 ARM 转译层上直接崩。游戏后面还会用自己的钩子覆盖它，这个钩子本来就没用。
- 修法：不挂 `window.onerror`，只包装 console 的方法；启动时不读文件，第一次落盘时再读。序列化日志参数时只展开普通对象和数组，引擎内部对象只记类型名，免得碰到原生属性又崩。
- 怎么确认的：去掉 onerror 和加载时读文件后，重启模拟器能正常启动，全流程跑通。

## UI 层级

**某个面板打开后盖住别的画面 / 整屏黑**
- 原因：为抬高某层改了 `Canvas.sortingOrder` / `overrideSorting`，之后没还原
- 修法：抬升前先记住原状态，退出时还原。**每次抬层都要配一个还原**

**地图盖住界面，或反过来按钮点不动**
- 原因：不同 canvas 抢排序
- 修法：明确分层（地图 / HUD / 面板 / 对白各一档），新面板接入时确认不会打乱已有分层

**弹窗被底下的界面盖住，早期的绕法是"弹窗一开就把底下那层藏起来"**
- 症状：关卡详情弹窗背后不是关卡列表，而是更底下的地图。翻补丁发现有人写了"打开详情时隐藏列表，避免详情被列表盖住"。
- 根因：另一个补丁为了让某个入口卡片"肯定在地图上面"，把它所在的画布层级直接设成 9000——那块画布其实是整个主界面的根。
  游戏自己的弹窗管理器把弹窗固定从 100 排起（并且每次显示都会重设），所以之后所有弹窗都被 9000 压住。
- 修法：先搞清游戏原有的层级带（这里：地图内部 <= 35、主界面按钮 40-47、弹窗 >= 100），自己加的层级一律落在带内（改成 60）。
  不要用"抬得比谁都高"解决遮挡，也不要去和管理器抢弹窗自己的层级（设了也会被它改回去）。
- 排查办法：写一个只打印的函数，量出"下层面板用到的最高层级"（根画布 + 往上的祖先画布 + 它里面单独排序的小画布）和上层面板的根画布、渲染模式，打一行日志。
  数字一出来就知道是谁不对（这次一眼看到 baseRoot=UIList/9000）。
- 教训：见到"把 A 藏起来免得挡住 B"的补丁，多半是层级没理顺留下的债，值得回头找根因。
**嵌套 Canvas 在父 Canvas 未激活时被重新激活，会被当成根画布重排（案例 A，踩了多轮）**
- 症状：去过历练区再回主线地图，当前任务节点看不见，实际被摆到了屏幕右侧（锚点 x≈1855）；节点是激活的。
- 原因：节点自带嵌套 Canvas，父 Canvas 不活跃时重新激活它，Unity 把它当根画布重排：锚点变 (0,0)、尺寸等于屏幕、缩放变成画布缩放系数（这里 0.456）。
- 修法：加布局自检：正常时记一份 RectTransform（锚点、轴心、尺寸、位置、缩放）；切地图时检查，锚点 x 异常或缩放不为 1 就还原（`OfflineTaskTipSanity`）。别去追是哪一次激活弄坏的。
- 怎么确认的：探针对比往返前后节点的完整布局值；修后日志出现 `task tip layout restored`，往返几次节点都在。

**地图把根列表 Canvas 改成 Overlay 后：粒子 / 模糊特效失效，相机模式弹窗被盖住（案例 A）**
- 症状：小游戏里蝴蝶 / 光圈看不见、对白里雾气雪花不显示、对白开头一整块白框；某些弹窗（指引后弹窗、关卡详情框）也看不见。一度怀疑缺图，但包里资源都在。
- 原因：进地图时把 `UIList` / `NormalList` / `PopList` 等根列表画布切成了 `ScreenSpaceOverlay`。Overlay 下粒子特效不渲染、抓屏模糊（grab-pass）抓不到屏渲染成白块；留在 Overlay 的列表画布还会盖住相机模式的弹窗。
- 修法：进剧情 / 小游戏时把这些画布切回 `ScreenSpaceCamera` 并恢复原 sortingOrder（`UIList` 10、`NormalList` 60、`PopList` 100）；对白模糊用运行时开关关掉；做一个自检函数在非地图 / 非回顾 / 非剧情状态下每次面板加载和页签切换后跑一次（`OfflineListCanvasSanity`）。
- 教训：遇到白框 / 特效看不见，先怀疑 Overlay 画布遮挡，而不是缺图；基础画布不要抬到超过 100（不要用大 order 或藏底层界面绕层级，先测画布链）。

**面板抬到 Overlay / 高层后，它的嵌套 override 画布没跟着抬，新开弹窗被盖住（案例 A 男主页）**
- 症状：男主页里点语音，语音面板看不见；点返回后男主页按钮全消失只能卡死；确认框也被盖住。
- 原因：男主页（panel 1024）把基础画布抬到 Overlay 8000，嵌套画布（`UISort` / `btn_back` / `btn_busy`）没跟着抬；之后新开的面板 order 比它低。
- 修法：抬面板时把它里面带独立排序的嵌套画布一起抬同样的量；在面板管理器每次显示面板后加钩子（`OfflinePanelOverHero`）：某页开着且新面板不是它时，把新面板根画布切 Overlay、嵌套画布抬到它之上；关掉该页后还原。

**界面元素只在"完整刷新"时才开关，而离线版切页面走的是快路径**
- 症状：某个小图标去过别的页签再回来就不见了；反方向又残留在不该出现的页签上。
- 原因：原版在重新初始化界面时按当前模式设它的显隐；离线版为了省加载时间复用了已经建好的界面，不再经过那个初始化。
- 修法：在快路径的"应用目标页面"函数里，把依赖模式的显隐各设一次。写快路径的时候，把原版初始化函数里所有 SetActive 过一遍，逐个确认。

**离线代码把「原版打开子面板时顺手关掉地图面板」当成离开功能，子面板几秒就被顶回地图（案例 A 2026-10-23）**
- 症状：在某个玩法区里点兑换所，不到 3 秒就弹回历练区地图，商店被关掉；同一区里的编队按钮也是这样。
- 原因：原版打开商店时会先关掉该玩法的地图面板。离线补丁里有个监视器，把「该功能的面板关闭」当成离开，于是把外层地图重新挂了回来。商店（面板 1）和编队（面板 111）不在该功能的放行名单里。
- 修法：查出子面板号，加进该功能的放行名单。凡是写了「离开某功能就恢复 X」的监视器，都要把该功能里会打开的所有子面板列一遍。
- 怎么确认的：logcat 里看到关闭地图面板后紧跟着 feature leave 和地图恢复；加进名单后，商店开着 6 秒以上不会被关掉，返回和真正离开时地图都能正常挂回。

**修弹窗被压住时，补救检查查错了节点，修了两次都没生效（案例 A 2026-11-05）**
- 症状：进某个角色页时，当天有互动事件的角色，对白看不见、也挡不住点击。玩家连点屏幕就变成一直在触摸角色，每点一下排一句对白，退出页面后才一股脑弹到地图上。
- 原因：引擎里有两个同名的弹窗列表节点。对白实际挂在 `[Stage] MainStage/PopList` 下，而之前的补救逻辑只检查了 `ApplicationObject/PopList`，等于什么都没碰到。
- 修法：页面开着时，每隔约 0.3 秒检查一次对白是不是掉到了页面下面，掉了就抬回来；重复的事件对白不再排队；退出页面前清掉排队的对白。修「盖住 / 压住」类问题之前，先在运行中把画布层级 dump 出来，确认弹窗真实挂在哪个节点，别按名字猜。修过一次没生效，先怀疑检查的对象不对。
- 怎么确认的：构造一个「有待处理互动事件」的角色。修前连点 5 下排了 5 句，退出后弹到地图上；修后排队数为 0，退出后地图干净，好感奖励当场弹出，和玩家录屏对得上。

## 存档

**每次重启回到最初关卡、等级或经验**
- 原因：服务端下发的会话态（关卡、等级、经验、任务领奖等）只改了内存，没有完整落盘；只保存一个字段同样会让状态互相脱节
- 修法：在每个状态变更点统一保存，并在进入 UI / 应用存档前先恢复；改完必须做杀进程重启测试，不能只在进程内验证
- 分层验证：先单独验证保存路径，再构造“保留待测状态键、其他键恢复默认”的恢复用存档，确认读路径真的应用了持久化值，而不是误走了默认/拉满分枝

**每次启动被「种子数据」重置回初始值（等级 / 突破 / 星级）**
- 原因：为了让玩家开局就拥有内容，离线补丁会在每次登录时**遍历配置表重新下发一份全量数据**。
  如果这份种子把可成长字段（卡等级、突破等级、星级…）按初始值写死，玩家的养成成果每次重启就归零。
- 特征：只保存「星级/碎片」这类显眼字段还不够——**凡是玩家能练的维度都要各自落盘**，缺一个就少一条成长线。
- 修法：给每个可成长维度一个独立的 prefs key（`XXX_LVLS_V1` / `XXX_BREAKS_V1`），
  种子构造信息时用「落盘值 or 初始值」，并在每个变更点写完即存。
- 实例：案例 A 的剧情战斗卡牌只落了星级和碎片，`iLvl` / `iBreakThroughLvl` 每次启动被重造为 1 / 0，
  于是「升级」「突破」两条线在重启后全部作废。

**改档 / 抬状态前先备份 prefs，验证链的中间档丢了就不能重放**

- 原因：低等级档、未通关档这类"验证链起点"不是游戏会自动重建的东西；一旦被覆盖或推进过头，
  只能 `pm clear` 从零再来，而"从零再来"复现不了当时的中间状态。
- 修法：每次开始"从低等级往上验证"之前先把 `shared_prefs` 拷出来存进项目 `logs\<轮次>-...\`，
  并在快照里写清"这个包/这个档对应什么状态、备份在哪、怎么还原"。
- 判据：报告里说“已验证 1-6 通关、停在 1-7”时，必须同时能回答“怎么回到那一刻”。

**收一次菜卡好几秒：真正慢的是「每次变更都读好几个大存档串」，不是 Save（案例 A 2026-10-20，真机）**
- 现象：离线版每改一次存档就 `PlayerPrefs.Save()`。收一次菜（6 个道具）整帧卡 ~6 秒，祈愿每抽一样卡，登录和回主界面也顿。**模拟器上完全看不出来**。
- 先踩的坑：想当然把元凶定成「Save 把整档（~100 KB）同步写盘」，去做「攒着批量 Save」。结果更糟——变成每个道具 1.8~2 秒。**批错了对象。**
- 真因（上真机实测才看清）：`Save` ≈ 0.000 秒、写 8 KB 值 0.02 秒、**读 8 KB 值 0.07~0.16 秒**（JNI 往返 + 解码）。改一个道具要 `GetString` 好几个大 blob，卡的是读不是写。模拟器上读也只有 ~10 ms，所以照模拟器判断必然误诊。
- 修法：离线自己的键（统一 `OFFLINE_` 前缀，原版代码从不碰）在 Lua 里留一份内存副本——读过一次就不再问 `PlayerPrefs`；写只改内存 + 记 pending，落盘时一次性 `SetString` + `Save`。落盘时机：玩家停手 6 秒 / 改动攒够 90 秒 / 切后台·失焦·退出（补丁接 `LuaApplication.OnApplicationPause`·`OnApplicationFocus`·`OnApplicationQuit`）。效果：改道具降到 0.006 秒，十连跑满 60 fps，登录与回主界面的卡顿消失。
- 边界：整份存档被换掉的操作（导入、模式还原）在**直接读** `PlayerPrefs` 前先 `OfflinePrefsApplyPending`、**直接写完**后 `OfflinePrefsCacheClear`；授权码这种一次性写当场 `Save`，不进缓存。带动态后缀、或别处用 `GetInt` 直接读的键，不要塞进这个「字符串」缓存。
- 通用教训：**卡顿一律上真机量，别信模拟器**（模拟器的 I/O 快一两个数量级，会把瓶颈藏掉）；做批处理之前先确认「批的是真瓶颈」。实现见 `tools/offline_prefs_flush.lua`（拼进最早加载的 `LuaApplication.lua`，并带锚点断言）。

**「资源清零重开」后体力只有 1：清零表漏了「新档默认值靠它不存在」的键（案例 A 2026-10-22）**
- 症状：清零重开后体力显示 1/120，而新档本来是满的。
- 原因：新档的满体力是在体力时间戳键不存在时初始化出来的；清零只清了资源键，没清这个时间戳。
- 修法：做清零 / 重开功能之前，先列出新档初始化依赖哪些键「不存在」，把它们都放进清零表。已完成主线的奖励会被补发机制按原表补回来，要先跟玩家说清楚。

**开发工具改完存档就强杀进程，改动还在内存里没落盘（案例 A 2026-10-20）**
- 症状：执行 `timeskip` 后读回时间偏移键，值没变。
- 原因：存档已经改成内存缓存 + 批量落盘（见上面「收菜卡顿」那一条），工具在落盘之前就杀了游戏。
- 修法：工具里先调落盘函数（这里是 `OfflinePrefsFlush`），再杀进程；手动修时，注入「改值 + 落盘」后再重启。凡是改成延迟落盘的项目，所有会杀进程的开发工具都要检查一遍。

## 本地回包 / 伪造服务器数据

**界面显示 `1970年01月01日`（或类似的纪元默认值）**
- 原因：为了让卡片/条目走「已解锁 / 已读」分支，把服务器下发的**时间戳字段**用非零哨兵常量顶上去
  （典型写法 `iFirstReadTime = 1`）。下游拿到这个字段直接当 Unix 秒去 `os.date('%Y', t)`，
  1 秒就是 1970-01-01。分支判断（`~= 0`）过了，显示就露馅。
- 修法：**伪造服务器字段时按它的真实语义取值，不要只满足分支条件。** 时间戳就给真实时间（
  `os.time()`），并按条目/章节持久化（例如 PlayerPrefs key 带条目 ID），首次写入后续复用，
  这样日期稳定、重启不变、也不会回落到「未读」分支。
- 实例：案例 A `<角色约会卡片项>:SetCardItem` 的 `chapterInfo.iFirstReadTime`，
  三处本地回包都写过常量 `1`，全部要换成 `OfflineEF_RoleReadTime(chapterID)`。

**某个入口按钮/菜单永久不出现，点上去像「空按钮」**
- 原因：原版代码用**某个状态值**来 gate 入口，而离线回包把这个状态硬编码成了「临时态」。
  典型：热卖/活动/限时状态本来只在活动期 > 0，离线种子为了「让数据看起来有」写死一个非零值，
  于是 `ShowXxx(not IsHotSaleTime())` 这类判断永远走隐藏分支，入口再也没有打开过。
- 排查：在反编译代码里搜这个状态的 getter（如 `IsHotSaleTime` → `sellInfo.iLeftFastSellTime > 0`），
  再搜谁读它、读到之后是显示还是隐藏。
- 修法：**离线种子要把状态落在「正常态」**（能让玩家自己触发的初始状态），不要落在「临时态」。
  「有数据」和「处在限时状态」是两件事。
- 实例：案例 A 的店铺 `iLeftFastSellTime = 1000` 让「热卖中」永不过期，
  `StoreBuildPanel` 的 热卖/上架/升级 三按钮被永久隐藏 → 商业街上架面板没有入口。

**别跨模块调用「注入进去的全局函数」——它们可能是惰性定义的**
- 症状：自己在补丁模块 A 里调用模块 B 提供的全局函数（如 `OfflineWareHouseApplyItem`），
  调用处明明在 `pcall` 里"没报错"，但**功能静默失效**（东西没发出去、状态没变）。
- 原因：补丁常把模块文件的内容**整段替换进某个函数体**（例如把抽卡模块塞进
  `XxxManager:SendLuckDrawReq`）。于是模块里那些看似全局的 `function Foo()` 定义，
  **只有在该函数第一次被调用时才会执行**——在那之前 `_G.Foo` 就是 `nil`。
- 排查：在调用点先打印 `tostring(_G.那个函数)`。是 `nil` 就中招了。
- 修法：**只用同一模块内已有的工具函数**，或把需要的工具定义在一定会先加载的地方。
  本项目里 `offline_all_features.lua` 自带 `OfflineEF_ApplyItem`（且内置 fallback），
  种植模块改用它之后就正常了。
- 附带教训：**发放/扣减这类关键动作不要只包在 `pcall` 里静默失败**，
  至少在失败时打一条日志，否则"没报错但没效果"会查很久。

**同一个种子函数喂多个消费方，筛选口径被"一刀切"**
**复活活动时，每个活动的购买 / 领取请求都要逐个确认有 handler（案例 B）**
- 症状：往事重现活动里买不了情笺。
- 原因：那几个活动的通用购买请求（`reqActivityCommonBuy`）没有专门的 handler，落到通用逻辑返回「活动没配置」。
- 修法：在通用购买 / 领取入口加兜底，按配置处理这类活动。复活一个活动 hub 时，把它每个子入口的购买、领取、兑换请求名列出来逐个确认离线有接（可配合 `case-c` 的「扫所有 RPCWaitSend 和已注册路由求差」）。
- 症状：某个列表/商店/背包里出现**明显不该出现的内容**（礼包、月卡、货币被摆上货架）。
  链路能跑通，所以容易被归为"小问题"而长期挂着。
- 原因：离线补丁常写一个"造数据"函数同时喂两个入口，筛选条件取了两边的**并集**（或干脆按宽口径）。
  但两边合理内容其实不同：NPC 商店卖消耗品，玩家货架只该摆"商品"。
- 排查：**去配置表找权威对应关系**，别凭字段类型猜。
  例：本项目 `reptGoodsNpc` 列的是"顾客会买的 70 件商品"，一查全是 `iItemType == 5` —— 这就定义了"商品"。
- 修法：给种子函数加**口径开关**（如 `onlyGoods`），**只改有问题的那一侧**，
  已验证过的另一侧保持原样，避免把修 bug 变成回归。
- 附带教训：**改了函数签名或调用行，要顺手搜一遍断言/测试里有没有写死旧签名的**，
  否则补丁会以"断言失败"的形式报出来（这次连中两条）。

**同一行数据被多个消费方用不同字段名读取，某处算术/取值崩在 nil**
- 原因：反编译产物里同一个数据结构在不同 UI 里读法不一致（旧命名 `iItemID`/`iCount`
  vs 新命名 `iItemId`/`iItemCount`）。伪造数据行只满足了一边，另一边拿到 nil，
  报错形如 `attempt to perform arithmetic on field 'iItemCount' (a nil value)`。
- 排查：拿到报错的文件行号，去那一行看它读的字段名；再全量搜**同一份数据**的其它消费方，
  列出所有用到的字段别名。
- 修法：**伪造行把所有别名都写上**（`row.iItemID` + `row.iItemId`、`row.iCount` + `row.iItemCount`）。
  多余字段对 Lua table 无副作用，漏一个就有一处 UI 挂掉。
- 实例：案例 A `OfflineEF_ShopGoods` 只给 `iItemID`/`iCount`（NPC 商店读法），
  `RetailPanel`/`StoreGoodsItem` 读 `iItemId`/`iItemCount`，一开店面板就报错。

**点击完全没反应，但日志里连请求都没有（静默 gate）**
- 原因：交互函数里有一个**不报错的边界判断**直接 return，常见是容量/上限/数量判断，
  如 `if (not (itemTotalCount >= self.totalCapacity)) then ... end`。
  离线种子把数量堆到超过上限（`50 x 999 = 49950` vs `iMaxStorage = 1580`），
  于是后续所有点击都被这个分支吞掉。
- 排查：搜该交互函数名，逐条看它开头的提前 return；同时**去看 UI 上自己的数字**
  （容量条、计数、进度）——超限往往就写在界面上，只是不显眼。
- 修法：种子数量必须**尊重界面自己展示的上限**（读配置表的上限字段，别用拍脑袋的大数）；
  需要「给足」时就贴着上限给，不要突破。
- 实例：案例 A 的货架容量条显示 `49950/1580`，`OnClickWarehouseItem` 因此静默挡死上架。

**自造的数值字段（战力/属性/评分）只满足分支条件，丢掉了成长维度**
- 原因：原版这类字段由**服务器算好下发**（如卡牌 `stPropInfo`）。离线补丁只能自己造，
  常见做法是拿配置表里的基础值乘一个显眼因子（典型 `基础值 × 星级`），
  而客户端里其实**已经有一份权威算法**（如 `CommonFuncion:GetCardAttribute`）。
  自己手搓的版本漏掉等级、突破、加成等任一维，数值表面上「看起来正常」，成长链却是断的。
- 症状：玩家升级/突破/强化**照扣材料、数字照涨，战力一点不动**；或反过来，数值虚高到门槛毫无意义。
- 排查：先在反编译代码里搜这个字段的读取方，再搜客户端**自己**算它的函数（往往用在对比/预览 UI 上），
  两者对照就能看出漏了哪几项。
- 修法：**照搬客户端权威公式**，把输入的每个维度都接上；然后拿配置表离线算出理论上限，
  和关卡门槛比一次（上限 ≪ 门槛 → 公式漏项；上限 ≫ 门槛 → 门槛形同虚设）。
- 实例：案例 A 的剧情战斗要求 1650 / 5250，离线公式只有「卡面×星级」，
  满星上限 1550 / 1500 → 怎么练都过不去；补回等级项与突破加成后上限 52005。
  客户端公式：`floor(0.01 × 卡面 × param) + 突破加成`，`param = (iAbilParam + lvl×250/(lvl+250)) × (1 + star/4)`。
- 附带教训：**别急着下「门槛太高、玩家会被卡死」的结论**。先确认成长链是通的，
  否则会把「公式漏项」误判成「设计不合理」，进而去做错误的下调门槛。

**"服务器推过来"的玩法（随机事件、报恩、通知类）：先找谁打开那个面板**
- 做法：从请求名 / 通知名搜到 manager 的回调，再到 model 存到哪张表，再搜谁读这张表、谁 `ShowPanel`。只看面板代码会走偏：客户端里留着从来没人打开的旧面板（案例 A 的 `<宠物互动面板>` 有一整套"摸宠物找惊喜"逻辑，全工程没有一处打开它；真正在用的是后院气泡 → `<宠物事件面板>`）。
- 触发规则在服务器上查不到时：定一条离线规则，写进代码注释和用户文档，标明"离线版定的"；规则里的数（概率、次数）单独列成常量。
- 定规则时先拿配置做统计找线索（案例 A 2026-10-18 的店头纸条）：客户端只有请求号和回包字段，看不出触发条件。统计商品表里各商品指向的纸条池，70 个里有 59 个指向普通池，于是定成「每个游戏日第一次卖货结算时，出一张还没得过的普通纸条」；纸条挂在店上直到被读，关闭详情时才记入存档。
- 面板关掉时只发界面内通知、靠另一个界面元素接着发请求的（这里是后院里那只宠物），元素不在场就没人接：在 model 的通知函数后面加一个兜底调用，处理函数自己保证只发一次奖励。

**"获得 XX"的通知弹窗数错（套装已收集 0/3）**
- 原因：弹窗读的是 model 里某一类的已有列表，这张表要先收到"整页数据"的回包才有；这次登录没进过那个页面时是空的。
- 修法：发通知前先按"得到之前"的样子把整页数据灌一次（注意别顺手把页面打开：先把 manager 上"收到数据就开面板"的开关关掉再灌），再记账、再发通知。顺便核对整页数据里有没有漏掉的类别（这里漏了宠物收藏 104，收藏界面里永远看不到）。

**把"结算用的数"显示到界面上，会照出结算函数的老毛病**
- 症状：让情报页的"总实力"改用结算同一个函数后，17 级的档显示 20144（应为 10342）。
- 原因：结算函数靠遍历顺序去重（"先遇到链头就把后面的步骤标成已算"），步骤表的顺序不固定，后面的步骤排在前面时整条链被算了两遍。以前结算数字只进日志，没人看见。
- 修法：先扫一遍找出"排在别的步骤后面"的步骤，只从链头算。教训：界面和结算各算各的时候，先让界面显示结算的数，再看数字合不合理。

**规则有好几种条件，本地只判了一种，其余等于全放行**
- 症状：某类关卡 / 功能新档一进去就全开；高阶材料随便刷，后面章节的门槛形同虚设。玩到高等级的测试档看不出来，因为它本来就满足条件。
- 原因：原版解锁表里有「先通过某一关 / 主角等级 / 好感等级」几种条件，本地实现只写了其中一种，遇到不认识的条件类型就返回"已解锁"。
- 修法：写解锁判断前先把表里实际出现的条件类型数一遍（按类型分组计数），每种都实现；不认识的类型默认**锁住并打日志**，不要默认放行。验证必须用全新档。
- 同类：上限公式要先看存的是什么。突破等级存的是 0 / 10 / 20，按"突破了几次"去乘就算出一个离谱的上限。

**奖励串里的"类型"没分发，全当成道具塞进仓库**
- 症状：奖励写着"店铺知名度 100"，领了不涨；好感、藏品类奖励领了不见。
- 原因：奖励格式是 `类型;编号;数量`，类型不同去处不同（道具 / 货币 / 店铺知名度 / 好感 / 藏品…）。本地入账函数只认道具。
- 修法：入账函数按类型分发；先在全部配置表里统计奖励串出现过哪些类型，逐个确定去处，没处理的类型打日志而不是静默入仓。

**原版"先发请求、紧接着改标记"，离线同步回包后标记卡死**
- 症状：某个按钮第一次点正常，第二次点没反应或状态不对；注入式自测全过。
- 原因（我的推断，和"同一帧销毁再重建"是同一类）：联网时回包晚几帧到，处理函数运行时标记已经置好；离线回包在发送函数内部就同步处理完了，随后才执行"置标记"那一行，标记留在"等待中"。自测直接调处理函数，不走客户端的发送函数，所以抓不到。
- 修法：静态扫一遍"调完 Send 立刻赋值"的写法，逐处判断；新接的功能在界面上把同一种操作至少连点两次。
**离线同步回包撞上客户端的三类时序假设（计数门闩 / 界面未就绪 / 预扣）（案例 A 多次）**
- 原版回包走网络、晚几帧才到，客户端为此埋了三类假设，离线同步回包会一一踩中：
  1. **「等 N 个回包」的计数门闩**：面板 onInit 发两个请求、各回包 `count--`，减到 0 才开面板（案例 A 商店 `transactionPanelReqCount`、`ShoppingManager`）。同步回包时第二个请求还没发，第一个已经把 count 处理完；更坏的是「发完再 count++」的写法会先减成 -1 再加回 0，永远不等于 0。修法：所有请求发完之后补一次判断，count 为 0 且面板没开就在这里开。凡是「等多条回包」的入口都按这个查。
  2. **界面状态没就绪，回包被忽略或被随后覆盖**：上架、速度查询、热卖结算点了界面不刷新。修法：用游戏调度器把回包延迟 0.15~0.6 秒（封成 `V3_Later(sec, fn)`：`LuaScheduler.delay` 挂当前 UI 的 gameObject）；战斗结算等战斗面板关闭后再回。
  3. **客户端已本地预扣，服务器又扣一次**：工坊做 1 个扣了 20（应为 10）。修法：处理请求先查面板的「已发送」标志（如 `mIsSendMakeFormationBtn`），预扣过就先把预扣的加回、再由服务器统一扣一次；失败路径把加回的再扣回。
  4. **界面搭建时就读的数据，恢复晚了就对不上**（2026-10-13~18）：有三种表现。后院按屏列表的顺序算位置和滚动范围，离线模块却在面板搭好后才恢复已解锁的屏，重启后点页签画面不动。某角色页的离线回包早于面板设好角色数据，一打开就报 nil，列表几乎是空的。原版靠服务器主动推送灌进 Model 的数据（如已得纸条），离线后没人发，面板每次打开都是空的。修法：恢复存档里的解锁态，放在面板搭建之前做（进入该界面那条请求的应答里），不要事后补刷；要用到面板数据的回包，延后到面板初始化之后再处理；没人发的推送，在 Model / 面板初始化处挂钩，用原版的解析函数（如 `Parse...Rsp`）把存档内容灌进去。
- 通用：接任何「发请求 → 等回包」的功能前，先读客户端这三处：有没有计数门闩、有没有在回包前切界面状态、有没有本地预扣。

**离线客户端的「服务器时间」恒为 0，限时活动永远不开（案例 A）**
- 症状：限时活动判断开没开拿到的当前时间是 0，活动永远不开；主线进度模型值也可能恒 0，男主个人剧情全判成「主线没走到」。
- 原因：离线版从不向服务器校时，`GetCurrentServerTime()` 一直返回 0；同理 `MainStoryModel` 的当前章 / 当前节也没人写。
- 修法：登录后主动校一次时（本游戏 `GufengxGameSystem.Instance:SyncServerTime(os.time())`），再下发本地构造的活动通知列表（`GET_ACTIVE_NOTICES`）。进度字段用「原值与按任务链推算值取较大者」补（包装 `GetCurSectionID` / `GetCurChapterID`）。校时后要回归所有读服务器时间的界面（对话、交易、换装、茶楼……）。
- 怎么确认的：注入探针读到时间 / 进度为 0，调用校时 / 包装后连读正常。

**自造的完成判定 / 已读 / 已领状态，要对照客户端的计数函数和提示文案，别按字面当单条处理（案例 B/C）**
- 几种一类的坑：
  - 红点 / 图鉴完成条件只查主件：只拥有套装里一件衣服，图鉴奖励就亮红点可领。服务器 `suitCheck` 只查 `mainPart`，但客户端 `getSuitOwnCount` 要求 `partItems` 全拥有（builtin 件跳过）。改成和客户端计数一致；登录时清掉未集齐套装的旧红点，已领不收回。原版规则查不到就按客户端提示文案（如提示 4019「收集完成可领取」）推断并标 `[推断]`。
  - 客户端进某页只发「第一条编号」表示整页已读（案例 C 手札总录 / 大事记、uiboyletters）：离线服务器只标那一条 → 每次进游戏又显示未读。改成按页（类型）整页标记已读。
  - 回包里「已领档位」列表被填成一串 0：界面认不出，日常宝箱领完还显示可领、能反复点。按真实档位写并持久化。
- 通用：伪造「状态类」字段前，去客户端 Model / 面板读它到底怎么用这个值（计数函数、提示语、「记录必须先存在才 +1」的前置行），不要按字面只处理一条。

**按分类过滤发放时漏掉另一类物品（案例 B）**

**复活收集类玩法：先看发送函数是不是空桩、客户端按什么键匹配、编号会不会和别的系统撞（案例 A 2026-10-18）**

- 怎么确认的：改后送礼升级，弹窗显示的前后等级正确。

**奖励发错类：没按游戏自带说明分类，或只改了掉落、漏了共用的阶段奖励表（案例 B 2026-11-06~07）**
- 症状：玩家反馈四类委托的奖励全是升星材料；改了每关掉落之后，还是不对。
- 原因：离线代码给四类委托统一发升星材料，没照物品说明和界面文案区分。改完掉落后，四类共用的那张星级阶段奖励表里仍然全是升星材料。
- 修法：先在文案表里查各类奖励原本应该是什么（物品说明 `items_desc_*`、界面说明），再把每关掉落和阶段奖励表一起按类拆开改。原版发的材料在离线版里用不上时（衣服已经能直接买），换成玩家用得上的东西，并写明是改过的。原版界面已有、只缺服务端逻辑的（合成），补上数量判断和扣料。
- 怎么确认的：模拟器上各类委托的奖励预览和说明对得上；凑齐材料合成后，衣服解锁，材料按量扣除。

## 随机与异步

**十连后崩溃（`SIGSEGV`）**
- 原因：本地抽卡与原版动画流程的交互（未完全定位）
- 修法：未根治。抽卡是最高风险点，任何相关改动都要做完整回归（单抽→十连→返回→重进→重启）

**按时间排序的测试偶发失败：两次操作落在同一毫秒（案例 B 2026-10-20）**
- 症状：通话测试单独跑能过，放进回归循环里偶尔失败。
- 原因：两通电话在同一毫秒被「接听」，按接听时间排序时出现平局；真实使用中不会发生。
- 修法：测试里用受控时钟，不用真实时间。
- 怎么确认的：换成受控时钟后连跑 8 次全过。

## 工程与文档

**文档自相矛盾，新 Agent 按旧文档走错路**
- 原因：多份文档各自演化；构建脚本存在新旧两套，旧的仍留在推荐路径上
- 修法：定一份"当前事实源"，其余文档指向它；废弃脚本明确标注，不要让它出现在推荐流程里
- 2026-11-02 补：旧探索文档里的数字（件数、来源、价格）也会过期。要交给用户拍板的数字，先用脚本从配置表和代码里逐条列出来，再下结论；旧文档只当线索，发现矛盾要在回复里明说更正（案例 A：一份旧文档说「原版没写来源的有 12 件」，逐条核对后只有 2 件）。

**手工修在产物里的补丁丢失**
- 原因：改动只落在 APK / bundle / 解包目录，没回到补丁脚本
- 修法：产物一律视为可再生；定期核对临时脚本是否已合并进主入口，确认后删除或纳入

**未提交改动被误清理**
- 原因：脏工作区 + 清理脚本
- 修法：清理前先看 `git status`；禁止 `git reset --hard` / `git checkout -- .` / `git clean`

**交付包不能自证基线 → 装了旧包才发现改动没进去**
- 原因：产物目录里堆着多个历史包，包名只带时间戳；构建清单不记录策略开关（如门禁 bypass、
  各调试旋钮），于是"哪个包是哪个配置"不可考。本轮实测：真正要装的"最新改动 + 默认策略"包
  根本不存在，只有"最新改动 + 实验策略"和"旧改动 + 默认策略"两种，光看目录判断不出来。
- 修法：把**策略注入值写进构建清单**（manifest 记 `gate_bypass` 之类的开关取值）；发/装之前先比
  「包构建时间 vs 最近改动时间」；交接文档里把"**重新出包**"写成第一步，别写"直接装某个现成的包"。

**支线/实验收尾必须回到默认基线并重签**
- 原因：为验证某个开关（门禁、封锁、调试旋钮）临时改了策略文件，验证完忘了改回来，
  之后每个包都带着实验配置，而清单里看不出来。
- 修法：支线停放时显式恢复 `policy.json` 一类策略文件的默认值、重签签名文件、并重出一版默认包；
  在快照里写明"现为默认值 X，行为等同做该支线之前"。

**交接要给"第一件必做事"，不是给一堆背景**
- 原因：新 Agent 没有会话记忆，只凭文档判断"现在该干嘛"，于是最容易在第一步就装错包 / 走旧链路。
- 修法：写一份**可直接复制**的接力提示文件（基线时间戳 + 第一步命令 + 硬纪律 + 指向压缩快照），
  用显式"复制开始/结束"标记包裹，别用嵌套代码块（复制时容易截断）。

**两个会话同时改同一个仓库，互相重做、互相覆盖**
- 症状：一边修好的系统级问题另一边没有；同一个共享文件出现两种改法；一边的包把另一边的设备状态弄乱。
- 修法（案例 A 2026-10-13 的做法）：
  1. 每条线一个 git worktree、一条分支；构建目录、日志、存档各用各的，只读输入用目录联接共享。
  2. 每条线一台设备（真机 / 模拟器），模拟器走单独的 adb 服务端口，让两边互相看不见对方的设备。
  3. 按"谁拥有哪些文件"分工：一条线拥有共享主体文件和发布包；另一条线只写自己的模块文件，在主入口里只加登记行。
  4. 共享代码里发现的 bug 用一条消息告诉拥有方，由拥有方核实后修；另一方只合并，不重做。合并方向固定（发布线 → 探索线）。
  5. 探索线的模块要进发布包，由发布线自己拿、自己在发布设备上验证；"在模拟器上过了"不算发布线的验证。
- 接手时先看两边的 `git log` 和各自的总览文档，再回答"现在做到哪了"；只读一边的快照会漏掉另一边一半的事实。

**"章节打通了"被当成"可以发了"**
- 回答"是不是彻底完成"要分开四件事，各自要有证据：① 内容：全新档按玩家顺序打到终点（哪个包、哪份报告）；② 修复：每条修复在**最终那个包**上复验过，不是在修它的那个中间包上；③ 交付物：正式包重新打过、哈希记下、已装到用户的正式安装、对外副本目录是同一个哈希；④ 发布卫生：调试开关、注入后门、未开放内容是否还在包里。
- 常见的假完成：章节在候选包上通关 → 之后又修了十几处 → 用户设备上和对外目录里还是旧包。

**正式包悄悄带着开发包的东西发出去（案例 A 2026-10-14、10-20）**
- 症状：加了 `--final` 打出来的包里仍然带着 Frida gadget（监听本机端口的调试后门）；另一次，正式包里的开发开关 `OFFLINE_V3_DEV` 还是 true，构建清单却写着已关闭。
- 原因：构建脚本不区分开发包和正式包，无条件把调试通道打进去；`--skip-patch` 复用了上一次开发构建打过补丁的 Lua，正式模式下设置发布标记的补丁步骤被跳过了。
- 修法：正式构建时换回原包的 classes.dex，不带 gadget 库，并在末尾自检（包内没有 gadget 条目、dex 里没有加载行、清单写明 `debug_gadget:false`）；`--final` 和 `--skip-patch` 同时出现就直接退出；发包前从包里解出 Lua 核对开关值，不信清单。去掉调试通道后，用正式包做的分身在真机上启动并玩一段，证明能正常运行。
- 怎么确认的：对比两份 classes.dex，类、方法、字段数完全一样，字符串表只多一条 `frida-gadget`；解出正式包里打过补丁的 Lua，看到开关为 true，带上补丁步骤重打后变成 false。

**后台构建开始之后改的代码，不在这次的包里（案例 A 2026-10-30）**
- 症状：打包期间继续改代码，打出来的包缺了最新的修复。
- 原因：构建读的是启动那一刻的源码。
- 修法：改完代码先看有没有后台构建在跑，有就停掉重打；先在开发包或分身上验，再打正式包。

**构建日志里写着签名证书密码的明文（案例 B 2026-10-20）**
- 症状：正式包打完，日志里的签名命令行带着 `--ks-pass pass:<明文>`，日志可能被归档、分享，甚至被提交。
- 原因：构建脚本把完整命令行原样打印，并写进了日志。
- 修法：打印前把密码替换成 `pass:***`，只改打印出来的那份，传给子进程的参数不变。失败时 assert 的报错信息里也带着命令行，同样要脱敏。打完包后 grep 日志目录和工具目录，完整密码和前几位都要搜不到。把这一项加进发包检查，手册里的「外发前人工抹密码」改成「已自动脱敏」。已经写出去的旧日志，批量改成 `pass:***`。如果用 sed 改，它会把 CRLF 变成 LF（见「批量改 CRLF 源文件后换行变 LF」），改完要用 Python 数 CR / LF 字节，确认每个文件只有密码那一行不同。

**出正式包的后台任务被会话结束或机器重启打断，留下半成品（案例 B 2026-11-03）**
- 症状：出包停在签名阶段，后台任务显示已停止，机器当天还重启过。
- 原因：会话结束时后台任务被一起终止，加上内存不足和重启。
- 修法：复工时先看中断留下了什么，把半成品挪到别的目录（不删）。确认内存和磁盘够用后，用同样的命令重出。比对源码指纹，和半成品一致才沿用之前的回归结果。

## 方向误判（最贵的错误）

**长时间调不通某个注入 / 加载机制，认定卡点就在这里**
- 原因：真正的阻塞在别处。运行时看不到"某个分支永远不会触发"这类事实
- 修法：**先把上一阶段留下的日志读完，再动手调。**
- 实例：前一阶段花了大量时间调 Frida Gadget 自动脚本模式。后来读 logcat 才发现，卡点是另一个"8 秒后弹窗盖住画面"的强制跳转，而它的触发条件（`sendCount >= 3`）在整份日志里永远不可能满足——**即使 Gadget 修好也照样进不去**

**越依赖运行时探针，效率越低**
- 原因：注入类工具对 C# 对象遍历不稳定、反复超时，会话越长越容易失败
- 修法：运行时只用来**生成假设**；关键结论用静态方式复核（在包里查字符串、比对文件内容）

**把侦察工具当成交付方案**
- 原因：注入方案在调试机上"能跑"，但验收标准要求"不 root、不用电脑、只装 APK"
- 修法：明确区分阶段。侦察用什么工具都行；交付必须落到包内改写。不要在让注入方案"跑通"上继续投入

**功能"没有反应"其实是被离线补丁主动关掉的（用一个哨兵值关掉整块功能）**
- 症状：某个系统（新手引导、活动、限时玩法）在游戏里**完全看不到、也不触发**，
  既不报错也不卡——因为它根本没被调用。
- 排查：不要只搜"这个功能怎么实现"，**先搜它是怎么被关的**。离线补丁为了让流程跑通，
  常会写下类似 `_G.OFFLINE_DISABLE_XXX = true` 的总闸，或者给状态字段灌一个哨兵值
  （如 `guideFlag = -1`）让 `IsXXX()` 直接走"已完成/已跳过"分支。
- 实例：案例 A 的离线版用 `_G.OFFLINE_DISABLE_GUIDES = true` + `ng.guideFlag = -1` 关掉了整条
  新手引导链。关键在 `IsGuided()` 的写法：**对负数一律 `return true`**，
  于是"标记为 -1"等于"所有引导都已完成"，一行就把 18 组引导全部静默关闭。
- 教训：**看到 `= -1` / `= 999` 这类哨兵值，先确认下游对它的处理是不是"全放行/全跳过"**。
  想恢复时，先把它改成"读存档/默认值"，再补上本地持久化，别直接改回 0 就完事。

**全屏引导遮罩在离线/模拟环境必然吞点击 —— 要分层处理**

- 症状：引导一开，底部导航/返回按钮全部点不动，只能停在某一个界面；日志里点击只报
  `Button On Click empty`（打在遮罩自己身上）。
- 原因：引导遮罩通常有**两层**：视觉提示层（高亮、手指动画）和**点击屏蔽层**
  （全屏 Raycast 组件 `Empty4Raycast`、以及 prefab 里的 `btn_xxxMaskBg` 这类全屏按钮）。
  原版靠点击屏蔽强制玩家只能点目标；离线版一旦有某步等不到服务器事件，屏蔽层就永远不撤。
- 修法：**保留视觉提示，拆掉点击屏蔽**——不要为了"安全"把整个引导关掉。
  实测两处注入点即可：挡住组件创建（`AddComponent(typeof(T_Empty4Raycast))` 那行）+
  让遮罩按钮永不激活（`SetActive(false)`）。这样引导能照常提示，导航永远不会被吞。
- 判断是否修好：点一个底部导航按钮，日志里应出现**真实按钮事件**
  （`Button On Click:<按钮名> instanceID:...`）而不是 `Button On Click empty`。

**新手指引在离线版被悄悄跳过 / 卡死的几种原因（案例 A，逐条真机复现）**
- 看门狗误判：转场黑屏期间的点击、以及点别的弹窗（`promptType ≠ 1000`）的点击都被计进「点了没反应」次数，指引刚出现就被强制结束。修法：手指晚出现时重置看门狗计时和点击数；当前有别的弹窗在显示时点击不计入；强制结束要同时关指引视图（`ctx:Finish(true)` → `FinishCurGuide()` → `CloseGuideFinger(true)`），否则留幽灵气泡。
- 「新功能开启」弹窗只弹一次：功能格子默认隐藏、靠弹窗播放后才亮；离线版限制成全局只弹一次，后续解锁的按钮一直藏着、指引找不到目标就自动结束并记成已完成。修法：按每个解锁按钮单独记「已看过」键，只播没看过的（已看过的从字典移除并直接 `SetActive(true)`）；日志打 `unlock popup: N new of M -> show`。
- 高亮目标在非主页签上算到屏幕外（>3000）：原版强制手指在目标离屏 / 不可见时结束并标已完成。修法：指引只在主页签开始、登录后轮询检查；目标曾被放到屏幕外时重新摆放而不是结束；地图 / 英雄页上指引层抬到最上并同步移动嵌套画布，归还目标时恢复原缩放。
- 离线绕过了原版弹窗（如抽卡确认框）：指引等的事件没人发 → 卡住。修法：离线绕过弹窗的地方补发指引在等的事件。
- 同步回包的时序：业务事件（编号 ≥100）比指引早到、点击事件比回包晚到，会丢步或多跳一步。修法：步骤开始前 2 秒内到达的业务事件在步骤开始时补发；同一帧内已被业务事件推进的，吞掉随后的按钮点击。
- 通用：指引走查用「补丁内置每步日志（guide / step / 等待事件 / 目标名@坐标 / 手指位置 / 遮罩状态）+ 脚本按手指实际位置点屏幕」驱动，不要往运行中的游戏注入 Lua（会和主线程抢虚拟机 SIGSEGV），人工盲点也会误触看门狗。

**补数据之前先查界面有没有入口：客户端里有「孤儿」面板和原版死代码（案例 A 2026-10-18~19）**
- 症状：后端已经把 CG、两类收藏的数据接好了，玩家却看不到；用户找不到某个功能的入口；原版功能清单里有几项一直没接上。
- 原因：终版客户端里有一个旧面板（CG 相册、玩具、收藏），已经没有任何地方会打开它。注入强行打开后，一个页是空按钮加「敬请期待」，CG 相册是空格子，配置里 47 条 CG 用的是同一张占位图。另有几项是原版开发时就砍掉的：查询函数是空的、没有调用方，或者原版处理函数本身就报错。
- 修法：补「藏品 / 奖励 / 功能」类内容之前，先 grep 谁会打开这个面板，再注入强行打开，看内容是不是占位。孤儿面板只做数据和存档，不要硬加入口，文档里写明「数据已通、界面不可见」；死代码不投入实现。把「查过、不需要做」的原因写进文档，免得下一个会话重复调研。

## 复活下线活动的皮肤（美术分层藏，别急着说丢了）

**说"这个活动只剩最后一版皮 / 美术丢了"之前，先把同名资源在各层包里比一遍**
- 背景：下线活动在终版客户端里往往只显示最后一期的皮肤，容易让人以为"其它期的美术随服务器一起没了"。其实换皮常常分层藏着，不是真丢。
- 要比的三处：① 热更包里的普通面板；② **同一热更包里的 `rep/*`（复刻）预制**——它和普通面板常带一批同名贴图，但 **path ID 不同**，是另一套皮；③ **原始安装包里的同名 bundle**——它可能在打包时被热更整包覆盖，里面还藏着一版。三处各导出同名贴图（`xxx_bg_01` / `xxx_title_01` 这类）逐一比对。
- 判据：同名贴图在不同包 / 不同 path ID 下存在不止一个版本 = 还有别的皮，没丢。
- 实例（案例 A）：一个抽取类活动一度被我判成"只有一版皮"，用户坚持"每个角色都有自己的样子、当年全解包过"，结果是对的——最后找齐三套：金色皮在热更普通面板、蓝色皮（复刻）在同包 `rep/*`、粉色皮在被热更盖掉的原始 APK bundle 里。
- 教训：**用户说"以前见过 / 解包过"时，先去各层包里找，再下结论。** 这类"美术还在、只是终版没登记或被覆盖"的被埋没内容，和"拿配置清单对镜像做差集"（见 `SKILL.md` 第 8 步）是同一类抢救。

**要发被热更 / 构建覆盖掉的那版皮：另存一份包 + 运行时按节点路径把真图拷上去，别用染色凑**
- 发法：把原始 APK 里被覆盖的那个 bundle 复制出来、**改掉 CAB 名**放到单独路径（案例 A：`assets/AssetBundles/Android/v3skin/<皮肤包>`，由 `tools/skin_bundles.py` 在构建期生成），运行时 `AssetBundle.LoadFromFile(...)` 加载，按**节点路径**把 Image / RawImage 的 sprite、贴图、尺寸、文字颜色拷到活着的预制上；切到别的皮时把拷过的东西复原。
- 选皮入口：hook 活动模型里决定"显示哪个面板"的方法（案例 A 是 `<活动>Model:IsShowFirstPanel` / `IsRestartCard`；原版靠 `ComActivityModel.RestartCardList` / `UseFirstAgain` 里的 `ShowPanelIndex` 定皮）。
- 坑一：**不要对"游戏自己稍后还要加载的那个 bundle"调 `LoadFromFile`**——会让游戏自己的加载报 "panel prefab missing"。要发的那版必须是改了 CAB 名的独立副本。
- 坑二：**染色不是换皮。** 按主题色正片叠底效果发闷（用户原话"太阴间"）；`Unlit/Gray` 不认颜色、`Graphics.Blit` 配 UI shader 渲染成黑、`GL.Color` / `DrawTexture` 不可用。真皮的美术在，就用真皮，别拿颜色凑。
- 坑三：注入一大段 Lua（约 18 KB）会把模拟器 Unity 线程冻住；调这种皮肤补丁要**打一个 dev APK** 装着测，别靠注入。

**热更包会整包替换 APK 里的同名资源包：照 APK 清单标的「有图」会失真（案例 A 2026-10-20）**
- 症状：几个复活活动的主界面入口报 `Error LoadSprite null ui/activity ActivityEntrance_<活动号>`，补丁表里明明标了有图。
- 原因：构建合并资源时，手机热更的 `ui/activity` 会整包替换 APK 里的同名包，而不是按文件合并。APK 里有这几期的入口图，热更那份没有，合并后就丢了。「有图」的标记是照 APK 清单标的。
- 修法：以合并后实际生效的资源为准来核对（用 UnityPy 分别读两份；热更文件前有 8 字节前缀，要先切掉）。缺图的期在加载处加别名兜底：用锚点把原版两处拼 `ActivityEntrance_<号>` 的地方改成先问一个别名函数，模块没加载时走原逻辑。挑别名时先导出全部入口图拼成总览图来挑；复刻期和原期活动名完全相同的，直接借原期的图。构建期自检读热更包，断言每个别名目标都存在、标记与实际一致、每个无图的期都有别名。
- 已知副作用：入口图是整张烘焙好的，借来的图带着原活动的标题文字，尺寸也可能不一样（偏大时会压到旁边的入口），要如实告诉用户；真要改，只能往资源包里加新图。
- 怎么确认的：在开发包上分别打开这几期，热刷新和冷启动都能看到入口图，logcat 里 LoadSprite null 为 0。

## 游戏内 UI / 弹窗

**自己弹一个对话框，结果是一块空白白框（没文字、没按钮图案）**
- 原因：绕过游戏 UI 框架，直接用 `AnimatedPopLayout` / `PopUtils` 加载裸 prefab
  （典型 `prefab/ui/dialog_common_msg`）。prefab 里的 `Text.font` 是 `nil`、按钮贴图依赖主题/皮肤 bundle，
  离线流程没走那套 UI 初始化，于是只剩默认白底。
- 排查：加载后用 `GetComponentsInChildren(typeof(Text))` 打印每个 Text 的
  `name / activeInHierarchy / font / text`。`font=nil` 基本就确认是没走原生对话框/皮肤。
- 修法：**优先用游戏原生的对话框 API**，不要自己拼 prefab。在 il2cpp `dump.cs` 里查 `DialogUtils`
  的静态方法；Unity Lua 侧通常是 `GameNS.<框架>.PopPanel.DialogUtils`：
  - 双选项（自定义按钮文字 + 两个回调）：`ShowTxtDialogCustom(txt, mode, confirmCb, confirmText,
    cancelCb, cancelText, isSystemDialog, isBlurBg, tweenFinishCb, title)`
  - 单按钮确认：`ShowConfirmDialog(txt, mode, confirmCb, isSystemDialog, isBlurBg, tweenFinishCb, title)`
  - 单按钮 + 取消回调：`ShowTxtDialog(txt, mode, confirmCb, cancelCb, isSystemDialog, isBlurBg, tweenFinishCb)`
  这些接口自带主题、字体与按钮，不需要自己注入字体。
- 实例：案例 A 的新玩家开局「等级 / 资源 / 解锁」三步选择，第一版裸 prefab 渲染成空白白框，
  改成 `ShowTxtDialogCustom` 后文字、双按钮、主题全部正常。

**富文本加粗把字糊成一团（案例 C 2026-11-01）**
- 症状：启动声明框里用 `<b>` 加粗的红字，笔画粘在一起，反而看不清。
- 原因：游戏字体加粗后字形粘连。
- 修法：只用 `<color=#...>` 上色，不加粗；文本组件要开 `supportRichText = true`；每句控制在一行以内，并截图确认。
**战斗 / 调查结算要点两下才进下一步：看不见的跳过按钮吞了第一下点击（案例 A）**
- 症状：结算界面第一下点击没反应，要点两下；第三下还会误点到下面的关卡。worker 曾误报成「战斗结算触发了两次」。
- 原因：战斗面板上有个不可见的 `btn_skip`，结算后仍可点，走了 skip 分支吞掉第一下点击。
- 修法：战斗一结算就把 `FightingTemplatePanel.Instance.btn_skip` 隐藏（在两个本地战斗结算函数 `FinishLevelFight` / `FinishBackFight` 开头调用）；或给 `SkipOnClick` 打补丁，结算状态下的跳过等同于点结果按钮。
- 怎么确认的：在结算页对着时间戳逐一核对收到点击的控件，发现落在 skip 身上。

**带内嵌图标的原版确认框在离线版软锁，是没装图标加载器（案例 A）**
- 症状：抽卡券为 0 时点十连毫无反应，日志有 `NullReference`，一个不可见的确认框吞掉所有点击。
- 原因：原版这里弹「用货币补买」对话框，文字里有内嵌图标，需要 `LinkImageText.funLoadSprite`。离线版没装这个加载器，`tryGetSprite` 抛空，对话框半开着挡住点击。
- 修法：登录时给 `LinkImageText.funLoadSprite` 装上图标加载函数（`CommonLoadIcon.LoadLinkImageTextSprite`）。装上后补买对话框正常弹出，流程走通。

**强制阅读 / 教程弹窗别靠计时，要看真实滚动并在设备上截图验证（案例 C）**
- 症状：新装后首次说明页按钮上没有倒计时、点一下就直接关了。
- 原因：面板在加载画面后面就已经打开并开始倒计时，玩家看到时早走完；而且找不到标准 `ScrollRect`，「滑到底」检测退回成只计时。
- 修法：用面板局部坐标看正文被拖动了多少，滑过大半才解锁（用局部坐标避免打开动画被算成滚动）；没滑到时显示提示。强制阅读类弹窗一律在真机上截图验证「没滑到不解锁、滑到底才解锁」。

**确认框点空白处会触发「取消」回调，自选翻页按钮不能放在取消键上（案例 C）**
- 做自选 / 翻页弹窗（一页一个条目，按钮「开这个 / 下一个」）时：若用普通确认框，点空白会走「取消」回调把框关掉，「下一个」若复用取消键就关不掉。要用带 `directExit` 参数、点空白直接关闭的那种确认框；「下一个」单独做一个按钮，翻页时延迟 0.3 秒再开下一页（同一帧开会叠）。

**主线走到原版最后的占位任务，任务条显示策划的玩笑话和「(0/1)」（案例 A 2026-10-18）**
- 症状：主线全部走完后，停在原版最后一条任务上（要求等级 999，没有下一任务）。任务条显示原版的调侃文案加「(0/1)」，任务面板的目标行还有另一个「(0/1)」。
- 原因：任务条总是用配置行的文字加「(当前/最大)」；面板目标行由另一个组件渲染，和主界面任务条不是同一套代码。
- 修法：把「没有下一任务」的任务认作终点，在构建任务信息时只改显示文字，任务数据不动，这样已经停在终点的旧存档下次登录就能生效。面板那个组件也要补上，并且只在文字恰好等于完结语时才去掉进度，免得影响它的其他用处。验收时两处都要看。

**从脚本里主动关掉原版的对白面板，原生层直接崩（案例 A 2026-10-30）**
- 症状：为了不让对白框挡住奖励弹窗，补丁里直接 close 了对白面板，模拟器上随即 SIGSEGV 闪退。
- 原因：原版从来不从脚本里关这个面板，这条路径在原生层会崩。
- 修法：别关面板，改提示队列。包装 `GamePromptMgr.ShowPrompt`：当前提示是对白、队首不是对白、且那个页面开着时，把当前提示置空；离开页面时清掉排队的对白提示，并同步减计数（相关条目：前面的 A queued prompt that cannot show blocks every later dialog）。
- 怎么确认的：同一套操作手点 3 轮，0 次崩溃。

**界面刚打开时按尺寸算缩放，结果接近 0，图被缩到看不见（案例 A 2026-10-30）**
- 症状：静态卡的卡池第一次打开只有底色，切走再切回来才显示卡面。
- 原因：打开的那一刻界面还没排版，按容器尺寸算出的缩放（`GetZoomRate`）接近 0。
- 修法：照动态卡的做法，先异步把图加载完、排好版再显示。

**改了按钮文字，界面上显示的还是原文（Laya，案例 B 2026-10-29）**
- 症状：把设置页一个按钮改了名，点击已经走新逻辑，文字却还是原来的。
- 原因：游戏在绑定事件之后，又按语言表把按钮文字设了一遍，提前改的文字被盖了回去。
- 修法：补丁锚点放在按语言表设文字的那一行之后（`btn_xxx.label = UtilText(...)`），在那里改名、隐藏红点。

## 工具链 / 环境（实测坑）

**Frida 探针从注入线程调用 Unity / 配置表 API 直接把游戏搞崩**
- 症状：`Error: access violation accessing 0x...`，脚本在 `LuaDoString` 那一行炸掉，游戏进程也可能不稳。
- 原因：注入线程不是 Unity 主线程；`CSLTypes.DataTableMgr.getInstance()` 这类会碰 Unity 对象的调用不安全。
- 实测**安全**的调用：`UnityEngine.PlayerPrefs`（读写+Save）、部分纯逻辑单例（`ComUIPanelMgr.GetIntance()`）。
- 修法：探针只做「读结果 / 写 PlayerPrefs」这种轻量动作，把结果落到 `shared_prefs` 再读回来；
  需要读配置表就**离线解包**，别在运行时穿。

**正确姿势：让注入的代码「在主线程上跑」——用游戏的调度器中转（本篇最有价值的一条）**
- 背景：注入工具（Frida 等）的回调跑在**自己的线程**上，直接碰 Unity / 配置表 / UI 必崩或卡死。
  但"只看不敢摸"会让验证退化成猜。
- 解法：注入时**只做一件事——把真正的工作登记给游戏自己的调度器**，让它在主线程执行：
  ```lua
  local holder = {}                       -- tolua 需要 table+function 形式
  local function body()                   -- 这段会在 Unity 主线程跑
    local dt = CSLTypes.DataTableMgr.getInstance()
    -- 这里可以安全地读配置、读/写模型、调游戏自己的业务函数
    GameNS.UnityEngine.PlayerPrefs.SetString('PROBE_OUT', 结果)
    GameNS.UnityEngine.PlayerPrefs.Save()
  end
  -- 关键：第一个参数传 nil！见下方说明
  CSLTypes.LuaScheduler.delay(nil, 0.2, CSLNewfunc(holder, body))
  ```
- **`obj` 参数一定要传 `nil`**。很多调度器的实现是「obj 为空则挂到全局系统对象」，
  例如本项目 `LuaScheduler._getNode(nil)` 会回退到 `LuaFrame.LuaGameSystem.Instance.gameObject`。
  这样外层段落**完全不需要在注入线程上取任何 GameObject**——而"取 GameObject"正是导致
  `access violation` / 游戏进程被杀的主要原因（实测约 1/3 概率崩，且会把游戏带下去）。
  传 nil 后连续多次调用都稳定。
- 反例：写 `CSLTypes.CommonFuncion.GetIntance():GetCurRunUIList().gameObject` 虽然多数时候能过，
  但要在这个不稳定的调用上赌运气，没必要。
- 取结果：写进 `PlayerPrefs`，再从 `shared_prefs` 的 XML 里读回来（跨线程/跨进程都稳）。
- 注意：**外层段落本身仍在注入线程**。`GetCurRunUIList()` 这类取 GameObject 的调用多数时候能过，
  但并非绝对安全（实测会偶发 `access violation`）。要更稳就把"取 go"也放进更早一次调度里，
  或者干脆只调用这个已知可用的取法。
- 收益：用这个方式可以**直接调游戏自己的业务函数做端到端验证**，
  不用辛辛苦苦走 UI（实测用它验证了「卡牌升级 / 突破 → 属性真的上涨 → 落盘」整条链）。
- 纪律：**动了玩家存档要还原**。验证完把临时写入的 prefs 键删掉并重启让种子重建，
  确认关键字段回到原值，再向用户汇报。

**从注入线程调用会「改 UI」的游戏函数 → 游戏整体卡死（比 crash 更阴）**
- 症状：进程还活着、无异常日志、CPU 空闲，但画面定格、点击毫无反应。
  用 `dumpsys gfxinfo <pkg>` 会看到 `Total frames rendered: 0`（正常应是持续增长），`50th percentile` 是个巨大值。
- 触发例：从探针线程直接调 `SomeUI:OnCancel()` / `popLayout:dispose()` 这类会动 Unity UI 对象的方法。
- 平反：这**不是游戏 bug**，重启即恢复。别据此判定"修复把游戏搞坏了"。
- 修法：**交互必须走主线程**。要么用 `adb shell input tap`（走系统输入链路，安全），
  要么只让探针做"读状态"，然后用游戏自己的日志回读判断进度。
- 关键习惯：**游戏自己的 `[TAG]` 日志就是最好的断言器**。驱动交互时每步 grep 日志
  （如 `xxx show step=N` / `xxx completed`）比截图判断可靠得多，也能立刻分辨
  "没推进"到底是"没点中"还是"逻辑错了"。

**离线解配置表：protobuf 描述符 + 数据文件**
- 路子：`analysis/protocols/*.bytes`（FileDescriptorSet）+ `src/phone_data.bytes`，
  用 `google.protobuf.descriptor_pb2 / descriptor_pool / message_factory` 还原 `TAllGameCfg`，再按表名取行。
- 好处：可复现、不依赖设备、可以反复试算（算理论上限、查门槛、对结构）。

**`adb install` 报空错误时改用 push + pm install**
- 症状：`Failed to install xxx.apk: `（原因串为空），1 秒就返回，像是没传文件。
- 修法：`adb push xxx.apk /data/local/tmp/a.apk` 然后 `adb shell pm install -r /data/local/tmp/a.apk`，
  报错会完整得多，也能装上。

**模拟器（BlueStacks）里 `input tap` 命中区域偏**
- 症状：按钮视觉位置正确，点上去只听到点击音、日志 `Button On Click empty`，弹窗/入口毫无反应。
- 排查：用坐标扫描（同一点附近 ±40px 打几发）确认是「命中区偏移」而不是「事件没绑」；
  再调 Lua 直接触发回调对照——回调能跑就说明逻辑没坏，纯是输入层问题。
- 修法：优先改成**游戏内 Lua / 回调驱动**的验证路径；必须用点击时多试几个坐标，
  别把「点不中」误判成「功能坏了」。

**原生弹窗不会自己消失，必须手动 `dispose()`；而且它不一定在「你以为的那个」PopManager 里**
- 症状：自己用游戏原生 `DialogUtils.ShowTxtDialogCustom(...)` 弹的窗，点完按钮流程走完了，**弹窗还留在屏幕上**，
  它的全屏拦截层吞掉所有点击（日志只报 `Button On Click empty`），玩家被困住，只能重启。
- 原因：原生 Dialog 与 `PopLayout` **不会自动关闭**，得调用方显式收。若流程是"每步新建一屏"，最后一屏没人收。
- 权威样例（照抄它）：`CommonMsgDlg:onClickCancelBtn → doClose → self.popLayout:dispose()`
  —— **在按钮回调里直接 dispose 是官方写法，安全**，不用担心"自己关自己"。
- 两个实测坑：
  1. `ShowTxtDialogCustom` 的返回值经 tolua 绑定**取不到（恒为 nil）**，不能存句柄。要关只能从 PopManager 里拿。
  2. 同一个引擎里可能有多个 `PopManager`。本例中弹窗注册在
     `Frame.SystemManager.getInstance().PopManager`，而 `CommonFuncion:GetIntance():GetPopManager()`
     是**另一个空实例**（`GetPoplayoutCount()` 恒为 0）——查错了会误判成"弹窗不在任何管理器里"。
- 修法：`SystemManager.getInstance().PopManager:GetTopPopLayout()` 取顶层，**核对 prefab / resName 再 dispose**，
  避免误关别的面板；`ShowStep()` 每次新建前先收上一屏，避免层叠。
- 兜底：如果拿不准关闭 API，`PopManager` 通常还有 `RemoveAllDialog()` / `RemovePopPanel(pop)` 可用。

**动手验证前先想清楚「副作用会不会自己消失」**
- 离线版常常**每次启动用配置表重造仓库/背包**（如本项目把所有道具按 `OFFLINE_START_COUNT` 重发一遍）。
  这类种子会让"花掉的消耗品、抽到的东西"在**重启后回到种子值**——测试副作用天然消失，无需手工还原。
- 但**受 PlayerPrefs 落盘的状态**（等级、突破、星级、剧情进度、引导进度）不会自己回去，必须手工清理。
- 做法：验证前后各读一次关键字段 → 重启 → 再读一次。
  数值回到种子值 ⇒ 属于前者，不用管；仍然保留 ⇒ 属于后者，**要删 prefs 键再重启**，并复查。

**`adb shell input text` 灌不了长文本：会被按键序列打断，还有单次长度上限**
- 症状：把授权码 / token 一类长串（几百字符）灌进输入框，结果只剩尾部几十个字符，或半路触发
  ESC / TAB 把界面搅乱；看起来像"校验失败"，实际是输入根本没进全。
- 原因：`input text` 走的是按键事件模拟，特殊字符要转义，且单次调用有长度上限。
- 修法：长文本别指望自动化输入——**留给人手工粘贴**，或换通道（先写进 prefs / 文件再让游戏读）。
  验证"输入 → 放行"这类链路时，如果自动化输入失败，只能报告"输入通道未验证"，
  不要写成"授权码校验不通过"。

**Windows / PowerShell 下改文件：别把补丁文本内联当命令行参数**
- 症状：`apply_patch` 之类工具用内联字符串传参时报 `ParserError: '<' operator is reserved`，
  或中文变成乱码导致替换失配。
- 修法：改用 PowerShell 字面 here-string `@'...'@` 赋给变量再 `Set-Content -Encoding utf8`，
  或用 python 以 `utf-8` 读写（`io.open(..., encoding='utf-8')`）做字符串替换；
  脚本输出非 ASCII 时先 `$env:PYTHONUTF8=1`，否则 GBK 控制台会 `UnicodeEncodeError`。
- 附带：删除文件若被沙箱拦截，用 `python -c "import os;os.remove(...)"` 或 `shutil.rmtree`。

**用内联脚本改源码时，反斜杠被工具层吃掉一层**
- 症状：用 `python - <<'EOF'` 这类内联脚本做"按原文查找再替换"，要找的那几行里有字面量的"反斜杠 + n"（例如补丁脚本里一行行拼起来的 Lua 字符串），怎么都匹配不上；打印出来看一模一样。
- 原因：命令字符串经过一层转义，脚本里写的两个反斜杠到 Python 手里只剩一个，"反斜杠 + n"变成了真的换行。（写这条笔记时又被它坑了一次。）
- 修法：逐字符比对找出第一个不同的位置（一下就能看出来）；需要字面反斜杠时用 `chr(92)` 拼，或者把脚本先写成文件再执行。

**注入通道在一次失败的调度之后一直超时**
- 症状：往游戏主线程排一段脚本，日志报调度失败；之后每次注入都 `TransportError: timeout`，游戏本身还活着。
- 修法：重启游戏再注入。调度用的宿主对象换成一直存在的那个（主界面），不要用"当前界面列表"。

**本地应答函数「查不到就什么都不做」，剧情晾在原地**
- 症状：剧情走到某个小游戏，对白框消失、画面停住，怎么点都不动；日志里没有报错，也没有"未处理的请求"。只在某个分支选项里出现，别的分支正常。
- 原因：原版把"向服务器要小游戏结果"换成了本地函数，函数里查配置表用错了表名（表其实叫 `rept某某Cfg`，写成了 `rept某某`，取出来是空），于是返回"没启动"；调用处在"没启动"时什么都不做。客户端自己随机的小游戏不走这条路，所以大多数小游戏正常，只有"结果由服务器给"的那几个起不来。
- 修法：表名对着配置管理器里的赋值语句核一遍；本地函数失败时必须留一行日志，并且走一条不卡死的退路（这里是跳过小游戏接着播）。
- 举一反三：靠试玩覆盖不到所有剧情分支。配置里有"是否由服务器决定"这类字段时，直接把这类条目和用到它们的对白全列出来（真机上注入一段只读脚本打日志即可），逐个确认有本地实现。服务器回包里的数值（落点、次数）没有原始记录时，看小游戏结束后接的那几句台词，剧情要什么结果就给什么结果。

**误删函数，语法检查和打包自检都是绿的**
- 症状：真机报 `attempt to call global '某函数' (a nil value)`，而这个函数昨天还在。
- 原因：用"从标记 A 到标记 B 整段替换"的办法改源码，A 和 B 之间夹着另一个不相干的函数，一起被换掉了。Lua 的语法检查只管语法，调用不存在的全局函数要运行到那一行才报错。
- 修法：打包自检里加一步：离线模块里调用的自家函数（按前缀认）必须在某个模块里有定义。整段替换前先打印被替换的内容看一眼有多长。
**补丁里的单例访问器 / 配置表名拼错，被 pcall 兜底悄悄吞掉（案例 A）**
- 症状：奶猫槽解锁后指引事件一直不发；升级时原版升级弹窗一直不出现。都不报错，只是功能不生效。
- 原因：离线补丁调 `BackyardManager.GetInstance()`，原版类里单例函数实际叫 `GetIntance`（少个 n）。调用包在 `pcall` 里，失败后悄悄走兜底分支。配置表名也有同类（真实名带 `Cfg` 后缀、或 `rept某某Cfg` 写成 `rept某某`），取出空表。
- 修法：补丁里所有单例访问器名、配置表名和原版类定义 / 配置管理器赋值语句逐个对一遍；`pcall` 兜底不要写成静默，至少打一行日志。把这类检查做成打包期 lint：扫离线模块用到的全局函数和配置表名，对照已定义的函数和真实存在的表（本游戏 247 张），不一致就打包失败。

**账号字段是"空"和是 0 不一样**
- 症状：主界面头像是一个空圆；点头像没反应。
- 原因：本地造的账号没填头像 / 头像框编号。原版代码对 0 有兜底（显示默认头像），对"空"没有：既不走兜底，也查不到配置，什么都不画。点头像没反应是另一回事：面板等的那条资料请求没人回（改名、换头像这些"写"请求早就接了，偏偏漏了打开面板的那条"读"请求）。
- 修法：本地造账号时，协议里的数值字段都给上默认值，默认值去全局配置里找（这里是"默认头像 / 默认头像框"那一条）。接一个面板时，把它打开、读、写三类请求列全，别只接写。

**面板同一帧销毁再重建，新面板的按钮全失效**
- 症状：某个页面出来了但点哪都没反应，或关不掉；日志是 `某面板.Instance`（静态的"当前实例"）为空。只在"从 A 面板直接跳到同类的新面板"的路径上出现。
- 原因：Unity 的销毁延迟到帧末。旧实例的 `OnDestroy` 在新实例的 `Awake` 之后才跑，无条件把静态引用清成空。原版靠网络回包隔了几帧所以碰不到；离线版回包是同步的，就撞上了。
- 修法：`OnDestroy` 里改成"静态引用是自己才清"。同一种写法的面板一起改，别等一个个撞。

**本地应答时调了原版的"回包处理"，它顺手又开了一条流程**
- 症状：打完一关回到列表，关列表时冒出一段没见过的对白，后面还跟一场多余的战斗。
- 原因：离线版自己直接开了战斗页，同时为了"记下当前关卡"调了原版的开始回包处理；那个函数还会通知列表面板去走原版流程（对白 → 对白里进战斗）。两条流程并存，原版那条被压在下面没人管。
- 修法：调原版回包处理前把它读到底，看它通知了谁。只需要其中一两行副作用时，自己写那一两行，不要整个调。

**脚本包解压后超过 16 MiB，游戏启动即退出**
- **2026-10-18 更正：没有 16 MiB 上限**（17.07 MB / 131 块的包实测能进主界面）。当时撞上的是「某块压缩后恰好等于原始大小」，见文末 "compressed size equals its raw size" 一节。
- 症状：加了几个模块后新包起不来，日志 `archive:/CAB-… is corrupted! [Position out of bounds!]`，进程收到信号 5。和"单个文件太大分配不了内存"不是一回事。
- 事实（另一条开发线量的）：这个包按 128 KB 一块压缩，线正好在 128 块 = 16,777,216 字节；退回线内就能起。是引擎上限还是打包库回写的问题没分清。
- 修法：打包自检里量解压后的大小，留余量，超了直接失败。要腾空间就给没打过补丁的原版文件做瘦身（去注释和空白），别动打过补丁的（自检断言靠注释字样）。

**注入的脚本里遍历宿主语言的容器，游戏原生层直接崩**
- 症状：往游戏里注入一段只读的诊断脚本，进程直接退出，`pcall` 接不住。
- 实例：用游戏自带的遍历函数（`CSLEach`）走 C# 字典 `m<玩法>CardDic`，两次复现。
- 修法：要枚举就从配置表拿编号，再逐个问模型的查询函数；不要在注入线程里直接遍历 C# 容器。
- 相关：游戏连续运行近一小时、注入过几十次后，一次普通注入也可能崩在注入工具自己的线程里（`gum-js-loop`）。长测试隔一段重启一次，崩了先看栈在谁的线程，别急着怀疑游戏逻辑。

**系统悬浮条（录屏、游戏加速条）会自己挪位置，固定的"禁点区"不可靠**
- 症状：照着坐标点游戏里的按钮，点到了压在上面的录屏悬浮条，打开了系统相册，游戏被盖住。
- 修法：每次点击前看当前截图里悬浮条在哪，而不是记一个固定区域；开测前请设备主人把悬浮条关掉最省事。点出去以后立刻停手，报告前台是谁，不要在别的应用里继续点。

**提示文字（飘字）在某些页面上一句都看不见，点击处理和文字都是对的**
- 原因：Unity 里「相机层」画布永远画在「叠加层」画布下面，层级数字设多大都没用。为了修层级，把某些面板的根画布改成了叠加层；飘字还挂在相机层的 UI 根下，于是在这些面板上被整块盖住。给飘字自己加画布、把层级设到 31000，反而在所有页面都看不见了。
- 查法：别靠点一下再截图（飘字一秒就没，截图要一两秒）。往游戏里注入一段用游戏计时器连续 15 秒、每 0.5 秒飘一句的脚本，同一段在主界面和出问题的页面各跑一次再截图，结论一眼就清楚。日志里先确认「处理函数跑了、文字算对了」，把问题缩到显示层。
- 修法：建一块单独的叠加层画布（缩放设置照抄原 UI 根，字的大小位置不变），每次飘字后把飘字对象挂过去；第一次飘字时预制体是异步加载的，晚 0.2 秒再挂一次。
- 注入试验脚本时，PowerShell 默认写出的 UTF-8 带 BOM，Lua 加载器会静默失败（注入工具照样回报成功）。用不带 BOM 的写法生成脚本，并在脚本末尾打一行日志确认装上了。

**两个区之间切换后画面换了，底部导航高亮还停在旧按钮上，玩家以为「点不过去」**
- 原因：原版换区要等新场景加载完，由场景回调（案例 A 里是 `MainPanel:ChangeSubPanel`）移动导航高亮。离线版为了快，在两个共用同一张地图的区之间「复用地图、只换内容」，不再加载场景，那个回调永远不来。从别的界面进去走的是完整加载，所以只有「从 A 区点 B 区」这一条路坏。
- 查法：在日志里看同一下点击走的是哪条路径（复用路径和完整加载路径各打一行），再对照截图看内容和高亮是不是一致。玩家说「点不过去」时先分清是内容没换、还是只有高亮没换。
- 修法：凡是绕过原版加载流程的快捷路径，都要把原版回调里做的界面收尾（高亮、当前页签记录）自己补一遍。

**进出某个全屏页面时主界面卡一下**
- 原因：为了避免层级冲突，进全屏页前把底下的地图面板「关掉」；关面板会让面板管理器把主界面舞台重新显示一遍（背景音乐都会切），回来时再从零重建整张地图。原版关全屏页时自己还会做一次资源卸载（约 0.45 秒），两段加起来将近 1 秒。
- 查法：日志时间戳逐行看「关页面 → 资源卸载开始 / 结束 → 地图重新加载 → 地图对象创建」各花了多久，就知道卡在哪。
- 修法：底下的面板只隐藏（`SetActive(false)`）不关，回来时直接显示并重排层级；隐藏失败（面板已不在）再走老路。原版自己的资源卸载别动。

**地图被改成叠加层画布后，C# 层弹出的确认框（按返回键的「确认退出」等）被地图盖住看不见**
- 原因：同上一条飘字问题——叠加层永远盖住相机层。Lua 层的面板能在面板显示钩子里抬层，但 C# 自己弹的对话框不经过 Lua 的面板管理器。
- 对策：凡是把某块大画布改成叠加层，就要列一遍还有哪些弹窗来自 C#（在 Lua 源码里搜不到文案的就是），给它们单独想抬层的办法。

**想在游戏里加「从相册选图」，以为必须改 Java / dex**
- 先在 IL2CPP 的 dump.cs 里搜 `Permission` / `Gallery`：很多手游自带权限封装（案例 A 有 `AndroidPermissionsManager.IsPermissionGranted(string)` 和 `RequestPermission(string[], 回调)`），脚本层直接调就能弹系统授权框。目标版本低于 29 的包在新安卓上仍是旧式存储（`appops` 里看 `LEGACY_STORAGE`），授权后按 `/sdcard/...` 路径直接读。
- 脚本桥的坑：桥接层的「数组初始化」函数可能返回脚本表而不是 C# 数组，要用 `System.Array.CreateInstance(typeof(String), n)`；造不出 C# 委托时给回调对象传空，结果靠轮询「是否已授权」拿。
- 授权框要设备主人自己点，agent 不代点；可以点「拒绝」测拒绝路径。

**Windows 的 Git Bash 里 `adb push x /sdcard/...` 报 `secure_mkdirs failed`，目标路径变成了 `<Git 安装目录>/sdcard/...`**
- 原因：Git Bash 会把以 `/` 开头的参数当成 Unix 路径转换成 Windows 路径。
- 修法：命令前加 `MSYS_NO_PATHCONV=1`，或者用 PowerShell 调 adb。


**授权码 / 兑换码 / 存档迁移这类「纯逻辑」模块，不要等上机才发现错——用 lupa 在电脑上跑真的 Lua，GameNS 用 Python 模拟**
- 做法：`pip install lupa`，把要发布的 `.lua` 模块（和门禁一起，顺序同构建拼接）原样 `execute` 进去；在 Lua 里先建一个 `GameNS = {UnityEngine={PlayerPrefs=...}, System={Text=..., Convert=..., Security=..., IO=...}}` 的模拟层，`CSLNew / CSLNewfunc / CSLArrayGet / CSLTypes` 也各给一个。真签发（pycryptodome + 私钥）→ 真验签（模拟层的 RSA 用 `release_public.xml` 里的公钥，和游戏里是同一把）。案例 A 的 `tools/tier_selftest.py` 就是这么做的：150 项，分钟级，抓住了好几处只有真跑才暴露的语法 / 逻辑错。
- 模拟 .NET 的 `byte[]`：**用十六进制字符串**表示。lupa 把 Lua 字符串当 UTF-8 解码，二进制（签名字节）放进 Lua 字符串会炸。
- 写完测试再做「突变」：把关键判断（到期比较、设备码比对、`to` 比对）一个个改坏，确认测试会红；不会红的测试等于没测。
- 时钟、权限、文件系统都放进模拟层里可控（`V3_Now`、`IsPermissionGranted`、内存文件系统），才能测 05:00 边界、无权限退路。

**签名绑定要「载荷里签过名的值」对「包内 / 本机的生效值」逐项比，别只验签名就放行**
- 授权码载荷里的群号、设备码、到期日、功能位都取自签过名的载荷，再和包里的群号、本机设备码、今天的日期比；功能位不要另存一个可手改的数字，存授权码**原文**，每次启动重新验签再算。
- 到期日别和包里的常量做字符串相等（改包里常量就绕过了，签发新到期日也会全部失效）；`YYYY-MM-DD` 字符串可直接按字典序和今天比大小，注意用固定时区（北京时间 +8）。
- 过期的授权码不要把已经玩过的人挡在门外：保留旧的「已解锁」标记当兜底，档位退回最低档。
- 门禁整体关闭开关（`gate_bypass`）要在**正式包构建的自检里断言为 false**，不要只断言赋值存在。

**Unity Android 的 PlayerPrefs xml（`shared_prefs/<包名>.v2.playerprefs.xml`）里键名和字符串值都是 URL 编码，且区分 `<string> / <int> / <float>`**
- 导出全部存档键时：从 xml 里取键名和类型（键名要 URL 解码），值仍然走 `PlayerPrefs.GetString/GetInt/GetFloat`（避开 xml 转义）；整数键用 `GetString` 读会得到默认值。应用自己能读写自己的 `/data/data/<包名>/shared_prefs/`，不需要权限。
- 脚本桥（tolua 一类）调不了 `AndroidJavaObject.Call<T>` 这类泛型方法，别指望 `SharedPreferences.getAll()`；读 xml 更省事。
- 存档文件里的键和值都 base64，换行 / 竖线 / 等号 / 百分号都不会破坏格式；`SUM` 管误码，**真正管归属的是开发者私钥的签名**（只有 SUM 的话，改 `src` 重算 SUM 就能把档克隆到多台设备）。
- 导入 = 先备份当前存档（备份失败就取消）→ `DeleteAll` → 写入 → **保留本机原有的授权键** → 关游戏让 Lua 全局缓存重读；别试图热替换。

**用 Bash 工具的 heredoc（`python - <<'EOF'`）写含双反斜杠的补丁脚本，工具会把 `\\` 先折成 `\`，于是 Python 里的 `'\\n'` 变成真换行，Lua 里就报 `unfinished string`**
- 症状：往 `.lua` 里插字面量 `'\n\n'`，文件里却成了真换行（字符串断成三行）；看 `sed` 输出才发现。
- 注意：连这份文档本身用 heredoc 追加时也被折了一次——写含反斜杠的内容一律用 Write / Edit 工具。
- 修法：补丁脚本用 Write 工具落成 `.py` 文件再运行（文件里的反斜杠不会被改），或用 `chr(92)` 拼；改完立刻 `grep -n` 看那一行。
- 同类：`pip download xxx` 会把 wheel 下载到当前目录，工作区里多出一个 `.whl`，提交前 `git status` 一定要看。

**Windows 下的管道和编码（2026-11-07）**
- 症状：PowerShell 里让 `git archive` / `tar` 走管道，得到的归档是坏的；`.ps1` 里的中文读成乱码；Python 打印中文报 `UnicodeEncodeError: 'gbk'`。
- 原因：PowerShell 管道按文本处理字节流；Windows PowerShell 5.1 不把无 BOM 的 UTF-8 当成 UTF-8；控制台默认 GBK，而 `python -I` 会忽略 `PYTHONIOENCODING`。
- 修法：二进制流改用 Bash 重定向（`git archive --format=tar > x.tar`）；`.ps1` 存成带 BOM 的 UTF-8；Python 里调用 `sys.stdout.reconfigure(encoding='utf-8')`。
- 反过来，Lua 注入文件、git 提交说明这类文件要写成**无 BOM** 的 UTF-8：PowerShell 5.1 写文件默认带 BOM，注入的 Lua 会静默加载失败，提交主题行开头也会多出 BOM（案例 A 2026-10-14 因此重做了两个提交）。用 `[IO.File]::WriteAllText(路径, 内容, (New-Object Text.UTF8Encoding $false))` 或 Python 写。

**OpenCV 写中文路径会静默失败（案例 B 2026-10-20）**
- 症状：录屏抽帧后目录里一张图都没有，也不报错，后面的草稿和校对图都缺了录屏那部分。
- 原因：`cv2.imwrite` 遇到非 ASCII 路径只返回 False，不抛异常。
- 修法：写文件用 `cv2.imencode('.jpg', img)[1].tofile(path)`，读文件用 `np.fromfile` + `cv2.imdecode`；保存后数一下文件数。

**镜像 CDN 被限流：降低并发，换用 curl（案例 B 2026-10-17）**
- 症状：用 24~48 路并发加 Python urllib 下载时，连接被拒或卡死，吞吐只有每分钟 1 MB；放到后台的进程随 shell 退出而终止；优先下载的那批文件全部「失败」。
- 原因：CDN 对高并发限流；urllib 没设超时会无限挂起；用 `&` 放后台的进程会跟着 shell 一起结束；Windows 下 Python 写出的列表每行带 `\r`，URL 末尾多了一个回车。
- 修法：用 curl，加 `--speed-limit/--speed-time`、`-m` 超时和重试，证书过期加 `-k`，并发降到 6~8；按优先级先抓开场剧情、剧情文本、UI，语音放最后；用工具自带的后台运行方式；读列表时先去掉 `\r`。

## 分档 / 授权开关（案例 A 2026-10-17 合并时）

**「载入时算一次」的开关跟不上授权：授权码是登录时才验、还能在设置页中途换**
- 症状：封顶章节写成模块顶层的 `if ... then MAX = X end`，载入时授权模块还没验码（或玩家后来升档），封顶就一直是旧值。
- 修法：做成函数（`V3C_ApplyCap(why)`），载入时、登录钩子最前面各调一次，并把它暴露给授权模块在换码后调；依赖封顶的其它改写（七日任务恢复原版）也挪进这个函数，降档时能放回去。

**开发用的覆盖键一定要挂在开发开关下面**
- 症状：调试时加的「存档键 X 存在就把封顶改成 X」在正式包里照样生效，能动存档（Android 备份还原）的人就能绕过付费 / 授权位。
- 修法：所有 `*_DEV_*` 存档键只在 `OFFLINE_V3_DEV = true` 时读；正式包打包时把开发开关关掉（`--final`），自测脚本里断言这一点。

**按开期过滤活动：在「判当前期」的唯一入口把关，但规划 / 诊断类调用要另给一个不过滤的版本**
- 做法：十几个活动模块判「现在是哪一期」都经过同一个 `TrackState`，把授权和开期规则塞进它，模块一行不用改。
- 坑：有些模块拿同一个函数扫未来几十天算日历、查和别的活动撞不撞期；过滤后它们看到的是「全关」，算出来的日历是错的。把原函数改名 `TrackCalendar`（纯日历），扫日历的调用和自测里核对日历的断言改调它。
- 外部窗口函数（兑换码 / 自排）由别的会话提供：不存在、报错、返回 nil 一律当没有；进行期以外的兑换期由本线按轨道参数补，接口文档里写清楚「返回的是进行期」。

**合并两条长期分叉的分支：先看清哪边的文档只是旧副本**
- 探索线里的发版说明 / 用户反馈表是从发布线早期抄过去的副本，没有自己的新行；直接取发布线那份即可，不用重新编号。动手前用 `git diff <merge-base> HEAD -- 文件` 看本分支到底加了什么。
- 同一仓库里 `.py` 是 CRLF、`.lua` 是 LF：用 Python 精确替换前先 `repr()` 看一眼换行，别让断言「找不到」浪费一轮。

**从活动轮换里拿掉一期：挖成空档，别删条目（案例 A 2026-10-20）**
- 症状：把轮换表里的一期删掉后出开发包，补丁自检卡在“该活动没有入口图”上，构建失败。
- 原因：核对脚本默认轮换表里每一期都有入口图。另外，直接删条目会让后面几期的日期整体前移，打乱手机上正在进行的那一期。
- 修法：删期改成“挖空档”（槽位保留，但不开），让核对脚本认得空档。动手前先对比改前、改后的轮换日期。

**放开类补丁别把门槛一起放没了（案例 A）**
- 症状：全新档一进游戏所有功能全开；半仙阁所有关卡全开；花笺突破一次后升级上限变成 100。
- 原因：离线补丁用总开关让主线解锁判断直接返回 true、把强制显示按钮的旧补丁留着；解锁 / 上限条件写得太宽（没判主角等级和上一关通关，上限公式写错）。
- 修法：关掉绕过开关，让原版的解锁判断（`ComUnLockMgr:CheckUnLock`，含 0 等级 / 1 猫数 / 2 主线任务 / 3 店铺等级 / 4 无条件）走完整；强制显示按钮的补丁改成按配置表行判断；按原版条件实现（半仙阁每章第一关要主角等级 + 通过上一章，花笺上限 `min(突破数+10, 100)`）。自测要覆盖「不该开的没开」，用全新档验证。
- 相关：汇报「某功能锁着」之前，先读代码确认那条规则是否真的被执行，别凭印象——曾报半仙阁第二章锁着，实际离线代码根本没判主角等级，用户的档正好满足所以看不出差别。

## 分档第二批：开局拉满 / 资源券（2026-10-17，会话 C）

**「一键拉满」不能只写存档，也不能指望热刷新界面**
- 缓存分两类：每次变更即读盘的键（`V3_LoadMap` 类，角色好感 / 藏品 / 持有卡牌）写完就是真值；启动时读进内存、之后只写回不读盘的（道具覆盖层、卡牌星 / 级 / 突破、宠物成长、店铺等级）必须**同时改内存表再落盘**，否则进程里下一次普通落盘会拿旧内存把拉满的值盖回去。
- 界面（卡牌 / 宠物 / 好感）读的是已建好的模型对象，没有统一的刷新入口；做法是写完存档 + 内存缓存后弹原版确认框「退出游戏」，让玩家重开。拉满函数留 `noQuit` 参数给注入自测用。
- 备份要读**存档**而不是内存：自测里先在内存里抬了一个探针值、没落盘，备份里自然没有它，还原断言就失败（自测写错，不是产品错）。

**拉满的「只增不减」：每个键各写各的比较，别整张表覆盖**
- 每个映射键取 `max(现有, 目标)`；已有值更高就保留；自测里先把一个材料抬到 55555、一个角色好感抬到上限 +777、一张卡抬到 100 级，拉满后断言它们没被压回；再拉一遍断言「什么都不再涨」（幂等）。
- 备份只留**第一份**（拉满前）：第二次拉满时存档已经是满的，覆盖等于丢了真正的「拉满前」。备份失败就不拉。
- 存档键没法枚举（PlayerPrefs 无 getAll）：备份清单 = 构建期扫所有模块里 `'OFFLINE_...'` 字面量 + 运行时的清档名单。带动态后缀的键（`OFFLINE_V3_UNLOCK_SEEN_<按钮名>` 一类）进不了清单，文档里要写明这个上限。

**原版确认框（DialogUtils.ShowTxtDialogCustom）的文字区只有 4~5 行高**
- 一页列 11 行选项，真机只露出前 3 行，其余被裁掉且不能滚。做「翻页选择」：一页放一项（▶ 当前项 + 第 n/N 项 + 剩余张数），「换下一项」翻页，最后一页放「暂不兑换」。
- 对话框按钮按下后不会自己关：`PopManager:GetTopPopLayout()` 核对 `resName == 'Dialog_Confirm_Cancel_UI'` 再 `dispose()`；翻页要延迟 0.3 秒再开下一页（同一帧开会叠）。

**往背包加一个「使用」弹自选面板的道具：配置行 + 现成的礼包使用消息**
- 配置库 `reptItem` 加一行（`iItemType=6`、`iUseType=2`、`iSubItemType=0`、`sSource='999|活动'`）。`sSource` 为空时详情面板不显示「使用」；`iSubItemType` 101~103 走礼包预览面板 122、104 走原版自选礼包，都不要。点「使用」发 `E_SVR_MSG_ID_OPEN_PACKAGE`，离线分发表里按 `iPktID` 拦自己的券，别的礼包交给原来的处理。
- 原版 `<宠物自选礼包面板>` / `<角色自选礼包面板>` 只有宠物 / 角色两种固定样式，没有通用列表，别指望复用。
- 加配置行走 protobuf：parse → `reptItem.add()` → 序列化 → 回读断言（行数 +1、字段逐个对、别的表行数不变）→ 同一输入加两遍结果相同（幂等）。新道具号先在配置库里查空号（本次用 59001）。

**新模块放进独立的小宿主，登录钩子放在 MsgManager 尾部**
- 宿主文件有体积闸（LoginController / MsgManager 258000 B），新模块各寄生在一个小管理器文件末尾（`SettingManager.lua` / `DailyTaskManager.lua`，锚点 `\nreturn <名>`），MsgManager 只加一个 600 B 的 `V3_OnLogin` 包装去 `CSLTypes.<宿主>` 触一下（懒加载）再调 `Install`。包装排在最后 = 分发表包装在最外层，能抢在先装的处理器前拦消息。
- 设置页加按钮：借用原版一个没用的按钮（`btn_limit` 点了开浏览器）改字改点击；锚点选在 `InitPanel` 中段的音量行，避开别的会话改的开头，两边补丁互不重叠。
- 新检测「新档」用现成信号：新手选择键 `OFFLINE_NEWBIE_CHOICE_V1` 写入之前的那一次进主界面 = 新档；再加「等级 ≤ 3 且主线 ≤ 10103」兜底（弹窗没答完就杀进程）。授权接口没装时 `V3_TierAllows` 兜底：开发包全开、正式包全关。

**工具链**
- 在 Bash 工具的 heredoc 里写含 `\n` 的 Python / Lua 源码，工具层会把 `\` 吃成 `\`，字符串里出现真换行、断言「找不到」。含反斜杠转义的源码一律用 Write 工具落盘再执行，或用 r''' 原始串。
- `v3_dev.py restore` / `restart` 后要等到「公告点掉 → 主界面」再 `luamain`，否则脚本进了没起来的调度器、什么日志都没有；用「先注入一条 ping 日志确认能回」再注入自测。
- 设备占用表是每个 worktree 一份，别的会话看不到你写的那一行：别人装包会把你分身里的包覆盖（`dumpsys activity exit-info` 里 reason=PACKAGE UPDATED 就是被人装了包）。上机前先 `exit-info` / `dumpsys package <pkg> | grep lastUpdateTime` 看有没有人在用，上机时直接给对方会话发消息。

**注入的宿主脚本悄悄长到上限边缘，下一个小改动就启动闪退**
- 现象：把多个离线模块拼进同一个宿主脚本文件（案例 A 是 `LoginController.lua`），文件过大时 Unity 在预加载阶段分配字符串失败直接闪退（实测约 261 KB）。构建自检只断言「不超过上限」，没人注意余量：2026-10-17 发现它已到 257.5 KB，余量不到 500 字节。
- 对策：每次构建都打印各宿主的大小和余量，余量低于 10 KB 就报警；新模块一律放独立宿主。要腾空间时，挑一个「没有和别的模块共享局部变量、也没被别的模块在加载时取用」的模块整体搬到另一个先于使用点加载的宿主，构建自检里引用它内容的断言一并改指新宿主（按次数计数的断言改成统计两个宿主合计）。
- 搬之前用脚本查两件事：它定义的局部名有没有被同宿主其他模块用到；它定义的全局函数有没有被其他模块在顶层赋给局部变量（加载顺序一变就成了 nil）。

**一键发全套后，客户端被上千条“集齐”推送压死（案例 C 2026-11-01）**
- 症状：领“全部衣服”后奖励弹窗关不掉，游戏主线程 CPU 100% 持续两分多钟，重登后才正常（衣服其实已经到账）。
- 原因：服务器每个 tick 都检测新集齐的套装，这次一下多出 1279 套，每套推一条通知，客户端逐条弹提示。
- 修法：批量发放后不推送，在后台把已集齐的套装静默记成“已见过”（登录钩子和发放函数共用同一个函数）。凡是一键拉满类功能，先想想会不会触发大量逐条通知，可以先在电脑上用 lupa 跑一遍，数一数推送条数。

**一键拉满好感后，每只宠物都冒感叹号、点不动（案例 A 2026-10-22）**
- 原因：只把好感拉满了，没把各级好感奖励标成已领；回包里每一级的领奖状态都是 0，于是每只宠物都显示有奖可领。
- 修法：拉满时顺手把每一级奖励标成已领，对已经拉满过的旧档做一次带标记的补救。拉满任何「有逐级奖励」的维度，都要同时处理奖励状态。

## 游戏内读相册 / 自定义图片（案例 A 2026-10-17，tier/custom-media）

**Lua 绑定层的「同名重载」只有部分能用，先注入一段探针挨个试再写代码**
- 实测（Unity 2017.4 + 这套 CSL/ToLua 绑定）：`ImageConversion.LoadImage(tex, bytes)` 抛 `C++ exception`，三参数 `LoadImage(tex, bytes, true)` 能用；`Graphics.Blit(src, dst)` 能用，带材质或带 scale/offset 的重载都抛异常；`GL.Color` 抛异常（其余 GL 调用都行）；`FileStream:Read` 不存在，用 `BinaryReader:ReadBytes`；`EncodeToPNG/JPG` 只能经 `ImageConversion` 静态类调；游戏里没有 `cjson`（`require` 失败），要自带 JSON。
- `tostring(long 属性)`、`tostring(枚举)` 会报 `field or property __tostring does not exist`：打日志前包 pcall。`GameNS.<不存在的命名空间>` 也返回一张表，不能拿来判断类型存不存在。
- 裁 / 缩 / 转图不用逐像素：`UI/Default` 材质 + `GL.Begin(QUADS)` 画四边形（四角 uv 按旋转算好）进 `ARGB32` 临时 RenderTexture，再 `ReadPixels`。手机竖拍 JPEG 像素多是横的，要读 EXIF 0x0112 转正。

**pbc 解出来的配置行读「不存在的字段」直接抛错**
- 症状：认表时写 `if row.iStar then`，对没有这个字段的表报 `[string "protobuf_pbc"]:215: iStar`，整个钩子中断（而且前面已经改了一半的表）。
- 修法：探测字段统一走 `pcall(function() return r[k] end)`。

**配置表在 Lua 里是普通表：预留行 + 运行时改字段 / 拿掉行，比运行时新建行稳**
- 构建期往配置库加「空槽位」行（同模板克隆），运行时包住 `DataTableMgr:convertToLocalTable`，每解出一张表就把没填内容的槽位行 `t[id] = nil`：所有「遍历整表」的列表（头像页、卡牌集、碎片页）都看不见。这一步早于登录种子灌入，按整表发碎片的种子也碰不到它。
- 模块挂在 `DataTableMgr.lua` 末尾最早；但它还没 `return` 时别碰 `CSLTypes.DataTableMgr`（会重入加载），用文件里的局部类表。主块局部变量有 200 个上限，模块里几乎全用全局函数。
- 运行时把行放回表后，清掉别的模块按表建的索引缓存（这里是 `_G.V3_CFG_CACHE`）。

**注入测试的代码太长时：先 adb push 到游戏目录，再注入一小段 `loadstring(File.ReadAllText(...))()`**
- `v3_dev.py luamainfile` 把整段代码放进命令行，60 KB 的模块报 `WinError 206 文件名或扩展名太长`。

**真机是用户自己的手机：他一碰屏幕就停手**
- 本轮两次：安装后用户正好在用手机，脚本拒绝重启；进游戏后进程被用户划掉（logcat 只有 `signal 9 (Killed)`，前后没有任何 Lua / Unity 报错）。先用 `phone_guard.seconds_since_user_activity()` 等到空闲几分钟再继续，别把「被杀」当成自己的 bug 去查。

**剥资源的正式包：活动「入口」和「面板」不在同一个资源包里**
- 活动图标在共享包（案例 A 是 `prefab/<活动目录>`），面板在各自的包（`prefab/activity/<名字>`）。只剥面板时入口照样出现，点进去才 asset isnull。
- 修法：保留名单和「运行期允许开哪些活动」用同一份清单（`release_content.json` 的 activities 由打包脚本填进 Lua），不在清单里的活动有兑换码也不开。
- 验收要用「资源按正式包剥、脚本开发开关还开着」的测试包，才能在没有真授权码时模拟高档位；真正的 `--final` 包只能验无位的情况。
**留下的资源包在总清单里依赖已剥掉的包，整包加载为 null（案例 A 2026-10-24）**
- 症状：瘦身包里点活动商店，回包正常，窗口始终不出现；日志只有 assetbundle null，没有缺文件报错。把窗口所在的包补回保留名单后照样打不开。

- 修法：打包期用 UnityPy 改总清单的 typetree，把每个保留包依赖列表里已被剥掉的项删掉；存回后照样走「压缩块不能等于原始大小」那套处理和可加载自检（见文末 compressed size equals its raw size 一节）。开关只放在瘦身 profile，全资源版先干跑一遍确认没有这种情况。删依赖前先用 UnityPy 看预制体实际引用了哪些依赖包的资源，真用到的要补包，不能删依赖。剥任何活动之前，先 grep 面板类名和包路径，看有没有别的活动在借它的面板。
- 怎么确认的：读总清单列出该包的依赖，只有那两条是被剥的；只剪这两条后重打，窗口和兑换确认框都正常，剥离自检全过。

**群里按日期发的活动码，在某些玩家手机上提示「已过期」**

**把模块搬去别的宿主时，新宿主文件自己的顶层 local 会遮住同名全局；要「晚于某模块执行」就包成函数、在原位置留桩调用**

- 搬前除了「共享 local / 顶层取用」两件事，还要查第三件：新宿主文件的顶层 local（反编译文件常有 `local F_GetInt` 之类）有没有和搬过去的代码里的名字重复。
- 也可以在打包时按标题行从大文件里切出一整节（源文件不动，别的分支还在改它），但要加断言保证那一节只有函数定义、没有顶层语句。

## Worktrees with junctions to the main repo (2026-10-17)

**注入工具（Frida 把 Lua 源码当命令行参数传）在 Windows 上有长度上限**
- 超过约 32k 字符的自测脚本直接 `WinError 206`，脚本根本没跑；批量跑自测时如果把输出丢掉，看起来就像「没有任何日志」。要么拆小脚本，要么让注入工具改成读文件。

**注入探测要排到游戏主线程跑，不要在注入线程里直接执行 Lua**
- 案例 A：`v3_dev.py lua`（Frida 线程里直接跑 Lua）在游戏开着时探测几次，游戏主线程就卡死：点不动、Unity 日志停，进程还在。`luamain`（排到主线程的定时器里跑）一直没事。
- 卡死后再用 `luamain` 也不执行，像是「注入坏了」，其实是游戏已经卡住。批量自测前后、探测状态，一律走主线程。

**Windows 的 Git Bash 没有 pkill**：`pkill -f xxx 2>/dev/null` 静默失败，以为停了的后台脚本其实还在跑，会和新开的脚本抢设备。用 PowerShell 的 `Get-CimInstance Win32_Process | ? CommandLine -like '*xxx*' | Stop-Process`。

**整行注释删除要认得块注释**：只删「以 `--` 开头的行」时，块注释 `--[[ ... --]]` 的结尾行 `--]]` 也会被删，注释关不上，后面的代码全被吞掉（语法检查才抓得到，运行时是静默少了一大段）。瘦身器必须跟踪长括号状态（含 `--[[` 开头和同一行就关上的 `[[...]]`），并且对瘦身的每个文件做「长字符串内容前后一致 + 语法」两条自检。
**给用户双击的 .bat 要纯 ASCII + CRLF，并按双击方式实测（案例 A）**
- 症状：用户双击后窗口一堆乱码报错。
- 原因：文件是 UTF-8 中文 + LF 换行，cmd 读不了；中文文件名在命令行里也传不过去。
- 修法：批处理文件和文件名都用英文、CRLF 换行；确实要用中文时，整个文件存成 GBK + CRLF（简体中文 Windows 按 GBK 读）。结尾加 `pause`，出错时窗口不会一闪就没。会删东西的脚本，先给一份只显示、不删除的空跑版跑通。交付前按用户双击的方式（`Start-Process`）真的启动一遍。

## Rebuilt bundle crashes at preload: a block whose compressed size equals its raw size (2026-10-18, root cause found)

Symptom (Unity 2017.4): at preload, the `UnityPreload` thread dies with `The file 'archive:/CAB-…' is corrupted! [Position out of bounds!]`. A variant of the same bug shows `Could not allocate memory … Trying to allocate: 1844674407…B … MemoryLabel: String` instead. It looks size-dependent: padding a different build to the same final size crashes too, and 144 bytes less boots.
Root cause: Unity's UnityFS reader treats any block whose compressed size equals its uncompressed size as stored, and it ignores the LZ4HC flag. UnityPy (`CompressionHelper.chunk_based_compress`) falls back to raw only when the compressed size is strictly greater (`>`). On a tie it writes the LZ4 stream and flags it LZ4HC. Unity then copies those 131072 LZ4 bytes into the CAB as if they were data. The next object header inside that block reads a garbage length. A huge positive length gives "Position out of bounds" (the CachedReader limit); a negative one gives the size_t allocation failure. Encrypted Lua barely compresses, so each block lands near 131072. Measured odds are about 0.09% per block, roughly 1 in 10 per 112-block bundle. "Same size crashes" only meant the same leading content, which yields the same blocks.
Proof (案例 A): every one of 15 saved builds that crashed had exactly one block with `cs == us` and flag 3, and none of the booting builds had one. Unity's exact crashing output with only that block rewritten raw boots. A known-good bundle with one block deliberately re-encoded to exactly 131072 bytes (still valid LZ4) crashes. The allocation size it requested matches the offline simulation byte for byte. In libunity, the message comes from `CachedReader::OutOfBoundsError` (read past the object's end, past the file length, or before its start), which fits a garbage length field. The `cs == us` branch in the archive reader itself was not located in the disassembly; the A/B tests establish it.
Fix: after any UnityPy save, store every compressed block with `cs >= us` raw (flags with the compression bits cleared). Then assert at build time that no compressed block has `cs >= us`, that no block carries the 0x40 bit, that the block-info table is smaller than raw when compressed, and that the sizes add up. Apply this to every UnityFS bundle you write. Plain serialized files (e.g. `assets/bin/Data/<hash>`) have no blocks, so skip them, or the build breaks. 案例 A: `unityfs_store_incompressible_blocks` + `assert_unityfs_loadable` in `tools/case_a_lua.py`. LZMA also sidesteps the bug, but it is not needed and costs a whole-bundle decompress at startup.
Myths this retires: there is no "16 MiB / 128-block" bundle limit (a 17.07 MB, 131-block bundle boots), and the per-script "261 KB" limit was very likely the same tie (its log was the allocation variant). Neither was the cause. The old failed experiments are explained too. Packer `(0x40, 0x43)` put 0x43 into every block's flags (UnityPy's tuple is `(data_flag, block_flag)`), which set the 0x40 "streamed" bit, so the loader returned null.
Verification trap: "process alive after N s" is not a pass, because a white screen with a loader NullReferenceException is alive too. Require the main screen or a log line from after Lua loads.
Method that cracked it: re-pack the identical CAB with your own minimal UnityFS writer. If that boots, the cause is in the container layout, not the content, and a block-table diff shows it immediately.

**清理产物目录：只认严格命名的直接子目录，逐层查链接，默认只打印（2026-11-04）**
- 症状：每份约 2.4 GB 的带时间戳构建目录越积越多。这块盘出过递归删除顺着 junction 删掉源码和私钥的事故，不能用通配符递归删。
- 原因：构建脚本只建不清；普通递归删除会顺着链接跑到目录外面。另外，Python 3.10 在 Windows 上的 `os.path.islink` 认不出 junction（只认符号链接），会把它当成普通目录进去删。
- 修法：写成独立的清理脚本。① 只处理名字完全匹配规则的直接子目录（如 `<模式>-<日期>-<时间>[-final]`），同名的普通文件不碰。② 目标本身和里面每一层都查链接：看 `lstat().st_file_attributes` 里的 reparse point 标记，junction 和 symlink 都认得出；有链接就整份跳过。真删时每层再查一次，碰到链接立即停止。③ 默认只打印“可以删哪些”，加 `--apply` 才真删。④ 保留最近 N 份，再额外保留每一类（模式 × 正式 / 开发）的最新一份，免得把别的工具当输入的包挤掉。⑤ 出错只打警告，不影响构建结论。⑥ 升级测试目录只清 APK，截图和 diff 保留。
- 多会话共用仓库时：开工前先看进程列表，谁的命令行里带着哪些产物路径，就不碰那些产物。除了名字里是今天的，24 小时内写过的也保留（跨午夜的构建，名字里是昨天的日期）。删之前和已发布目录里的副本比一次 SHA-256。超过保留期的旧包仍可能被别的任务读取，这个残余风险要告诉用户。
- 怎么确认的：在临时目录里用真实的 junction 和 symlink 跑了 25 项测试；对真实目录空跑一遍，前后文件对比没有变化。

**A collection UI exists but nothing in the offline server ever grants its items (2026-10-19, 案例 B)**

## 案例 C 侦察（2026-10-21）

**A 1.2 GB APK was only a quarter of the game (micro client)**
- Symptom: everything decompiled fine and the plan looked straightforward, until the bundle manifest was diffed against the package: 42,700 bundles listed, 12,120 present; about 91% of the clothing models missing.
- Cause: a big publisher's micro client (`_ClientType: 2`). The rest was downloaded on demand through the SDK's Puffer downloader and died with the servers.

**A rejected Lua header is not encryption**
- Symptom: unluac refused every script with "non-standard lua format: 1".
- Cause: byte 5 (format) of the Lua 5.1 header was changed from 0 to 1; nothing else was touched.
- Fix: compare the header byte by byte with the standard one, reset the changed byte, decompile.

**The original game stops at the publisher's privacy agreement (`MSDKPolicyActivity`)**
- Symptom: a test run on the emulator never reached Unity; logcat only showed the MSDK policy activity.
- Cause: the launcher activity is MSDK's user-agreement and privacy-policy dialog.
- Fix: clicking "同意" accepts a real agreement on the user's behalf; ask first. For the offline build its HTML and title string were replaced with the memorial disclaimer (see `case-c-micro-client.md`, "开屏和协议页").

**Shell quirks that wrote files to the wrong place (Git Bash on Windows)**
- `/tmp_xxx` in Git Bash is the Git install directory (`<Git install dir>\tmp_xxx`), not a temp folder; the safety check then refuses to `rm` it. Use the session scratchpad or a project path.
- The heredoc backslash pitfall recorded above (Bash tool folds `\\` to `\`) bit twice more here, once while appending this very entry. Write scripts and docs with the file-writing tool, not heredocs.
- Git Bash also rewrites device paths in arguments: `adb pull /data/local/tmp/x` became `<Git install dir>/data/local/tmp/x`. Prefix the command with `MSYS_NO_PATHCONV=1`, or avoid device paths on the host side altogether (next entry).

**A re-signed build exits about 2 s after launch with code 4 (the publisher's TP shell)**
- Symptom: the patched, re-signed APK showed the MSDK agreement page, then `Process … exited cleanly (4)`; no Java exception. The original APK did not do this.
- Cause: `TPShellApplication` loads `libtprt.so`, which checks the APK (FileChecker/CRC, package name) and kills the process. The same shell decrypts the first 0x1000 bytes of the managed assemblies (`mono_patch`).
- Fix: switch the shell off through the `TPConfig` string constants in the dex (value `true` → `TRUE`, same length, refresh SHA-1/adler32), and ship plain assemblies dumped from the original game's memory. Details and script: `case-c-micro-client.md`.

**Root-owned files cannot be pulled; stream instead**
- Symptom: `su -c "dd … of=/data/local/tmp/x"` worked, then `adb pull` failed with "remote open failed: Permission denied".
- Fix: skip the temp file: `adb exec-out su -c "dd if=/proc/<pid>/mem bs=4096 skip=<page> count=<n> 2>/dev/null" > local.bin`.

**Appended code in a game UI module crashed the whole UI init (`table` is nil)** (2026-10-21)
- Symptom: after appending a module to `ui/uiprivateagreement.lua`, loading stuck at 75%; the log said `attempt to index global 'table' (a nil value)` in the module's main chunk.
- Cause: the module uses `module(..., package.seeall)` but then `declareSingleton`/`declareObject` replaces the module metatable with one whose `__index` is the base class, so globals (`table`, `pcall`, `UnityEngine`) are nil inside. The game's own files reach them through a `local Gox = _G` at the top.
- Fix: go through the file's `Gox`; the patch script now lints appended modules for bare globals and asserts the host file has `local Gox = _G`.

**Zero-filling every struct property made the game fine the player** (2026-10-21)
- Symptom: after sending every struct-typed player property as an all-zero struct, login showed "您的账号将被处以罚金并进入处罚状态".
- Cause: the client treats `punish.endTime ~= nil` as "punished"; `0` is not nil. The real server sends only non-default properties and lets the client fill defaults (`{}`, fields nil).
- Fix: send only what the save holds; give the properties the client really needs (`home.homeSkinId`, `home.<npc>Id`, `homeTree.treeLv`...) explicit values one by one, found from the errors.

## 案例 C：玩家备份接入（2026-10-22）

**Backed up the test save, then uninstalled in the same line; the backup had failed** (2026-10-22)
- Symptom: `adb pull /sdcard/…/save.mp …; adb uninstall <pkg>` — the pull printed "failed to stat remote object '<Git install dir>/sdcard/…'", the uninstall went ahead, the test save was gone.
- Cause: Git Bash rewrote the device path again (entry above), and `;` does not stop on failure.
- Fix: `export MSYS_NO_PATHCONV=1` at the top of every Bash call that passes device paths, and chain "back up → destroy" with `&&`, never `;`. Check the backup file exists before any uninstall or `pm clear`.

**Same versionName and versionCode, different APK** (2026-10-22)
- Symptom: the APK inside the player's phone backup had the version we had been patching (same versionName and versionCode), yet 1518 entries differed, including the managed assemblies and the Lua bundle.
- Cause: the publisher re-packed the same version later (resource refresh); version numbers were never bumped.
- Fix: compare APKs entry by entry (CRC + size), and compare the resource manifests' own version fields. When the backup's APK is newer, rebase the build on it and re-dump anything that came from the old one (here: the decrypted assemblies).

**A micro client deletes your pushed resources on the first start after install** (2026-10-22)
- Symptom: 31,153 bundles pushed to `Android/data/<pkg>/files/assets/`; after the first start 31,125 were left.
- Cause: on a "new program" start the launcher compares external bundles with the *package* manifest: it deletes the external copy of every bundle the package also has, deletes bundles whose MD5 does not match, and deletes the external manifest and the Lua hot-update folder. The 28 missing ones were hot-updated versions of bundles that also exist (old) in the APK.
- Fix: ship the final manifest as the package manifest, replace hot-updated in-package bundles with the final files in the APK, and fold the Lua hot-update folder into the Lua bundle. Read the launcher's "install new program" path before deciding where resources live.

**UnityPy `read_typetree()` ignores what `save_typetree()` stored** (2026-10-22)
- Symptom: added 112 TextAssets one by one, each time reading the AssetBundle object, appending to `m_Container`, saving. The rebuilt bundle had 8533 objects but only 8421 container entries.
- Cause: `read_typetree()` always parses the object's original bytes; the previous `save_typetree()` result (held in `obj.data`) is not read back, so every add started from the original list.
- Fix: read the AssetBundle tree once, keep it, append to it, and write it back once in `save()`. Reload the saved bundle and assert the counts.

**A method name that exists in both directions broke the RPC name check** (2026-10-23)
- Symptom: the build-time check said `Player.checkNetWork is not client->server`, but the client does send it.
- Cause: the RPC table has `checkNetWork` both as a client→server request and a server→client callback; the checker's dict keyed by (class, name) kept only one.
- Fix: map (class, name) to the *set* of directions.

**`pm clear` wipes the pushed resources too** (2026-10-23)
- Symptom: after `pm clear` for a fresh-save test, `Android/data/<pkg>/files/` was gone, 3.7 GB with it.
- Cause: on Android 9+ clearing app data also clears the app's external files dir.
- Fix: for a fresh save while keeping resources, delete only the save file; use `pm clear` only when you mean to test first-run resource import.

**The phone was attached, but `adb devices` did not show it** (2026-10-24)
- Symptom: Windows listed the phone as a USB device, yet `adb devices` only showed an emulator.
- Cause: several projects share the machine, and each runs its own adb server port. The USB device was claimed by the server on port 5038, not the default 5037.
- Fix: run `adb -P <port> devices` on each port in use (find them with the process list: `adb -L tcp:<port> fork-server`) and target the phone through that server. Don't kill another project's adb server to grab the device.

**Old-style storage permission still reads Download on Android 14, but can't delete there** (2026-10-24)
- Symptom: a targetSdk 28 build found and read resource zips in `/sdcard/Download` after the storage permission prompt, but `os.remove` on them silently failed.
- Cause: scoped storage (Android 11+) lets an app delete only files it created itself; the zips came from another app (browser, file manager, adb).
- Fix: after importing, check whether the file is really gone and, if not, tell the player to delete it in the file manager.

**Sized a revived feature from code alone; the page art said otherwise** (2026-10-23)
- Symptom: a revived "level a card to unlock its message" page was filled with ~50 rows made by pairing every related message onto a card range; on screen, the background art named one specific festival event and its dates.
- Cause: the server-side list was lost, and the row count was inferred only from the client's per-group rule ("exactly 2 per card").

**Imported resources are on disk, but the game still says "not downloaded yet"** (case C, 2026-10-24)
- Symptom: after importing all 31,125 external bundles, level 1-4 refused to start: "story not downloaded yet, 0KB/539KB". Levels 1-1 to 1-3 had worked, so it looked like a missing file.
- Cause: the micro client decides "downloaded" from its own table of missing bundles (`MicroAssetMgr.allBundles_`), not from the files. On first install it marks every external bundle missing and saves the table (`res.dat`); the original downloader removes one entry per finished download. Importing files bypasses that, so the table never empties. 1-1 to 1-3 only worked because their bundles happen to ship inside the APK.
- Fix: at the end of the client's resource start-up jobs, drop every table entry whose file exists and re-save the table. Here that was 31,125 file checks, spread over frames, 2.8 s on an emulator. General rule: when you replace a downloader, find the state the downloader maintained (ready flags, size counters, serialized lists), not just the files it wrote, and test content whose assets are *not* in the APK.

**"Offline" build still phoned home whenever the phone had a network** (case B, 2026-10-24)
- Symptom: none visible. Every test had run with the game's network blocked, so nobody had looked. With the network open, the build sat on the disclaimer page and tried 22 addresses within 100 s (publisher analytics and gateway, one-tap-login SDK, QQ Connect with the phone model).
- Cause: only the privacy dialog had been skipped; the publisher SDKs still initialize in `Application.onCreate` and after the privacy callback.
- Fix: drop `INTERNET` from the manifest and add a release check that fails if it is back. Then cold start with the network open and expect zero sockets and zero DNS queries for the app's uid.

The SDKs caught theirs; the engine's MAC lookup did not, and startup died on an empty device-info JSON. Keep the network-*state* permissions, because a missing one throws as soon as an SDK calls it.

**The decompiled data table disagreed with the game at runtime** (case C, 2026-10-24)
- Symptom: workshop evolution consumed 2 copies on the device, while the same server code run in lupa against the decompiled `data/partevolution.lua` consumed 3. The UI showed "14/3" (it prints `originalNum + 1`), i.e. 2 at runtime.

- Fix: never hard-code numbers copied from decompiled tables into the fake server; always read `Data.xxx` at runtime. When a device result disagrees with an offline test, log the runtime value (`N.log`) before "fixing" the server. **A scout "waited on its own background work" for 40 minutes** (case C, 2026-10-24)

**One daily cap reset at midnight while every other daily reset at 05:00** (case B, 2026-10-24)
- Symptom: none in play-through; found while auditing. A minigame's daily reward cap reset at 00:00 Beijing time, the rest of the dailies at 05:00, so between midnight and 05:00 the cap was already fresh while the day's other limits were not.

**Removing INTERNET made a vendor ROM ask "allow this app to turn WLAN on or off?" on every launch** (case B, 2026-10-24, HyperOS)
- Symptom: three seconds after each cold start a system dialog from the security center asked whether the game may toggle WLAN. The emulator never showed it.
- Cause: the publisher SDK reads the MAC address by enumerating network interfaces; without INTERNET that returns null, so it falls back to `setWifiEnabled(true)`, reads `/sys/class/net/wlan0/address`, then restores the old state. A targetSdk < 29 app can still really toggle WLAN on Android 10+; MIUI/HyperOS intercepts it as a prompt.
- Fix: stub the fallback (return empty, the SDK's own "no MAC" branch). Lesson: after removing a permission, cold-start on a real vendor-ROM phone, not only an emulator, and grep the SDKs for calls that change device state (`setWifiEnabled`, `requestNetwork`, `startUsingNetworkFeature`).
**去掉 INTERNET 后，真机上点进设置就闪退（案例 C 2026-10-24）**

- 修法：录屏的同时，脚本每次 adb 点按都记下主机时间。剪辑前先算录像的逐帧运动信号，用一次已知的点击标出主机时钟和录像之间的偏移（实测误差约 0.5 秒），再按点按记录生成剪辑表：空等段加速，高光段保持原速。成片抽帧拼成总览图，逐段检查开头有没有残留的加载画面或主界面。本例从 5 分半压到 3 分钟出头。
- 没声音时：先查是哪种静音（响铃模式、勿扰、媒体音量为 0）。只在录制期间临时调高媒体音量，录完调回原值；录制时声音被接走，手机本身不会外放。本来就没有背景音乐的开头（免责页、登录页），用主界面的音乐垫上。录完要还原测试存档、删掉授权码文件、释放设备登记。

## 「按钮点了没反应」先查有没有没回的等回包请求（案例 C，2026-10-24）

- 现象：每日任务面板里第 1 个活跃宝箱点了不发请求，同面板别的按钮有的能用；模拟器上什么都不提示，真机上过一会儿弹「数据请求超时」。
- 原因：面板 onInit 发了一个 RPCWaitSend("queryElect")（评选赛数据），本地服务器没接 → 客户端的等待遮罩把界面锁到超时，这段时间里的点击全被吞掉。和特效、射线检测都无关（之前在这上面白花了两轮）。
- 做法：一出现"点了没反应"，先看 logcat 里有没有 `unhandled`；更彻底的是把客户端所有 `Event.RPCWaitSend / RPCOverTimeSend` 的请求名扫出来，和服务器已注册的对比，没接的至少回一个空包（脚本思路：正则扫 `Event\.(RPCWaitSend|RPCOverTimeSend)\s*,\s*"(\w+)"`）。

## 中途改属性客户端不理：只有 setX、没有 onX（案例 C，2026-10-24）

- 现象：在线时周期开启（05:00 的周六周期）、角色支线通关后下一关解锁，都要重新登录才生效。
- 原因：客户端属性分发（refreshEntityProperty）登录时调 `set<Name>`，之后变化调 `on<Name>(old, new)`。很多模块只写了 setX，在里面把数据拷进自己的管理器（ActivityCycleMgr、TaskBranchData），中途用 batchSyncProperty 推属性，值虽写进了玩家对象，管理器里的副本不变。原版服务器中途用的是专门的推送 RPC（notifyCycleStatus、syncBranchProgressData）。
- 做法：服务器中途推属性前，先查客户端有没有 `on<Name>`；没有就找同名的 sync/notify RPC。可以写脚本扫 `function set(\w+)\(self` 和 `function on(\w+)\(self, *old`，和服务器会中途推的属性求差。另一个连带坑：重发属性的计算函数里如果有"已通知"之类的副作用（cycle 的 notified），重发会把增量推送吞掉。

## 反编译出来的文件内容可能和文件名对不上：用字节码里的 chunk 名核对（案例 C，2026-10-24）

- 现象：`ui/reputationshop/*.lua` 等 112 个文件读出来全是同一个无关文件（AssetDetect.lua），分析了半天才发现。游戏里这些功能是好的。
- 原因：自己写的 UnityPy 打包工具给新增 TextAsset 克隆模板对象、`save_typetree` 写新内容；写入没问题，但之后 `obj.read()` 仍解析模板的原始字节，读源码时拿到的全是模板。
- 做法：Lua 5.1 字节码头部后面就是源文件名（`@UI/xxx.lua`），批量反编译后跑一遍"条目名 vs chunk 名"的比对，0 个不符再用。自己的打包工具里，新增条目的字节码要另存一份，读取时直接返回，不要信 read()。

## 热更新合并后，打包脚本读到的仍是旧版脚本（案例 C，2026-10-24，接上一条）

- 不只新增条目：被热更新替换的 299 个脚本，`set_raw` 写进去后 `read()` 仍返回原始字节。后果是：
  1. 打包时对 `main.lua` 等"读出来 → 打补丁 → 写回"的文件，实际是对**旧版**打补丁、覆盖了热更新版（终版 `HIDE_CHARGE_SYS = true` 丢了）；
  2. 读源码用的协议表、管理器全是旧版，新协议（20 个）在"源码"里根本找不到，看起来像"客户端调了不存在的协议"。
- 做法：自己的资源包封装里，所有写操作（替换 / 新增 / 改源码）都把写进去的字节另存一份，读取优先返回它；合并热更新后跑一遍"字节码 chunk 名 = 条目名"和"读回的字节 = 热更新文件"的核对。补丁锚点换到热更新版上（这次隐私页提示号 210181 → 210182）。
- 判断"是不是读到了旧版"的快速信号：运行时日志的调用栈里出现源码里搜不到的函数名（这次是 `ActivityMgr.syncPromotionalActivityData`）。

## os.date 在游戏进程里会返回错的日期（案例 C，2026-10-25）
- 现象：本地服务器的"游戏日"偶尔在登录时跳到明天又跳回来，按天重置的数据被清两遍。
- 根因：Lua 5.1 的 os.date 调 C 的 localtime / gmtime，结果放在进程共用的静态缓冲区；Unity / Mono 的其他线程同时调用会把它写乱。同一秒里 "%Y%m%d" 偶尔返回明天，"!" 格式的 UTC 错 16 小时。登录时调用最密。
- 修：在最早加载的模块里包一层全局 os.date，连调两次结果一致才返回（客户端模块只把 os 表存成局部变量，也一起受益）。查这类问题时，在可疑函数里同时打印"算出来的值"和"重新格式化一次的值"，两者不一致就是它。

## 客户端"按物品号数数量"的缓存可能在登录时被建成空表（案例 C，2026-10-25）

## 降 minSdk 跑旧系统：R8 已经把低版本分支删了（案例 D，2026-10-29）

## 手机本地模型被系统后台限速、发热降频，慢到每秒一个字（案例 D）
- 症状：llama.cpp 在手机上跑小模型，测速程序前台跑还行，丢后台当服务只有约 1 token/s；充电发热时每句等 15~30 秒。

- 做法：不改用户的输入法。验接口做成“预设一键填好 + 测试按钮自动发一句”，用 `adb reverse` 把手机端口映射到电脑上的假接口。小米“USB 安装提示”10 秒自动拒绝，要在脚本里轮询前台、看到安装确认 Activity 就点。凌晨测带语音的游戏用 `appops set <包名> PLAY_AUDIO ignore`，测完改回 allow。
