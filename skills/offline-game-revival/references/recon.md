# 侦察：从 APK 到可改写逻辑层

## 1. 先回答"逻辑层在哪"，不要急着全解包

目标不是拆开所有资源，而是回答一个问题：**游戏规则跑在哪一层？**

| 形态 | 逻辑位置 | 改造难度 |
|---|---|---|
| Unity + tolua/xLua | Lua 脚本（TextAsset） | 低，首选 |
| Unity 纯 C# | `Assembly-CSharp.dll` | 高，要改 IL |
| Cocos / Laya | `assets/` 下脚本 | 低 |
| Laya 原生（Conch） | `assets/cache/<域名>/<crc32>` 里的 `js/bundle.js`；先找线上 `bundle.js.map` | 低，但缓存校验有坑，见 `case-b-laya-native.md` |

先看包结构、有没有 `libunity.so`、有没有 `luascript` 或脚本 bundle，再决定路线。**别对着一堆资源文件空转。**
**同一天顺手查一下 native 库的 ABI。** 列 APK 里 `lib/` 下有哪些目录、`libunity.so` 在哪些目录：老 Unity 游戏（如 5.5 + Mono）可能只有 `armeabi-v7a`（32 位），这类引擎版本做不出 64 位。只有 32 位库的包，装不了「不支持 32 位应用」的新手机（部分新旗舰）和 iOS，这是改不了的硬限制——越早知道越好，直接写进安装说明和 FAQ（替代办法：旧手机、电脑模拟器、云手机），别等用户装不上才发现。

### 同一天要回答的第二个问题："资源齐不齐"

包很大不代表是全量包。找游戏自己的资源清单（Unity 常见 `manifest.*`、`AssetDatabase.manifest`、版本文件），
解析出全部资源包名和大小，和 APK 里实际有的文件做差集，按目录汇总缺多少。再拿内容表（服装、角色、关卡）对一遍，
算出"多少条目有模型"。微端只带开头几章和少量资源，缺的那部分原本在线下载，停服后要么去服务器碰运气、要么靠玩家手机里的缓存。

缺的资源最好的来源是**玩家手机的应用备份**（小米、华为、OPPO 自带的备份会带上 `Android/data/<包>/files/`）。拿到后：认格式流式解开、
用**备份里的外部清单**逐个对 MD5、确认备份里的 APK 是不是和你手上的同一个（同版本号也可能不同）、把热更层（脚本、清单）并进包里。
完整流程见 `case-c-micro-client.md`「玩家手机备份 = 终版客户端 + 全部资源」。

这个结论决定项目能做到什么程度，**要在写任何补丁之前交给用户拍板**。实例（案例 C）：1.2 GB 的包只有清单的 1/4，约 91% 的衣服没有模型
（`case-c-micro-client.md`）。
**找微端的更新地址（YooAsset 一类，案例 F 2026-11-07）**：包里常常没有写死的资源服务器地址，只有 `cdn_url` 这类键名，地址是启动时向一个版本检查接口要来的。做法：把热更程序集从 bundle 里导出来反编译，读版本检查和资源初始化的代码。接口地址可能藏在场景数据（`level0`）里，渠道号等构建信息在 `sharedassets0.assets`，签名用的常量也在包里，按 URL 前缀 grep 就能找出来。照代码拼请求，匿名调用一次，拿到资源服务器地址和各包的最新版本。资源路径一般是 `{cdn}/{平台}/{包名}/{版本}/{文件}`；服务器上的清单可以下载回来，和 APK 自带的清单做差集，算出缺多少（实例：缺 4236 个文件、约 4.55 GB）。
- 资源服务器和版本接口常是两套服务，接口还活着不代表文件能下载。如果域名解析到 `169.254.x.x` 这类不可达地址，换公共 DNS 直连真实节点也超时，说明资源服务器已经下线。下载脚本要在连续失败后退避，别无限重试；不要换 IP 去碰源站，转去互联网档案馆和玩家备份里找。判断是否恢复，要看能不能拿到文件内容，不能只看 DNS。

**最快的可救性判断：把原包装进 root 模拟器，断网冷启动**（案例 E 2026-10-20）：静态解加密资源、解加壳的元数据都很费时间，而游戏自己的代码在运行时就会把它们解开。冷启动时截图、抓 logcat：如果能渲染出完整的登录画面，说明本体和资源基本齐全、加密不挡启动，拦路的只是网络登录层。再看日志，分清登录分几段（渠道 SDK、游戏服连接）。日志里加载失败的资源，去包里和清单里查一下，判断它是热更才有的小资源，还是缺了本体。

## 2. 加密与解密

脚本常被加密后塞进 AssetBundle。密钥通常硬编码在 C# 里，找 `Key()` / `ScriptKey` / `Config` 这类方法名。

实例（案例 A）：1443 个 TextAsset 是 DES-CBC，`key == IV == <8 字节密钥>`，该常量来自 C# 的 `LuaRuntimeConfig.LuaScriptKey()`；`all_lua_files.lua` 是唯一的明文例外。

做法：搜常量 → 认出算法（DES / AES / XXTEA）→ 写脚本批量解密 → 验证解出来是合法脚本（能过语法检查，不是随机字节）。

先排除两种"看着像加密、其实不是"的情况：

- **改头防反编译**：Lua 字节码头部某个字节被改（案例 C 是 5.1 头的 format 字节 `00` → `01`），反编译器直接拒绝。
  逐字节对照标准头，改回去再反编译；操作码没打乱的话输出是干净源码。之后查加载器是否允许明文 chunk（`bytecodeOnly`/mode 参数），
  允许的话补丁直接放明文 Lua，省掉找同位宽 `luac` 的麻烦。
- **单字节异或**：熵比明文只高一点、深处成片出现同一个值（明文的 0），就是单字节异或。Mono 程序集常见"头部强加密 + 其余单字节异或"，
  这时不用逆向解密函数，异或掉尾部再按 PE/CLI 结构重建头部即可反编译（做法见 `case-c-micro-client.md`）。

还要先看 **`AndroidManifest` 里的 `Application` 类是不是加固壳**（某大厂的壳：`com.<厂商>.tpshell.TPShellApplication` + `libtprt.so`，
其他家的壳类名不同）。有壳的话，改过/重签名的包会在启动时被壳自己杀掉，而且壳往往还负责运行时解密脚本或程序集——
"静态解不开的那一小段"很可能就是它解的。去壳和拿明文的做法见 `case-c-micro-client.md`。
**只加密了一段的资源包：先把加密窗口钉死**（案例 E 2026-10-20）：UnityFS 头正常、第一个压缩块解不开、后面的块正常，多半是自定义的局部加密。步骤：手动解析 UnityFS 头和块表，逐块单独解压，看哪些块失败；对失败块的压缩流做熵扫描，熵骤降的位置是加密段的终点；直接在密文上跑 LZ4 解码，崩溃的字节位置是起点；再拿多个包对比起止位置是否一致（实例：1691 个包都是第 0 块的 [56:4096] 被加密，其余是明文）。两个包的密文互相异或，可以探一下是不是固定的流密码。做完这些，就只剩密钥 / 算法没找到。
- 热更 DLL 如果也只加密了开头、PE 头没了，不用重建 PE：直接在解出的字节里找 `BSJB`，解析 `#Strings` 堆和 MethodDef 表，就能拿到全部类名和方法名。按命名分层（例如 `Req*` 是客户端请求，`on*Result` 是服务器回调），离线服务器要合成的就是回调这一层。符号表存档备查。
- 找密钥之前先排除两件事。一是解密后的包有没有落盘：root 看一眼私有目录，成本很低。二是手里那个看着像密钥库的数据文件，是不是加固 SDK 自己的索引（实例：一个 `.dat` 里是多条 zlib 流，解开是类名映射表，不是资源密钥）。`global-metadata.dat` 开头不是标准魔数 `AF 1B B1 FA` 的，说明被壳变换过，主程序集走静态 IL2CPP dump 不通。改登录、网络的逻辑多半在热更 DLL 和脚本层，不必先破主程序集；密钥走运行时，直接取解密函数的返回值。
- **YooAsset 一类的数据表**（案例 F 2026-11-07）：每行带 7 位变长的长度前缀。行内解密：从一个固定种子开始做几轮移位异或，再逐字节异或种子的低字节，种子按线性同余推进。字段按 `Read7BitEncodedInt` / `ReadString` / `ReadSingle` / `ReadBoolean` 的顺序读，列表字段存成字符串。从反编译的数据表类里照抄每张表的读取顺序，写一个通用解码器。两个坑：有的表根本没加密，当成加密去解就得到乱码，要先判断；表结构一定要用最新版热更程序集反编译出来的（实例：换成最新版后，333 张表里 322 张对上了，旧版代码会让二十多张表错列）。

### 加密地图：一次性回答"到底哪些东西是加密的"

项目做久了会有人问"是不是还有没解开的数据"。别凭印象答，花半小时扫一遍，结论长期有用：

1. **全量分类。** 安装包每个条目 + 热更目录每个文件：大小、前 16 字节、魔数分类、前 64 KB 的熵。目标是"未知"类为 0。
2. **熵高不等于加密。** 压缩过的资源包、音频、贴图熵都在 7.5 以上。判断加密看的是：标准工具能不能加载（资源包全部能被 UnityPy 加载 = 包没加密）、公开格式的头在不在（声音库里找得到 `FSB5` 且头部字段合理 = 没加密）、抽样能不能解出正常内容（贴图解成图片看一眼）。
3. **文本类资源逐个判定。** 每个 TextAsset：可读文本 / 公开二进制格式（骨骼、声音库、protobuf）/ 高熵且长度是分组长度的倍数 → 拿已知密钥试解。
4. **固定前缀不是加密。** 资源包开头多出固定的几个零字节是常见的"防通用解包器"手法，跳过即可；回写时原样带上。先去原始安装包里数一遍有多少文件带这个前缀，别把它当成"损坏"去修。
5. **配置表做逐字段核对。** 用协议描述解开后再扫一遍线格式，数"描述里没有的字段号"。为 0 说明协议版本和数据版本一致；重新序列化后字节数和原文件相同是第二个证据。
6. **找第二份数据。** 安装包里常常内置一份旧的配置库（不在资源包目录，而在引擎的数据目录里），热更后手机上那份才是新的。两份逐表比行数，确认构建用的是新的。
7. **运行时的加解密点单列一张表。** 在解开的脚本和程序元数据字符串里搜加解密、校验相关的名字，按用途归类（脚本加载 / 登录标识 / 资源校验 / 支付 / 网络封包），每类写清"离线版要不要管"。网络封包的加密对离线版无关，查不清就如实记为没查清。
8. **把"解不开"和"不在手里"分开写。** 服务器数据库、没 root 取不到的私有目录，是数据缺失，不是加密问题。

实例（案例 A 2026-10-13）：5563 个文件扫完，真正加密的只有 Lua 脚本（DES）和日志里的登录标识（3DES，密钥写死在 Lua 里）；2434 个资源包、247 张表、4906 个文本类资源其余全是明文或公开格式。扫描分给两个执行子代理并行（一个扫包内资源，一个查包外数据和运行时加密点），各约 10~14 分钟；它们标"没验证"的三处（内置配置库、声音库内层、贴图）由主模型补验。

## 3. 运行时侦察：注入类工具的正确用法

打包期改写不是唯一手段——**运行时注入是很好的侦察工具，但很差的交付形态**。

它高效给出的东西（静态分析往往要花几倍时间）：

- **加密密钥**：直接读游戏自己调用的解密函数返回值，比逆向算法快得多
- **函数级靶点清单**：hook 网络层，记录实际被调用的类 / 函数 / 参数，得到"必须改哪些文件"
- **协议 schema**：抓真实请求 / 响应的字段结构，本地回包照着填
- **判断确认**：某个遮罩、某次调用到底是不是问题的原因

边界，必须记住：

- 它是**侦察**，不是**交付**。只要最终产物要求"只装 APK、不 root、不用电脑"，注入方案就不可能过关。
- **探针本身不可靠**：遍历 C# 对象、attach、脚本超时都会失败，长时间会话后更容易反复超时。关键结论要用**静态方式复核**（直接在包里查字符串、比对文件）。
- **它给出的结论可能是错的**：运行时看不到"某个分支永远不会触发"这类事实，容易把时间花在错误方向上。

所以：用它快速建立地图（密钥、靶点、协议），**然后离开它**。不要在"让运行时方案跑通"上投入时间。
## 3. 校验字段：不要猜，看日志

Unity AssetBundle 加载时校验 CRC，值可能存在于两处：

- `<bundle>.manifest`
- `assets/AssetBundles/<Platform>/AssetDatabase.manifest`

**猜哪个生效会浪费一整轮。** 直接跑一次，Unity 会把两个值都打印出来：

```
E/Unity: CRC Mismatch. Provided d906612, calculated ab764880 from data.
         Will not load AssetBundle 'luascript'
```

把生效的那个 manifest 里的 CRC 改成 `0`（跳过校验）或 Unity 给的正确值。

实例：案例 A 实际读的是 `AssetDatabase.manifest`，不是同名的 `luascript.manifest`——先猜错一轮，靠真机日志才纠正。

## 4. 建立索引，别通读

解包后动辄上千条目。做法：

- 生成条目清单（路径、大小、类型）
- 对解密后的脚本建符号索引：函数名 / 类名 → 所在文件
- 之后靠**按符号检索**定位改动点

- **没有直接对应表时，交叉定位**（案例 F）：例如要找某角色的专属武器，先从语音目录名（编号 + 拼音）认出角色编号，再在预设配装表里查这个编号配的武器，回到武器表核对属性和主题，最后用角色编号反查立绘的资源路径。几处证据一致才写进报告，并标明哪些是表里直接写的、哪些是推断的。

## 5. 大文件一律定向检索

历史导出、构建日志、工具输出动辄几十 MB，整读会直接撑爆上下文。

```powershell
Select-String -Path <file> -Pattern "关键字" | Select-Object -First 20
```

目录先取规模再深入，不要递归枚举大目录：

```powershell
Get-ChildItem -LiteralPath <dir> -Depth 1
```

## 6. 侦察阶段的产出
## 外部来源「回包样本」先验真再用

别人发来的「全解锁回包」「抓包」样本不一定是真原版抓包——可能是对方用大模型按配置表生成的。收到先做三步再决定用不用：① 无 schema 的 protobuf dump 解开；② 按客户端协议定义给字段命名，确认它到底是哪个协议（案例 A 一份样本其实是藏品数据 1506，不是以为的区域解锁）；③ 把样本里的 ID 和自己导出的配置表逐个比对，看有没有新信息（那份样本 326 个藏品 ID、101 个套装 ID 和配置表完全一致，只有藏品 / 套装字段，没有区域解锁字段，另有几个数值找不到出处）。数值没出处的不照抄。

从玩家截图反推商品编号时，先拿中文名在**解密后的全部配置表**里 grep（物品名分散在不同表：普通道具表、花笺卡表……只查一张会漏）；被挡住 / 缺失的格子按同类成套的规律推，并在汇报里标 `[推断]`。
**配置表能还原多少，先分三类再动手**（案例 A 2026-10-12，以卡池为例）：① 表里完整的（常驻池、限时池、活动池的条目和概率），直接导出；② 只有名字、日期、档位而没有概率的，做成「自定规则」交给用户拍板；③ 所有奖励表里都查不到的（例：哪次充值送哪只限定宠物），也交给用户定，别在上面白耗时间。做总表时，用「出现在哪些卡池表里」把池外的条目挑出来，再交叉查是哪些表在发放它们。

**玩家记忆里的玩法入口要拿代码核对**（案例 A 2026-10-12）：用户记得「点某页的卡会出树状剧情，星数不够解锁不了」，代码里那一页点卡是直接播剧情；树状剧情和星级锁其实挂在另一个按钮下面。先拿配置表字段（节点、前置节点、星级）和客户端的入口代码找到真实入口，再写回包，并在汇报里点明和记忆不一样的地方。

一份能直接支撑改写的最小结论：

1. 逻辑层是什么、在哪、怎么解密
2. 校验在哪、怎么绕过
3. 启动 → 登录 → 主界面这条链路上，有哪些必须拦截的调用
4. 一个 known-good 的回滚点（原始包 + 当前可运行包）

## 复现不了的设备问题：先收诊断，再动手（案例 C 2026-11-06）
玩家报"电流声"、"开 Wi-Fi 就卡"这类模拟器上复现不了的问题时，只做低风险改动（这次把"录麦克风判断吹气"改成按住算吹到，录音会把音频切到通话模式），并在导出日志开头加诊断信息（CPU、联网状态、帧率、音频采样率），等下一份日志再定。
