# 发布与分档：发新包不丢玩家存档

> 来源：案例 A 离线纪念版 2026-10-17 的分档分发设计。只讲技术，不涉及定价和商业规则。

> 这篇是通用的发包技术，不限于停服游戏。常见的正当用法：发布你自己开发的游戏；在权利人授权下分发纪念版；发布取得授权的二创、同人作品。授权码绑定设备、水印标出每一份的来源，都是为了限制安装包被恶意传播。具体能不能分享、能分享给谁，取决于当地法律和权利人的态度，请自行判断。

## 1. 覆盖安装保住存档的硬条件

Unity 游戏的存档一般在 `/data/data/<包名>/shared_prefs/<包名>.v2.playerprefs.xml`，卸载就没了。覆盖安装能保住存档，要同时满足：

| 条件 | 做法 |
|---|---|
| 包名不变 | 所有版本、所有档位都用同一个包名。别为某个客户单独改包名，那等于新装一个游戏，存档带不过去 |
| 签名不变 | 发布 keystore 至少备份两处（另一块盘 + 离线介质）。丢了它就再也发不了能覆盖安装的更新 |
| versionCode 不降 | 相同可以覆盖，降了会被系统拒绝 |
| 存档格式只加不改 | 新功能用新键，「键不存在 = 老行为」；旧键不改名、不改含义。项目里如果有「存档纪元」一类会清档的开关，发布后永远别动 |
| 防旧包写坏新档 | 加一个存档版本号键；包里写死自己认识的最高版本，读到更高的就拒绝进入并提示更新 |
| 已分发的包可重现 | 出包前提交源码并打标签，记下哈希。发现分发包是用未提交的工作区打的，立刻补提交、核对源文件修改时间早于出包时间。项目不在 git 里时（案例 B），构建脚本把每个构建输入的 sha256 写进包内的构建清单，正式包另存一份输入快照 `release/src-<tag>.zip`，发包检查脚本比对两者——快照目录不可再生，和私钥一起备份 |

**老 Unity 游戏还要检查两件和「新手机装不上」有关的清单字段**（案例 C）：
- **ABI**：只有 32 位 native 库的包装不了不支持 32 位应用的新手机和 iOS，无法修，写进安装说明和 FAQ（见 `recon.md`）。
- **max_aspect（maxAspectRatio）**：清单里声明得太小（如 2.2），而常见 20:9 屏幕是 2.22，刚好超出，系统会把老应用缩成屏幕角落的小窗。打包时在清单补丁里把 `max_aspect` 改成 3.0（用 `aapt2 dump xmltree` 核对改没改进去）；已发出去的旧版本让玩家在系统设置里给应用打开「全面屏显示」。挖孔屏顶上空一条没法在清单层修，写进 FAQ。

## 2. 分档：一种包 + 授权码里的功能位

不要按档位各出一个包：维护量翻倍，玩家在档位之间换包时，存档里引用的内容在低档包里没有配置，会报空值。

做法：
- 授权码（设备码绑定、私钥签名）的载荷里带一个**功能位**字段，档位只是功能位的预设组合。
- 授权码**原文**存进存档，每次启动重新验签再算功能位。不要只存一个算好的数字，那样改存档就能升档。
- 升档：在游戏里输入一个新授权码，不用重装。旧格式的授权码继续有效，映射成最低档，已分发的玩家不受影响。
- 代价要讲清楚：低档玩家的包里其实也有高档内容。如果脚本层能被解包，这些内容挡不住铁了心的人。所以要配合按份水印，并且只在信得过的范围分发。

- **客户端没有兑换码输入框时**（案例 C）：本机码用客户端已暴露的 `SystemInfo.deviceUniqueIdentifier` 来算，放在设置页的“复制”按钮里，点了弹出并写进剪贴板；授权码借聊天框或改名框输入，按固定前缀分流到授权分支；权益做成告示邮件，玩家点领取才执行。
- **门禁页把本机码当主角**（案例 A）：玩家不会走网页流程拿码。门禁页用富文本把本机码放大，借原来隐藏的按钮改成「复制本机码」（`GUIUtility.systemCopyBuffer`）和「打开反馈渠道」（`Application.OpenURL`），不新建 UI。
- **给所有过了门禁的老玩家免签送一个新活动**（案例 A）：在发布配置里加一组「过门禁即送」的位，过了门禁就并进有效授权。门禁本身不动，包里只带这一个活动，带不出别的内容。脚本加密后没法在包里搜，要在模拟器上用旧码存档实际跑一次，确认入口出现。
- **验签前先查脚本引擎的底子**：案例 C 手机上是 32 位纯解释的 Lua 5.1（armeabi-v7a 的 `libslua.so`，没有 JIT，也没有 bit 库），大数运算很慢。用纯 Lua 自己写 SHA-256 和 RSA 验签，公钥取小指数，估算耗时 17~43 毫秒，真机验证通过。
- **授权只升不降**（案例 A 2026-11-01）：游戏里输入新码时先比高低，比现有授权低的不替换，只提示已经包含；签码工具（命令行、机器人、图形界面）新签的码自动并入这台设备以前批过的全部功能位。否则高档玩家顺手输了机器人自动发的基础码，看起来像「东西被删了」。判断逻辑用 lupa 在电脑上测高换低、低换高、同档重输三种。
- **玩家说码用不了**（案例 A 2026-10-26）：先用游戏内置公钥验签，核对长度和截图是否一字不差，排除码本身的问题；再用脚本照游戏的校验规则模拟各种粘法（只粘码行 / 整段全粘 / 选到消息末尾 / 少两个字符 / 多一个全角空格），看各报什么错，和玩家的提示对上。发码模板把码单独放在最后一行，写明「只复制最后一行」；让玩家先粘进备忘录看头尾对不对，再换系统自带输入法试。根治办法是门禁页加「粘贴授权码」按钮直接读剪贴板、输入框不用密码框、从整段文字里自动挑出码，但这要发新包。
机器人私信发码时，说明和授权码分成两条消息，码单独发一条：手机端长按复制，拿到的是整条消息（案例 B 2026-10-29；还没用真实私信领码跑过）。
- **签码台账**：发码工具的测试必须把台账、序号文件、码文件都指到临时目录（工具加一个台账目录的环境变量，没设才用正式目录），测试一开始就断言路径指向临时目录，跑完核对正式台账行数没变（案例 B 2026-10-20，此前每跑一次测试就往真台账写十几行）。台账去重：每台设备只留最后一次签发；设备码只会是十六进制，带 G、O 的是手误，一起清掉；先干跑再执行，旧记录挪进带日期的备份目录，不直接删，序号计数不动；两个码只差字符顺序、格式都合法的，交给用户判断。
- **在手机上签码**（案例 A 2026-10-24，网页还没在平板实机跑过）：签名算法在手机浏览器里都能算，可以照桌面工具把签发逻辑复刻成一个网页。私钥不放进网页，在电脑上用口令加密成密钥包，网页解密后只存在浏览器本机；手机端的序号段和电脑端错开，签发自动记台账；用真私钥签出的码拿游戏内置公钥（或游戏自带的校验脚本）验签，并和桌面版逐字比对；密钥包和口令分开放，确认密钥包路径已被 gitignore。
## 2.1 剥内容版：只带部分章节 / 功能的防转载包（案例 A 2026-10-17~23）

只靠隐藏按钮不安全：功能代码、配置行和资源还在包里，有人拿高档授权码或旧存档就能把功能弄出来。要在打包期按「入口 → 数据 → 资源」整条链剥：
- **一套脚本用 profile 切换**：另写一份 `release_content.<profile>.json`，用环境变量指向它；所有读取点改成「环境变量优先，默认读原文件」，新字段一律可选，全量包不受影响。先 dry-run 看剥离计划和行数，再真打。
- **只删资源不够，文本还在配置表里**：剧情图删了，对白表解包照样读得到。要按行过滤配置表；保留哪些段，要从保留内容自己的表追引用（例如活动剧情表 → 对白段号），别按章节字段过滤（一个章节号可能对应好几个活动）。静态复验的期望行数要随 profile 切换。
- **删了数据也要删入口**：剥掉某类角色剧情的文本和配音后，如果入口还在，点进去要加载的配音包不存在，就会卡在空白界面。要么把要保留的几类放回包里，要么删掉驱动入口的数据表，让入口跟着数据消失。和别的玩法共用编号的资源包不能整包删。
- **别的活动可能借用被剥活动的面板**（案例 A 2026-10-24）：几个活动的兑换商店共用同一个窗口，预制体放在其中一个活动的包里；剥那个活动时连包一起剥了，别的活动点商店时回包正常、窗口却不出现。剥离前 grep 面板类名和包路径，看有没有别的活动在借用。补回后还要查依赖，见 `pitfalls.md`「留下的资源包在总清单里依赖已剥掉的包」。
- **保留清单从配置表反推，别按目录编号猜**：资源目录的编号不等于使用它的章节。卡面要经过「卡面名 → 资源名表 → 包路径」才能定位；卡面名里用 `|` 分成卡面 + 背景两层的，要拆开逐段解析；对白配音对应的声音库可能放在后面章节的声音包里。能获得的卡（卡池 + 剧情奖励 + 活动赠送）要全部算进去；清单脚本带 `--check`，有缺失就非零退出。
- **保留清单还要追两条链**（案例 A 2026-10-30~11-04）：① 动态卡面的骨骼层不写在卡面名里，要经「卡面动画表 → 资源名表 → 包路径」另算一遍，漏了只剩背景、人物不见；② 对白用的背景和立绘常放在别的章节的包里（例：第 3 章某节的背景在第 9 章的包里），要扫全部对白表，把引用到的包逐个对照 APK 算出缺口。改了开放范围（例如免费版多开一章）后按顺序重跑：资源引用脚本 `--write` → 对白资源检查 → 静态复验（期望行数随之更新）→ 打正式包点验。开发包不剥离，开放范围只能在正式包上验。
- **静态复验脚本靠环境变量知道当前是哪个 profile**：没设就按全量期望比，剥离包会报 FAIL；反过来全量包上按剥离版写死的行数比，会固定报一项不过。检查前先设好变量，固定的已知失败写进验收说明，免得每轮重新排查。
- **剥功能用源码标记块**：模块里用 `-- @STRIP{feature}` / `-- @/STRIP{feature}` 包住，构建时按配置删掉，并断言标记成对；同时屏蔽对应的授权位，配置库里不加对应的道具 / 槽位；最后在脚本包里搜被禁的函数名，有残留就构建失败。再在模拟器上用「全开」授权码试一遍，确认这些能力仍然被屏蔽。
- **同包名覆盖安装会带来别的版本留下的放行标记**（例如「全解锁」标记让剥功能版也能选全部头像）：剥功能版要把读取这些标记的代码一起剥掉，不能只去掉写入的地方。
- **验收**：剥离和去掉调试通道都绑在 `--final` 上、开发包不剥离时，剥离效果用静态复验脚本（同时查资源和配置文本）加正式包的冷启动日志来验，功能逻辑在同数据的开发包上注入验，汇报时写清各自证明了什么。在剥离包上把每个保留入口都点一遍，日志里的 `asset isnull` 和 Lua 报错都要为 0。原包里本来就没有的资源要记下来，别算到剥离头上。

## 3. 活动开期

- 日常活动：内置日历，从一个固定锚点按真实日期轮换，不用存档，所有人同一天看到同一个。
- 限定活动：签名兑换码，载荷是「活动 ID + 开始日期 + 天数 + 范围（全体 / 某设备）」，群里发码就等于开活动。私钥只在开发者本机，别人伪造不了。
- 领奖记录按「活动 ID + 开期」分开存，防止拨系统时间重复领。
- **想让活动有稀缺感，用硬规则，别只靠涨价**（案例 A 2026-11-03）：累计型任务和可补领的奖励会抹平价格门槛，价格只能卡总量，卡不住「每天都要来」。先按全勤收入、各类任务总量算账，再加规则：全勤门槛（登录奖励领满才能换卡，商店拒绝并提示）；一期只能换一件衣服或场景（换完其余货位消失）。活动币结束会折成别的货币、不能攒时，单件价格不能超过一期的最低免费收入。

- **往期活动一次复活几百个时**（案例 C 2026-10-25）：按组做成轮换线，每周一 05:00 换期，每条线本周只开一个，免得活动面板挤爆。每批走固定流程：worker 交货 → 自己跑模块检查和全部冒烟 → 打包 → 订设备 → 换测试档和授权码 → 只点验本周轮到的那一期 → 还原存档并逐字节核对 → 释放登记 → 提交。汇报时把“真机验过”和“只在测试环境验过”分开写。终版表里没有数据的期数直接排除，并写明原因（例：复刻商店 24 期里有 14 期因商店表无数据被排除）。

**往期活动批量复活：有日期的按原版日期锁死，没日期的做成自选（案例 A）。** 服务器停了没有开活动的机制，而原版活动常横跨好几年，一起放出来或固定轮换玩家觉得没意思、挤进一年又会撞期。做法：
1. 从配置表把每个往期活动的起止日期抽出来做成排期模块，有日期的每年同月日开、开原版那么多天；撞期时同一类同时只开一个，优先开「对应原版那一年」的（按年份轮转）。
2. 日期缺失或本来就与同类同开的，做成设置页里的「活动自选」，玩家点了当天开、同类在开就排队；没日期的默认开 14 天。
3. 本地应答活动排期请求（如 `GET_ACTIVE_NOTICES`，时间用 Unix 秒），**先校时**（离线客户端的服务器时间恒为 0，见 `pitfalls.md`）；每个活动模块自己登记轨道。验证用时间快进把时钟拨进活动期再看入口和界面；对白累计次数很大的玩法不要做成限时，否则永远攒不够。
4. 电脑上先模拟几年逐天跑一遍，确认每个活动都开得到、同时开的数量不离谱。

**自选入口别用邮件 / 告示发（会一次多出十几封信，玩家嫌乱）**：借用设置「更多」页里离线本来就点不了的按钮（如「公告」），改成弹选择框，一页一个活动、按钮「开这个 / 下一个」。注意确认框点空白会触发取消回调，「下一个」不能放在取消键上（见 `pitfalls.md`）。

**本地活动排期模块的结构（案例 A 2026-10-13）**：以一个固定纪元（某天 05:00）为起点，每条轨道写明（活动类型、周期、时长、间隔），按当前时间算出哪些活动开着；应答排期请求和活动 CG 已读，到边界时重推一次通知。顶部图标类活动互斥，侧边入口各条轨道各自轮换；各活动模块只往轨道表里登记自己的轨道。客户端拿到通知后，会自己给相关地点画「限时」标记。用户问「这个活动什么时候开」时，用脚本按代码里的纪元、周期、偏移，把每个活动的开期算成日期表写进文档，再拿设备日志里的剩余时间核对；存档带开发时间偏移的，要告诉用户游戏时钟比真实日期快几天。按农历的节日，用 `lunardate` 一类库生成多年的日期，不凭记忆写。

## 4. 每个玩家不同的内容（头像、卡面）放进游戏里做

- 不为每个客户打一个包。在底座配置里**一次性预留空槽位**（头像位、卡位，带齐配套的子表行），游戏内编辑器只往槽里填内容。
- 图片和视频从手机相册导入，复制到游戏自己的目录，存档里只记文件名。
- 先查原包有没有现成的权限封装，往往不用改 Java 层就能弹相册授权框（见 `pitfalls.md`）。

## 5. 存档迁移（换手机）

游戏内导出存档文件，带上来源设备码和校验 → 开发者用工具重签到新设备码 → 新设备导入，只接受签给本机的文件，导入前自动备份。离线做不到吊销旧设备，这是已知上限。

实现要点（两个案例都做过：Unity/PlayerPrefs 一次、Laya conch/localStorage 一次）：
- **签名复用授权码那把私钥**，消息加域前缀（如 `"<MAGIC>|" + SUM + "|" + 目标设备码`），防止授权码签名被挪来当存档签名。导出文件不带签名，所以玩家自己备份的文件也要经开发者重签才能导回去——这正是防篡改的那道门。
- 导出排除绑设备的键（授权码、本机种子），导入时也跳过它们、保留新机原值。
- 导入顺序：**先备份当前存档到用户可见的文件夹，写不出备份就整个取消** → 冻结离线服务端的内存存档（否则定时落盘会把刚导入的数据盖掉）→ 清旧键写新键 → 提示后自动退出进程，重开时所有缓存从新存档读。
- 文件放「下载」：targetSdk ≤ 28 的老包仍是旧式存储，补 `READ/WRITE_EXTERNAL_STORAGE` 清单权限 + 运行时 `requestPermissions`（只在点导出 / 导入时弹）。查找文件要递归两层子目录，覆盖聊天软件保存到「下载」下的子文件夹。
- 开发者工具配 `inspect`（看导出时间、键数、昵称、进度）和 `migrate`，台账单独一张表；签之前先 inspect 一眼，可疑就不签。
- 新机要先有授权码进过一次游戏才看得到"导入"按钮（入口挂在授权后的公告 / 设置页），在玩家说明里写清顺序。

## 6. 并行开发的分工

- 先写接口规格（全局函数名、功能位名、存档键），每个会话在自己的 git worktree 和分支里干活，只改自己负责的文件。
- 调用方要对「依赖的函数还不存在」做兜底，各分支才能独立构建、独立验证。
- 真机一次只给一个会话用，设备占用写在一张登记表里。

## 7. 上线后：玩家 bug 反馈闭环

不管是你自己做的游戏，还是在授权下分发的纪念版、二创、同人作品，包发出去以后 bug 都会不断冒出来。别靠翻群聊，搭一条固定的流水线：

1. **一个地方收**：论坛帖子（如 Discord 的论坛频道）比群聊好，一帖一事，能贴标签、能回头查。置顶一份发帖模板：包的版本、档位、机型、复现步骤、截图或录屏。
2. **机器收集，AI 分诊**：定时拉新帖，跳过已经处理过的，分成"真 bug / 用法问题 / 重复 / 新需求"。真 bug 先在模拟器上复现，复现不了就回帖要录屏。
3. **修完要验**：同时发了几个包或几个档位的，每个包都要修到、验到；回复里写清楚"哪个版本修好了"。
4. **对外发言要人点头**：AI 起草回复和标签，用户看过、点头才发。批量发之前先给用户看完整的待发清单。
5. **留一张处理表**：帖子 → 结论 → 修在哪个提交 → 进了哪个版本。下一轮先读这张表，跳过已处理的帖子。

现成实现：[hearback](https://github.com/Cynthia-wlan9509/hearback)（开源的 Discord 机器人：收帖、归类、交给 AI 修、起草回复，人点头才发）。

**游戏内留一个“导出日志 + 进群”的入口**（案例 C 2026-11-01）：玩家报 bug 往往只有一句“卡了”。在设置页原有的“客服”入口上挂一个对话框，放两个按钮：一个导出日志，一个复制群链接再打开。日志里写版本、包名、机型、角色进度、本次运行的日志环形缓冲（约 2000 行）、最近 60 条请求，再加上一次运行的日志（每 30 秒或出错时落盘），这样闪退后重开再导出，也能看到出事那一次。文件写到「下载」，没权限就申请，申请不到就退回私有目录。注意发布版可能把报错调用栈清掉了（本例 `main.lua` 在发布版里把 `debug.traceback` 换成了空函数）：找到游戏留下的原函数（这里叫 `traceback_org`）自己包一层，所有 xpcall 的处理函数都改用它。

**处理每个帖子先对版本**（案例 A 2026-11-05）：先看玩家的包版本和 `git log`，已经修过的只回「更新到某版」，不重复改；没修过的在开发包上手动走一遍。批量类问题用配置表脚本核对全部条目（例如所有关卡是否可达、需要的道具能不能拿到）。判断不是 bug 的，要给出可查的证据（日志里的某一行），并请玩家导出日志。

## Per-chapter issuing plus free module checkboxes (LIC3, 2026-10-17)

- Payload: `LIC3|group|device|expires|open-up-to-chapter|module-bits-hex|activity-list|serial`. The chapter is a number, not a bit. Parse module bits one hex digit at a time, never through a float, so new modules can take higher bits without hitting the 53-bit limit. Activity list: `*` = all, or a comma-separated list of IDs.
- Old codes must map into the new model (e.g. LIC1 → chapter 2; LIC2 with the MAIN bit → the highest chapter at the time it was issued). Keep the old APIs (`Allows('MAIN')` = cap ≥ old top) so unchanged callers keep working.
- The cap only blocks moving forward; never take away a chapter the save has already entered.
- The issuing tool appends every code to a ledger CSV outside git, and can look up history by device.
- Lua 5.3: `tostring(99901.0)` gives `"99901.0"`. Normalize numeric IDs with `string.format('%d', n)` before any set lookup.
- Pacing: the user chose original pacing for every tier, with "max out" as the paid shortcut. Don't propose global speed-ups; check that max-out clears every level gate.

- 封顶章节 = max(min(授权给的章, 包里最高章), 存档当前所在章)：降档后不回退，当前章也能玩完。包里最高章在打包时从发布清单的章节列表算出，用占位符注入（如 `@PKG_MAX_CHAPTER@`），别写死：章节开到 15 章时，写死的 9 章让 3 个自测用例全挂了。授权函数不存在或报错时，退回旧的总位判断。（案例 A 2026-10-18）
- **2026-11-07 更正：开放章节不再只看码里写的章节**（案例 A）。免费版把免费码抬到第 3 章后，全资源包里拿旧免费码（第 2 章）的玩家，反而比装免费包的少一章。改成按码的内容判断：章节 ≥ 4、勾了活动和抢先体验以外的板块、或活动为「全部」的，算完整授权，开放全部章节；基础码在任何包里至少开到当前的公开范围。所有签码工具的预设一起改，自动发码的程序要重启；完整授权的名单从台账整理成私有文件，不进 git。
- **取消分档、让旧码全部全开时，只改包里的判定，不用重签码**（案例 B 2026-11-07）：放行判断写在包里（`allows(名字)`），对要放开的名字直接返回真，玩家用旧码装上新包就生效。只有单独发放的定制项继续看码。签码工具照样把这些位签进码里，这样还在用旧包的玩家也能用。补偿信、更新说明、玩家说明、发码手册的措辞要一起改。验证办法：拿最低档的旧码和缺某一位的旧码各覆盖安装一次，确认入口都出现，再还原存档、核对 md5。

## 已经发出去的"大功能位"事后拆细（两个案例都做过）

先发了一个"全部活动"位，后来想按单个活动签（加一期活动、单独升档）。做法：
- **只加新位，旧位改成"超集"**：新位各管一期（例如周年 / 生日 / 春节）；判定函数里"问某一期"时，有旧的总位也算真；"问总位"改成"开了任一期"，给几期共用的基础模块用。已发的码不用换。
- **入口按期分开、模块按期关**：主界面入口各认各的位；一期活动的入口若长在另一期的界面里（本例春节横幅在周年地图上），只开它时那个宿主界面照样能进，宿主自己的子入口点了**给分档提示**（"当前授权没有开放……可以找群主升级"），别用"不支持"糊弄。
  拦截函数返回字符串 = 提示文字、返回 true = 通用提示，客户端补丁原样弹出来，提示文字留在离线模块里改。
- 测试和模拟器里所有"假授权"替身要按同样的超集语义改，否则一改开关一片红；用真授权模块签几张组合码跑一组端到端（各组合的判定、摘要文字、拦截提示）。
- 显示名跟着改（总位从某期活动名改成"全部活动"），三处常量（签发 CLI、游戏模块、签发 GUI）一起改。**新位只有新包认识**：旧包会当没开，手册里写清楚。

- **加新位会撞上旧测试**（案例 B 2026-10-20）：旧测试常拿下一个空位（如 0x4）当「未知位」的例子，还写死了各档位的数值。改完常量后立刻跑授权测试，把未知位的例子挪到新的空位，档位值按新表改。已签发的码不带新位，需要换码的玩家要列出来。
- **改规则前先盘点所有签码入口**（案例 B 2026-11-07）：项目自带的签发 GUI 和命令行之外，可能还有放在别的项目里的合并版签发器（桌面快捷方式指向它）、手机网页签发页、机器人自动发码脚本，它们各带一份档位 / 功能位表。那次只改了项目自带的那份，用户打开桌面快捷方式，看到的还是旧界面。要逐个确认谁在用、谁有自己的位定义，同一次全部改完，再用对拍测试核对。机器人如果调用的是同一个签码脚本，就不用另改。

## 存档版本号补到第二个项目时的细节（案例 B v0.8.8，2026-10-23）

- **越早发越好**：保护只在带它的包里生效，更早的包读到新存档照样会写。真要把版本号 +1 之前，先确认玩家都已升到带保护的版本；什么算"+1"写进出包手册（改键名 / 含义 / 编码才算，加新键不算）。
- **挡住进入 + 冻结写盘**，不只是弹个提示：开屏公告页的正文换成说明、按钮改成"请安装更新的版本"；内存里的存档照常读，但写盘函数直接返回。
  导出存档仍然能用（导出读的是原文，正好让玩家留底）；会写存档的按钮（一键拉满之类）藏起来；导入同样检查文件里的存档版本，高了就拒收（查找和导入两处都拦）。
- **读不出来时别直接开新档覆盖**：原文先另存成带时间戳的键再开新档。这个键会跟着导出走，发包人的检查工具（inspect）要能把它和存档版本一起打出来。
- **测试坑**：加载老存档会补写版本号（标脏），所有"操作失败后存档不变"的断言要先 flush 一次再拍快照，否则失败路径里的一次正常落盘会被误判成改了存档。
- **发包检查写成两个脚本**，别靠手工记：① 一键回归（自动发现新加的测试文件，并发跑，慢的模拟可跳过，出一张结果表）；
  ② 核对要发出去的 APK：sha256、签名证书 = 发布证书、不带 debuggable、包里没有调试钩子模块、和上一版对照证书一致、versionCode 和存档版本都没降。最后一行给"可以发 / 不能发"。
  对测试包跑一次确认它三项都报错，才算脚本本身验过。
## 给委托方做定制体验版（案例 A 2026-10-15）

委托方想看一版换了头像、卡面、点击特效、带满级存档的体验包，但不能碰正式包、别的存档和发布线：
- 所有产物放进单独的文件夹；用独立包名（改包名的做法见 `patch.md` 第 5 节）和正式包并排安装，数据互不影响。
- 改动写成一份 `spec.json`（图片、卡牌行、特效缩放等），由一个脚本读它重出整包（每轮约 3 分钟）；签名私钥只读不改。要加新东西（视频卡面、信件、藏品），就是改 spec、再加一步脚本。
- 每一步补丁先 dry-run，再整包重写；debug 包验完，再出正式风格的包。
- 同时写一份给后续 agent 的 README，说明每类改动怎么做。

## 免费公开发布（不用授权码，案例 C 2026-11-01）

免费分发在技术上拦不住二次倒卖；给资源包加密码只会挡住普通玩家（游戏直接读「下载」里的 zip，加了密就导入不了）。最后的做法：
1. 发布版用一个开关去掉授权码，所有权益对所有人开放，做成告示里的权益信，想领再领；聊天框和设置里不再出现本机码。
2. 每次启动都弹的说明框最上面，加醒目的免费声明：本游戏免费，花钱买到的是被骗了，请退款并举报，以及原始发布在哪里找。倒卖的人不改代码就删不掉。

**发布物改名的影响范围（案例 C）**：用户嫌包名里的代号不好听想换时，资源包按「包内第一个标记文件」认（不看文件名），所以资源包可以直接改文件名、内部标记不变，旧名的资源包在新装包上照样能导入。但要同步改：导入页提示语、缺包列表、安装说明都写新名并说明旧名也行。**存档文件名不要改**（会弄坏编辑器和老存档）。

**首次安装插一个强制教程（案例 C）**：玩家不看文档，反复到群里问怎么导资源包。做法：导入资源前插入几页带倒计时的说明（开场说明要滑到底才能点「我已知晓」，用真实滚动判定，别靠计时——见 `pitfalls.md`），之后答十几道情景题（资源包数量、要不要解压、放哪、MT 管理器、更新只覆盖安装不用重下、备份、苹果能不能装、太新的手机装不上），全对才放行；答错当场讲正确做法再问同一题、不从头重来；只对新装、未导入资源的人弹，覆盖安装的老玩家不弹。

**对外说明与版权措辞（案例 C）**：别照用户的意思写不属实的话，并说明为什么。用户想写「没有侵犯原公司的代码」，但游戏本体用的就是原版程序，这话不属实、反而更麻烦；「技术学习交流」这类话也容易让人联想到拆包。只写真实的：游戏和资源来自玩家手机备份；联网部分是自己重写的、不用官方服务器和后台数据；全部版权（含程序）归原权利方；有问题立即下架。删掉「技术学习交流」，分享截图里的官方下载二维码也关掉。写完要告诉用户哪句没照写、为什么。

## 联系版权方（2026-10-25）

- 先查清研发商、发行商和停服原因（例如代理到期），确定先找谁。
- 收件邮箱要核实归属：大公司官网上的商务邮箱常常属于别的业务线。本例用了对方隐私政策里写明的个人信息保护负责人邮箱（政策刚更新过，说明这个人还在岗），信的开头写明借用这个邮箱、请转交法务或 IP 负责人；投资者关系邮箱当备选，两周没回音再发。不要同时群发好几个部门。
- 信里的数字都要能查证（做了多少天、还原了多少条目），只留两三个最能说明能力的。“现在的状态”如实写：分发给了谁、有没有收过钱。
- 去掉 AI 腔：加粗小标题、一二三四分点、“先说结论”“这不是……而是……”、“赋能”“沉淀”、破折号都删掉。视频不发附件，放链接。

补充（案例 A 2026-10-20）：
- **先从游戏自己的文件里挖版权信息**：在解密后的配置表 / 文本里 grep「有限公司|著作权|软著|版权所有|ISBN|审批文号」，常能拿到著作权人全名、软著登记号、出版单位、审批文号，这些在网页搜索里搜不到。顺带 grep 游戏里出现的邮箱。
- **国内工商、软著、商标查询站多数拦境外 IP**，还要验证码、实名登录，这些不能替用户代填。先问用户人在哪、有没有国内网络；没有的话，只查境外能打开的（破产重整案件信息网、搜索摘要、互联网档案馆），其余列成清单，让用户回到国内网络后用手机 App 自己查，并写明要看登记状态、股东、年报邮箱。别反复去试被拦的站。
- **发信前查邮箱域名还活不活**：公司解散后官网域名过期，邮箱也失效了，用 DNS / MX 查询确认。失效的话，改找仍在运营的原发行商的商务邮箱，请对方确认版权归属并转达；官方微博、应用商店认证账号的私信当备选。互联网档案馆里旧官网的「关于我们」页能找到旧的联系方式。
- **第一封信可以只问三件事**：版权现在归谁、请转达给原负责人、愿意走正规授权。说「技术可行性已验证」就够了，不讲具体做法，不用「破解」「解密」这类字眼；不写任何不实的话（例如声称从没分发过）。信先存成草稿，等用户逐字看过、明确说「发」才发；建议用户花点钱咨询游戏 / 知识产权方面的律师。

- **发信前先确认两件事**（案例 B 2026-10-25）：一是授权码在任何环节有没有收过钱，协作者收的也算，收过就先停；二是对方要求停止时立刻停，并删掉演示视频。展示视频里如果能看到授权序号或档位，对方容易当成在卖，信里要主动说明不收费、小范围分发、每次启动都有免责声明。别把项目当成去这家公司求职的筹码；只讲思路，不给安装包。
