# 多 agent 分工：贵模型做判断，便宜模型干体力活

一款游戏的离线化动辄几百个接口、几十万行反编译代码、几十 GB 录屏。全交给最强的模型，额度烧得很快；
全交给便宜模型，又会在关键推断上出错，还会自信地宣布"已完成"。实践下来最划算的是分三层：

| 角色 | 做什么 | 适合的模型（举例，按你手头有的选） |
|---|---|---|
| **主 agent（lead）** | 定方案、做关键推断（补丁点、校验算法、存档结构）、定位疑难 bug、**检查下面两层交回来的结果** | Claude Opus / GPT 旗舰 / DeepSeek-R1 这类推理强的 |
| **worker** | 规格已经写清楚的执行：按清单实现一组接口、写回归测试、批量生成数值表、按方案重构 | Claude Sonnet / GPT 中档 / DeepSeek-V3 / Qwen |
| **scout** | 只读的大范围体力活：全仓搜调用方、通读长日志并摘要、反编译产物初筛、OCR 文本结构化 | Claude Haiku / GPT mini / DeepSeek-V3 / 本地 Qwen |

人类负责：真机上的操作确认、对外发布、任何账号和密钥。

## 每个阶段怎么拆

| 阶段 | 主 agent | 可以并行外包的 |
|---|---|---|
| 侦察 | 判断逻辑层在哪、加密/校验方式 | scout：列出全部网络调用点、搜所有 `localStorage` / 存档读写、统计资源目录 |
| 接口清单 | 定输出格式、抽查 | scout ×N：按模块分组（案例 B 把 315 个接口分成 A/B/C 三组并行）逐个记下"调用方读了哪些字段" |
| 写假服务器 | 设计存档结构、核心模块、公共工具 | worker ×N：每人一组接口，**不碰别人的文件**，各自带 timewarp 用例 |
| 补丁 | 找锚点、写主入口 | — （补丁点之间耦合强，别拆） |
| 时间快进测试 | 定门槛和清单 | worker：按 `timewarp.md` 的清单补用例 |
| 真机验收 | 判断"通过"的标准、读失败现场 | scout：读长日志找第一个异常；人类：点手机 |
| 数值抢救 | 把结构化结果对上配置 id、处理冲突 | 本地脚本（0 token）→ scout 级模型做结构化（`llm_structure.py`） |

不该拆的：几次工具调用就能做完的小活（子 agent 从零开始，要重新读上下文，反而更贵）；
两个任务改同一批文件；后一步依赖前一步的推断结果。

## 省 token：钱主要花在重读旧对话上

三款游戏一共用了一百四十多亿 token，其中 98.5% 是缓存读取：模型每回一句话，都要把前面的对话从头再读一遍。
这部分单价只有正常输入的十分之一到二十分之一，但量太大，仍是账单的大头；模型真正写出来的内容只有三千多万 token。
所以省钱的关键是让每段对话短：

- **一轮一收尾**：每轮结束把现状写进一份 5 KB 左右的快照（当前状态 / 最近几轮做了什么 / 待办 / 接手先读哪几个文件），
  下一轮开新会话读快照接着做。不要把上一段对话整段贴进新会话，也别为了"了解背景"去通读几 MB 的旧对话记录。
- **单次工具输出控制在 8 KB 左右**：长日志、反编译结果、接口清单先落盘，再用 grep 定向看；截图先缩小再给模型看。
  一次输出几十 KB 不只是贵，有的 API 对单条消息有大小上限，超了整轮直接失败。
- **体力活交给便宜模型**（上表），主会话只做判断和收货。
- **模型别只看单价**：真机测试要反复看截图、读日志。实测里一款便宜的模型看图慢、想得又多又乱，同样的活要多跑好几轮，
  省下的单价被轮数吃掉；最后判断和真机测试都换成了最强的模型。

- **同一个点连着两三次没进展就停**：别让 agent 继续换花样试。先只验证一个前提：设备上跑的真是新代码吗？例如让新代码在日志里打一行版本号，看 logcat 里有没有。实测一个便宜模型驱动的 agent 在前提没证实的情况下死循环了两三天，烧掉约 50 亿 token，还走了偏门。卡住的那一步临时换强模型去定位，体力活再交回便宜模型。

## 交接格式（照抄就行）

**派活（主 agent → worker / scout）**，每一项都要写：

```text
目标：一句话说明要交付什么
背景：只给必要的（存档结构在 offline/00_core.js 第 20~60 行；接口规格在 api/B.json 的 delegate/* 部分）
范围：只改 offline/32_delegate.js 和 tests/delegate.test.js；不要动其它文件
完成标准：node tests/delegate.test.js 全绿；新增用例覆盖 timewarp.md 清单的"计时类"三条
交付格式：改了哪些文件 / 测试输出最后 5 行 / 没做完或拿不准的点（单列）
```

**交付（worker / scout → 主 agent）**：做了什么、证据（测试输出、文件行号）、**拿不准的点单列**。
不允许只写"已完成"。

**主 agent 收货**：自己重跑一遍测试，抽查 diff，确认没越界改文件，再告诉用户。子 agent 的结论是线索，不是事实。

**补充两条实测规矩：**
- **派活要给时限**：写明限时（如 60~90 分钟）；卡住的部分先跳过并写清原因，不许把回归丢到后台再空等。案例 C 有一个没限时的 worker 跑了近 5 小时，大半时间在等自己的后台测试。主 agent 看文件修改时间判断它是不是真在推进，没在推进就停掉。另外先让 worker 判断每一项能不能做（要付真钱、要别的玩家、数据表缺行、界面打不开），不能做的直接排除并写明原因。
- **否定结论必须复核**：子代理说“永远 / 从不 / 没有”时，主 agent 要自己去看关键代码行。实测一个子代理只读了调度链里的备用路径，就报“这个首领永远进不了二阶段”；实际上正常路径是另一段代码，条件满足就会换阶段。派这类活时写清判断方法：从调度入口开始，按顺序列出每个处理器的接管条件，再确认具体对象最终落在哪一个。

- **停止条件要分级**（案例 F 2026-11-07）：给下游 agent 的提示词里别写「任何一步出错就停下」。它会照字面执行，把路径找不到、网络读不到这类小错也当成大事，结果干等十几个小时。改成：小错（路径、网络、测试夹具、断言写法）换个最稳的办法绕过去；只有删东西、覆盖文件、改别人负责的代码、多个会话同时装包时才停。项目里的 agent 规则文件也只留少数几条护栏。
- **进度写进仓库，不靠截图**：每段提示词末尾加一句：每做完一步，在进度文件（如 `进度/<会话名>.md`）里追加一行（时间、做了什么、卡在哪、下一步），做完就提交推送；别的会话正在推送时先等。联络方只读仓库核对进度；超过半天没动静，就让用户问一句那个会话是不是停了。

## 在不同工具里怎么落地

- **Claude Code**：本仓库作为插件安装时自带 `agents/revival-scout.md`、`agents/revival-worker.md`、`agents/revival-verifier.md`，
  主 agent 会按描述自动派活；也可以复制到 `~/.claude/agents/` 单独用。
- **支持子 agent 的其它工具**（OpenCode、Codex 等）：把 `agents/*.md` 的正文当成子 agent 的系统提示词，模型按上表选。
- **只有聊天网页（DeepSeek / ChatGPT / Kimi 网页版）**：开两个对话。一个贴 `prompts/chat-playbook.md` 当主 agent，
  它会告诉你要跑什么命令、要把什么结果贴回来；另一个专门做体力活（比如把 `for_llm/` 分块逐个贴进去）。
  能用 API 的话，体力活直接交给 `scripts/llm_structure.py` 批量跑，不用手贴。
- **用 DeepSeek 驱动整套 agent**：任何支持自定义 OpenAI 兼容接口的 agent 工具都能接 DeepSeek
  （OpenCode、Cline、Roo Code 等）；DeepSeek 也提供 Anthropic 兼容接口，Claude Code 可通过设置 `ANTHROPIC_BASE_URL` 接入，具体以 DeepSeek 官方文档为准。
  这时建议 R1 类推理模型当主 agent、V3 类当 worker。

## 实例：按系统并行写本地服务器（案例 C 2026-10-23）

scout 出请求↔回调对照表 → 主会话写模块约定 + 几秒钟的自检脚本 → 三个 worker 各写一个系统文件、各自自检 → 主会话连线（任务进度事件）、合并构建、真机验收。
详见 `case-c-micro-client.md`「本地服务器：并行写模块」。只读的 scout 没有写文件权限时会把报告放在消息里，主会话要自己落盘。

## 两条线共用一个仓库 / 设备时的分工与合并（案例 A）

两条并行线共用一个 git 仓库和一台设备时：
- 分工划清——共用代码（共享主体文件、发布包）由一边负责，另一边只写自己的模块文件、在主入口里只加登记行；发现共用 bug 发一条消息给拥有方，拥有方核实后修，另一方只合并不重做；合并方向固定（发布线 → 探索线）。
- 合并未提交的共用文件时，直接覆盖会被权限分类器当成不可逆破坏拦下（`git merge-file`、脚本重写、直接 `git apply` 都会被拦）。做法：先把这些文件 `git add`（只暂存、留一份可恢复副本），再 `git apply --3way` 打对方的补丁，冲突手工 `Edit` 解决后再 `git add`；合并前先备份。
- 设备占用登记表要是主 checkout 工作区里的一个绝对路径、只有一份（见 pitfalls）；别的 worktree / 分支里各自一份会互相看不见，导致两边同时用设备。

- 设备被另一个会话占着时，后到的会话只做不占设备的事（案例 A 2026-10-12）：从配置表和客户端代码静态解包、写**新文件**形式的模块、做语法检查、写方案文档；不改对方在用的文件，不打包。接入构建要改的几处写成清单，等设备空出来再做，汇报里写明「代码未接入、未上设备」。
## 和外部协作者共用一台编译机（案例 F 2026-11-07）

- 编译、装 DLL、改工程的活一次只跑一个；只读的活，或者只往仓库里加文件的活（导出数据表、打包资源后推送），可以并行。
- 定一个固定的合并时间（例如每晚一次）。合并前一天冻结当天的修复，对准对方最新推送的版本先自测。
- 合并包里给每个独立模块（例如每个首领）一个能单独关闭的开关：某一个没过回归，只撤它，不让它卡住整批。
- 用定时任务在额度刷新后自动唤醒被打断的会话时注意：给会话发消息的工具默认要人点批准，无人值守时会直接被拦下。要提前在设置里给它开免批准；没开之前，定时任务只能出一份「该唤醒哪些会话」的报告，由用户回来手动发消息。
- 给协作者看进度用的共享在线文档，别用浏览器自动化往里插大段内容：光标容易偏，用户同时在编辑时会互相打架，表格列宽也调不动。要表格就导出 CSV，让用户导入在线表格；非改不可时，先请用户别动文档，每改一步都回读页面文字确认。
